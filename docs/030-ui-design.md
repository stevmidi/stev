# UI Design Conventions

The UI uses curated dark palettes rendered with `egui`/`eframe`. All theme colours live in `src/view/theme/` as `egui::Color32` values — the palette literals in `palettes.rs`, the accessors in `mod.rs`; keep new UI work compatible with palette-driven rendering rather than hardcoding colours inline.

## Theme & Contrast

- **Theme presets are first-class**: `src/view/theme/mod.rs` owns the active preset and the shared colour accessors (`bg()`, `fg()`, `accent()`, `track_color()`, etc.). The theme is picked in the settings modal's Appearance tab, or stepped with `Shift+F5` / `Shift+F6` — both apply and save it at once — so any colour used in rendering should come from theme helpers (shapes read the theme at paint time).
- **Theme cycling stays view-local, by design**: `Display::handle_theme_input_event` consumes `⇧F5`/`⇧F6` before input is forwarded, mutating the `static` preset in `view::theme` (`Display::step_theme`). The theme touches no core state; the only thing core does is write it to `settings.json` (`InputEvent::SaveTheme`, so no file I/O runs on the render thread). There is no key arm for `⇧F5`/`⇧F6` in `input_handler.rs` — do not add one, it would be unreachable behind the view-local consumer.
- **Strong contrast**: avoid ultra-low-alpha structure lines. Grid lines and structural markers should rely on manipulating RGB luminance directly (via `Color32::from_rgba_unmultiplied` arithmetic or `gamma_multiply`) rather than alpha alone.
- **Background grammar — every filled region is one of three roles**, and the arranger and the clip view use the same three:
  1. **Content plane** — where musical material lives: `bg()`, or a few RGB steps above it (`bg + 5` arranger lane fills, `bg + 7` note-lane white rows). Canvas, track lanes, note lanes, and the piano roll's **velocity lane** (`bg + 7`, the white-key lane tone — it shares the piano-roll editing surface and its vertical time grid, DAW-standard, rather than being a separate readout).
  2. **Readout strip** — a graduated quantitative band above the content: `bg_timeline()`. The timeline ruler, closed off against the content below it by a `grid_seam_color()` groove seam (1px in the arranger, 2px in the clip views).
  3. **Frame chrome** — a structural panel around the edges: the `bg_panel()` family — `bg_panel()` at the app edges (header, footer), `bg_panel().gamma_multiply(0.8)` for the left gutters (arranger track column, piano-roll legend column). Never used for an internal data panel — that's role 2.
  A new filled region picks the role it belongs to rather than a fresh colour.
- **Grid Hierarchy**: one grid system spans both views, and **the visible grid is the snap grid**. Which tiers exist comes from `GridTiers` (`view/display/grid.rs`): in every view `grid_tiers(pixels_per_tick, 1/16, surface)` picks them from the zoom — a powers-of-two ladder (1/256 … 1/2 bar, 1, 2, 4 … 64 bars), each tier the finest rung whose lines clear a pixel threshold (`MIN_SNAP_PX` 8, `MIN_BEAT_PX` 8, `MIN_BAR_PX` 16, `MIN_LABEL_PX` 28 — and, in the arranger, a stricter `ARRANGER_MIN_SUB_BEAT_PX` 16 for rungs finer than a beat), so zooming the arranger in adds 8ths (from 32 px/beat) then 16ths (from 64) under the beats (never finer than 1/16), while the default 32-bar view — which is also full zoom-out on a short project — is beats at any window width, and zooming out drops the beats, then coarsens the structural tier to every 2, 4, 8 … bars. At the default 32-bar zoom it is exactly bar + beat, snap = beat, a label on every bar. The clip view (`Clip`) uses the same ladder on the **piano-roll surface** (`GridSurface::PianoRoll`), at Ableton's "Adaptive: Narrowest" density: sub-beat rungs need only `PIANO_ROLL_MIN_SUB_BEAT_PX` (6), and the snap floor is the ladder's finest rung, a 256th (15 ticks; `GridSurface::snap_floor_ticks`), where the arranger's is a 16th. So a 2-bar clip fitted to a ~1300 pt clip view snaps to 64ths (16 steps a beat), wider windows go finer, and zooming in keeps halving the step down to 256ths — fine enough to set a clip's end by ear with the cursor (`220-capture-without-pending-view.md`), where a 32nd is ~60 ms at 120 BPM. Bar labels still thin on long clips. More grid options (Ableton's wider settings, fixed grids) are future work. `draw_timeline` walks the finest tier (`snap_ticks`) and draws each line once, **by role** — the coarsest tier it sits on (`GridTiers::role_at`: `Bar` / `Beat` / `Snap`) — never by rung or view: a bar line looks like a bar line at every zoom, and the finest visible tier is always the dimmest. Every line's x goes through `grid_line_x` → `region_bound_x`, the single time-anchored rounding formula. **Every in-lane grid line is the same groove at a falling opacity** (`GridTiers::line_strength`): bar 1.0 — **0.8 in the arranger** (`ARRANGER_BAR_LINE_STRENGTH`), beat 0.5 (`BEAT_LINE_STRENGTH`), finest tier 0.28 (`SNAP_LINE_STRENGTH`) — beats that *are* the finest tier (the default arranger zoom) take the snap strength, so the finest visible tier is always the faintest. One hue, one polarity, softer as it gets finer (the Ableton / Bitwig feel): the bars carry the structure and the subdivisions are barely there until you look. Do not give the finer tiers a different base tone (e.g. `grid_major()` minus a step): it sits lighter than the lane while the bars sit darker, so the eye reads two competing grids, and `grid_major`'s distance from `bg` varies ~13–50 across themes, so in the near-black themes the finest lines come out the brightest on screen. Translucency also lets a line blend with whatever it crosses — the selected-track accent tint, the piano roll's key rows — so one rule serves every view. The grid is drawn after the lane backgrounds and before clips/notes, so it only ever blends with lanes. **Tracks first, time second** in the arranger: its lane seams are the same groove at full strength, and full-strength bar lines would match them, closing every lane × bar cell into a tile — the view reads as a chessboard. So the arranger's in-lane bar lines sit below the seams' full strength (0.8, `ARRANGER_BAR_LINE_STRENGTH`, still above the beat's 0.5, under 1.5pt seams, `ARRANGER_LANE_SEAM_W`), and the bar's prominence is shared with the ruler's full-height tick and number. If the lattice creeps back, the next lever is phrase emphasis (every 4 bars stronger, single bars softer), which makes the strong cells wide rectangles instead of squares. The clip views keep bars at 1.0: no horizontal seams cross them (the octave dividers are a pitch axis, 2px, and never formed tiles). Don't alternate bar or bar-group shading (or lane shading): it draws the chessboard outright. The **structural lines are grooves** — `grid_seam_color()`, a few RGB steps *darker* than the canvas at full alpha (see the grooves bullet under § Borders) — and **hierarchy comes from stroke width, not colour**, exactly as in the arranger:
  - **Bar lines** (`in_lane_bar_color`, `timeline.rs`): `grid_seam_color()` in **every view** — the one vertical division the arranger and the clip view share, so it lands at the same place and tone when you switch between them (a modal layered over the arranger keeps it too). In the arranger the `Bar` role is the structural tier, so zoomed far out it lands every 2/4/8… bars and the bars between are `Snap` lines. Width scales to the job (`in_lane_bar_w`): **1px in the arranger**, **2px in the clip view** (top of three tiers, so it needs to anchor the beats and 16ths below it). It keys off the pane being drawn (`active_pane()`), never keyboard focus (`view_state`) — docked, both panes are on screen, so focus-keyed widths would swap in both on every click. The ruler bar-tick stays 1px (`BAR_STROKE_W`).
  - **Octave dividers** (B/C, clip view — `draw_note_lane_backgrounds` + `draw_piano_keys` + `draw_octave_legends`): `grid_seam_color()`, **2px** — the primary pitch reference, the analogue of the arranger's track seams (the clip view uses 2px, as its bar lines are 2px too). The same seam runs unbroken across all three piano-roll zones (legend, keys, note grid), so all three `.round()` the y identically (or the thickness steps at a column boundary), and the legend draws its segment only when the octave below is in view (`nn > note_lo`) — matching the note grid, which keys off the B one semitone down — so it never leaves a lone half-clipped stub at the viewport's bottom edge.
  - **E/F divider** (clip view): `grid_seam_color()`, 1px — a minor adjacent-white-key seam.
  - **Beat lines** (`GridRole::Beat`, `timeline.rs`): the bar groove at `BEAT_LINE_STRENGTH` (0.5), 1px. Drawn wherever the beat tier exists (clip views always; the arranger once beats are ≥ 8px apart and the structural tier is one bar). When nothing finer sits under them (`!GridTiers::has_tier_below_beat()`) they drop to the snap strength — they *are* the finest tier then.
  - **Snap-tier lines** (`GridRole::Snap`): the bar groove at `SNAP_LINE_STRENGTH` (0.28), 1px — the finest visible tier, whatever rung it is (16ths in the clip views at typical clip lengths, 8ths on long ones; 8ths/16ths, half-bars or odd bars in the arranger depending on zoom). The two strengths are eye-tuned; check the near-black themes (Neon Slate, Verdant Onyx…) first, where the lane sits only ~13 levels above black and the groove has the least room.
  - **The ruler ticks hanging off the timeline strip are the exception** — they keep crisp tones so the timeline itself reads sharp: `bar_color` (`grid_major()` + 26) for the bar tick, `grid_major()` for **both** the beat and snap ticks — graduated by height, not colour: bar 1.0, beat 0.5, snap 0.35 of `REGION_BAND_H` (see § Timeline). **The ruler is a readout, not the snap grid**: bar and beat lines always get a tick, but a sub-beat snap line gets one only on `GridTiers::ruler_ticks` (`has_ruler_tick`) — the finest rung at least `MIN_RULER_SUB_BEAT_PX` (16) apart and never finer than a 16th, falling back to the beat. The piano roll's 6 px snap lines are fine as faint grooves, but a crisp tick at each one turned the strip between the bars into a comb; a fitted 2-bar clip now snaps to 64ths in-lane while the ruler graduates 16ths. Bar numbers draw only on `label_ticks` multiples (`GridTiers::is_labelled`), so they thin to every 2/4/8… bars zoomed out instead of colliding. Only the lines that extend down *into the lane/note area* are grooves / dimmed.

## Clip Anatomy

- **Flat, dark-card style**: clip bodies use `BG_PANEL` as the base fill so they read as slightly darker cards on the `BG` canvas. Avoid gradients, heavy shadows, or anything that breaks the flat aesthetic.
- **A track keeps its colour**: each palette holds 16 track colours (`TRACK_COLOR_COUNT`; the first eight hand-tuned, the last eight generated to sit apart from them at the same lightness and chroma), and a track draws in its own **colour slot** (`Track::color_slot`, mirrored as `TrackLane::color`), not its position — so removing a track recolours nothing below it. A new track takes the next colour in rotation past the last track's that no track uses (`next_color_slot`, `track_edits.rs`); the slot is persisted (`060`). Renderers ask `Display::track_color(track_idx)` (a lane, a clip shape) or `Display::lead_clip_color()` (the piano roll's notes and velocity bars — the lead clip is always on the selected track), never `theme::track_color` with a position.
- **Colour as accent, not fill**: track colours are used at low opacity (≈16% tint) over the dark base, and at full opacity only for small accent signals such as a header strip or left accent bar. Never paint the whole clip body in the full track colour.
- **Clip body edges are pixel-snapped** (`x` / `end_x` `.round()`ed in `draw_arranger_view`, `original_x` / `original_width` kept raw for the thumbnail math): a fractional left/right edge antialiases across two columns, and one clip's tint/header then bleeds a sliver onto the pixel its neighbour also covers — visible on roughly every other clip as `start_tick * pixels_per_tick` beats against the pixel grid. Rounding the same edge expression on both clips makes touching clips share one exact boundary.
- **Clips are inset from their lane, top and bottom** (`CLIP_V_INSET` = half the seam width + `CLIP_SEAM_CLEARANCE` (1.25) = 2px at the 1.5pt seam — derived so retuning `ARRANGER_LANE_SEAM_W` carries the margin; via `clip_body_band` in `draw_arranger_view`): a clip body doesn't fill `lane_h` edge to edge — it sits as a card floating in the lane with the `grid_seam_color()` groove seams visible above and below it. `clip_body_band` returns the inset span **pixel-snapped** (`lane_h` = the viewport height over the track count rarely divides evenly, so an unrounded inset antialiases the top/bottom edges across different pixel rows lane to lane), so `draw_clip_body` gives clips in adjacent lanes exactly aligned top/bottom edges. Drawing-only: clip selection and the `clip_resize_band` edge-drag grab band stay lane-relative (the inset is small enough that the drawn header still sits well inside the band).
- **`draw_clip_body`**:
  - `BG_PANEL` base rectangle
  - Tint layer, a flat 16% of the clip's own track colour on every clip — **there is no per-clip "selected" look**. The model still tracks a lead clip (the clip under the cursor on the selected track: what `Shift+Tab` opens and `/` inserts into, see `020-views-and-state.md`), but it gets no visual and no UI event: a highlighted clip promises that Delete/Duplicate/Cut act on it, and here they never do — every destructive operation reads the marquee. Do not introduce a cursor-selected glow (tint bump or header accent). A clip that isn't inside an active marquee must look no different than with no selection at all. An Arranger time selection with a real tick width (`Display.gesture.time_selection: Option<TimeSelectionRect>`, `TimeSelectionRect::has_tick_range` — a zero-tick-width point-in-time track selection has no range to visualize) then paints one *additional* highlight on top: only the sub-rect overlapping `[rect.start, rect.end)` (`tick_overlap`, `rendering/mod.rs`) **and** whose track falls inside `rect.track_start..=rect.track_end` gets lifted to 32%, in a neutral `theme::fg_dim()` tone rather than the track colour, so a selection spanning several tracks reads as one unified rectangle rather than a patchwork of per-track tints. Nothing outside that sub-rect changes, on this clip or any other clip in the arranger. Don't also dim every other clip while a marquee is active: it reads as the whole arranger flashing gray on every drag. It is driven by what plain `⌘/Ctrl+C`/`X` would grab (the marquee rectangle) — the one and only selection signal a clip carries. Track lane stretches within the tick range that fall in a gap between clips also get the same flat 32%-equivalent `theme::fg_dim()` highlight at full row height, but **only on the marqueed tracks** (`draw_time_selection_gaps`/`gap_spans`, iterating `rect.track_start..=rect.track_end`), so the selection reads as extending straight through empty space rather than stopping at each clip's edge. See `020-views-and-state.md` § "Plain `⌘/Ctrl+C`... `⌘/Ctrl+X`".
  - `CLIP_HEADER_H`-px (20px) header strip at the top — the primary track identifier, and also the clip edge drag-resize grab band (see `020-views-and-state.md` § "Clip Edge Drag-Resize"): the strip is deliberately tall enough to grab without swallowing presses lower in the lane. Accent opacity is 45% normally, 20% muted — full strength would shout at this height, and since no clip is ever drawn "selected" (see the tint bullet above) nothing earns it. **Untouched by `time_selection`** — the strip is a track identifier and a grab band, never a selection signal.
  - The band is also the **move grab**: a press on it (off the edges) selects + marquees the clip, a hold-and-drag moves it — see `020-views-and-state.md` § "Clip Band Press & Move Drag". While that drag is live the clip keeps drawing at its real position, untouched, and `draw_arranger_view` draws it a second time as a **ghost** at the snapped drop position, last in the pass so it composites over whatever it hovers: `draw_clip_at` → `draw_clip_body` with `alpha = CLIP_GHOST_ALPHA` (0.45), which `gamma_multiply`s every fill (base, tint, header, thumbnails, divider) and skips the marquee highlight (a ghost is part of no selection). This is the one sanctioned use of alpha on a whole clip body — the point is precisely that the clips underneath show through — and doesn't loosen the "brightness, not alpha" rule for structure lines. `Grab`/`Grabbing` cursor icons are the only other affordance, mirroring the edge resize's icon-only approach.
  - 1px `BG`-coloured right-edge divider to mark clip boundaries without a heavy border frame
  - Selection is never a coloured outline or ring: the marquee highlight's *location* is the only selection signal a clip carries.

## Piano Roll (Clip View)

- **Uniform key geometry; row height shrinks only to fit the home range**: `src/view/display/rendering/piano_keys.rs` gives every MIDI note the same row height (`KEY_ROW_H` by default) regardless of pitch class — white and black keys are equal-size cells side by side (Ableton-style), not interlocking, differently sized shapes. Don't introduce per-pitch-class row heights ("realistic" narrower black keys): they fight readability (thin black-key rows/events) and make `PIANO_ROLL_SCALE` uneven across rows. Rows are flat at `KEY_ROW_H` whenever there's room; `piano_keys::fit_row_height` only shrinks them — uniformly, never below a 1px floor — when the clip's home note range doesn't fit `note_area_h` at that height (see the next bullet). The user's **octave-legend zoom drag** (next bullet) replaces the fit with its own row height. All 12 semitones per octave tile **contiguously with no gaps or overlap** at any row height (verified by `mod tests` in that file).
- **Octave numbering is Cubase-style**: MIDI note 0 = C-2, note 127 = G8 (`piano_keys::octave_of`/`pitch_class`). This is what makes the legend span exactly -2..8.
- **Vertical viewport: framed on open, then the user's** (the vertical twin of the clip view's home framing, § Panes): when a clip is opened (`frame_clip_home` → `latch_clip_home_notes`, on `ClipEntered` / `LeadClipChanged`), `piano_keys::home_note_range` pads its notes by half an octave (clamped to 0..127; C2..B5 for an empty clip) and saves the range as `RenderState::clip_home_notes`. `Display::note_area_geom` → pure `NoteAreaGeom::framed` derives everything from that saved range and the pane height — **never from the clip's current notes**, so no edit (insert, drag, transpose, quantize, delete, undo) moves the grid: rows are `fit_row_height` of the home range (flat `KEY_ROW_H` with room to spare, shrunk just enough to show the whole range otherwise), centred on the home range, and the rows visible around it fill the height. **Vertical scroll**: the wheel / two-finger Y delta over the clip pane (`TimelineScroll::delta_y` → `scroll_note_area_by` → `NoteAreaGeom::scrolled_centre_row`) sets `RenderState::clip_centre_row`, the view's centre in row units (`None` = centred on home), clamped so the view never scrolls past G8 at the top or note 0 at the bottom (`scroll_y_bounds`) — any pitch is reachable even when the rows were shrunk to fit. Row units, not pixels, so a pane-size change (dock ↔ maximize, window resize) refits the rows from the saved range and keeps the pitch at the centre. No follow: an Up/Down transpose can move notes out of view. **Octave-legend zoom drag** (Ableton / Bitwig): a press on the octave-legend column left of the keys (`Display::is_on_octave_legend` — not the keys themselves, whose clicks do nothing) starts `gesture.key_zoom_drag` (`KeyZoomDrag`: the content row under the press and an `AxisFilter`). Each motion is a step from the view as it is now: its `dx` scales the rows exponentially (`key_zoom_row_height`, rightward = taller, ×2 per `KEY_ZOOM_DOUBLING_PX`, held between the whole keyboard fitting and `MAX_ZOOM_ROW_H`), and the grabbed row moves its `dy` from where it sits (`NoteAreaGeom::anchored_centre_row`), so a vertical move scrolls. Stepping from the clamped view rather than from the press means a drag turning around at a zoom limit or a keyboard end acts at once — nothing to unwind. Once it actually zooms, the height is the user's own (`RenderState::clip_row_h`, used by `framed` in place of the fit): kept through pane-size changes (held to the zoom range, centre pitch kept), dropped with the home framing (clip open, capture re-frame, `reset_clip_zoom`). The pointer is `CursorIcon::ZoomIn` (the CSS `zoom-in` magnifying glass) on hover; **the drag hides and holds it** (Ableton / Bitwig): the icon is `CursorIcon::None` while the drag is held (not `ViewportCommand::CursorVisible(false)`, which egui-winit undoes whenever the icon changes), and `Display::sync_pointer_grab` sends `CursorGrab::Locked` on macOS (`Confined` on Windows/X11, which lack `Locked`) when the drag starts and `CursorGrab::None` on release, so the pointer reappears where it was pressed (with the magnifying glass back: no `MouseMoved` follows a release the pointer didn't move for, so `MouseReleased` re-derives every hover itself — `Display::refresh_hovers`, the same pass `MouseMoved` runs) — acting only on the edge (`GestureState::pointer_grabbed`). It runs on raw motion, not positions: `InputPoller` turns egui's `pointer.motion()` (winit device events, delivered while the button is held even outside the window) into `InputEvent::PointerMotion`, so the drag doesn't stop at the window or screen edge as absolute positions do. Each motion first goes through `AxisFilter` (`pointer_state.rs`), as in Ableton (Bitwig doesn't): from a smoothed recent speed per axis, the dominant axis always passes and the other only when it is more than half of it (a deliberate diagonal), so the sideways drift of a vertical scroll doesn't zoom and the vertical drift of a zoom doesn't scroll. With no history at the start, the first 6 points of motion are held back and judged as one, so a drag doesn't open with drift. The drag owns the pointer: while it is held `MouseMoved` does nothing at all — no cursor line, note hover or other gesture follows the pointer into the grid (the press clears the cursor line and note hover). View state, never undone, no Esc. Otherwise only three things set the vertical framing: opening a clip, a pane-size change, and a **capture insert that lands out of view** — `UiEvent::CaptureInserted` (sent by `handle_edit_result` after the take's `EventsUpdated`, from `EditResult::EventsModified::inserted_take` — on the commit and on every redo of it, never on undo) re-latches the home range only when any of the take's rows isn't wholly visible (`NoteAreaGeom::shows_rows`, `Display::reframe_after_capture`); a take already in view moves nothing. That is decided from what's on screen, never from a stored "has the user scrolled" flag. A note move drag past the note area's edge **auto-scrolls** (`Display::auto_scroll_note_area`, run each frame after input: a note move held with the pointer past the top/bottom edge scrolls at `edge_scroll_speed` — a crawl just past the edge, faster further out, capped — and re-extends the drag at the same pointer; the frame requests the next while it scrolls, and the view stays where the drag left it, Esc included). The **event marquee never auto-scrolls**, as in Ableton: the view sliding under a sweep is distracting while the joining notes audition (`020` § Event Marquee Selection), and it would select notes the user never saw — the marquee stops at the visible rows; scroll first (wheel), then sweep. `draw_clip_view` clips its note-event drawing to the note area as a backstop.
- **Two equal-width columns left of the note grid**: `Display::content_origin_x()` is view-state-aware — in the clip view it reserves `2 * PIANO_MARGIN_W` (legend column + piano-key column) instead of the Arranger's tiny track-label gutter. Every shared draw path that calls `content_origin_x()` (cursor, playhead, ruler) picks this up automatically — don't special-case them separately.
- **The left columns are one continuous panel, exactly like the arranger's track column**: `draw_note_lane_backgrounds` fills `[0, content_origin_x()]` from the top of the timeline strip (`track_area_top()`) down to `track_area_bottom()` with `theme::bg_panel().gamma_multiply(0.8)` — the exact track-column fill — *including the strip corner above the columns*, so the panel reads as one piece top to bottom. `draw_timeline` stops its `bg_timeline()` strip at `content_x` and this fill runs first, so the panel owns the corner (same handoff as the arranger). `draw_piano_keys`'s `grid_seam_color()` right edge at `content_origin_x()` closes it — the analogue of the track column's groove right edge. The octave-legend labels and the piano keys draw *on* this panel; `draw_octave_legends` fills no rect of its own. **One deliberate difference from the arranger: no `TRACK_COLUMN_GRID_GAP_X`-style canvas gap.** The arranger gaps the column off the first bar so clips don't touch it; here the piano keys *must* sit flush against the note grid so a note row lines up with its key.
- **Black and white keys are the same size, full column width**: `draw_piano_keys` draws every row as one `PIANO_MARGIN_W`-wide, `KEY_ROW_H`-tall filled rect, colored `theme::piano_key_black()` or `theme::piano_key_white()` — no separate narrower black-key pass, no overlap. Rows read as distinct purely from the color change at each boundary, *except* E/F and B/C, the two adjacent-white-key pairs with no black key between them — those get an explicit `hline` seam or they'd read as one tall key. Both are the `grid_seam_color()` groove tone, continuing the matching seam in the note grid unbroken across the column boundary; hierarchy is by width (**B/C** 2px, octave boundary; **E/F** 1px). Not `theme::separator()`, and never an alpha-dimmed separator — the mudded competing-tier anti-pattern under § Borders.
- **The piano roll's structural dividers are grooves, like the arranger's**: the piano-key column's right edge (keys → note grid) and the note grid ↔ velocity lane divider both draw in `grid_seam_color()` — the key-column right edge is the direct analogue of the arranger's track-column right edge (1px); the velocity divider is a lane boundary like the arranger's track-to-track seams (2px) and, since the velocity lane shares the note-grid background, it is the only thing separating the two. Not `theme::separator()`, which reads brighter and harsher than the recessed seams around it, worst on the darkest palettes.
- **Velocity lane — DAW-standard, part of the editing surface**: `draw_velocity_panel` draws only the 2px groove divider at its top, the per-`NoteOn` bars (the lead clip's track colour, `Display::lead_clip_color()`, or `accent()` when selected), and a right-aligned `fg_dim()` "VEL" label. Its **background** (`bg + 7`, the white-key lane tone) and the **vertical bar/beat/16th grid lines** running through it are painted upstream by `draw_note_lane_backgrounds` — the fill on the raw painter before `draw_timeline`, so the grid (which already extends to `track_area_bottom()`) composites down through the lane. No separate `bg_timeline()` fill and no horizontal guide lines — the shared surface + shared time grid is how Ableton / Logic / FL / Cubase all render it, and it ties the velocity lane to the notes above it. Drawn whenever the clip pane is.
- **Event bars nearly fill their row**: `draw_clip_view` computes each event's height as `row_h - 2 * Display::EVENT_V_PADDING` (floored at 1px), vertically centered in its row (`note_y_for(nn) + (row_h - h) * 0.5`) — derived from the actual `row_h` in `NoteAreaGeom`, not a fixed constant, so the small fixed padding shrinks along with the rows instead of being clamped away and the event filling the row edge-to-edge.
- **Notes outside the clip's window are shaded as not playing** (`220-capture-without-pending-view.md`): in `Clip`, the note grid outside the lead clip's window gets a `bg()` shade at `OUTSIDE_WINDOW_SHADE_ALPHA` (0.55), and a note whose onset is outside the window dims by the same `SILENT_NOTE_SCALE` as a muted note, in the piano roll and the velocity lane alike (`is_outside_window`, `rendering/clip_view.rs`).
- **Muted events dim, same intent as a muted clip**: `draw_clip_view` scales the note bar's fill by a flat `0.35` (`SILENT_NOTE_SCALE`) when `EventShape::is_muted()`, applied to both the unselected velocity tint and the selected `accent()` fill — mirroring the arranger's muted-clip `note_alpha` (0.65→0.25) rather than introducing a separate visual language for event-level mute. **Deliberately does not drop the selection accent on a muted-and-selected note**: the whole note body — not a separate border — *is* the selection indicator here, so letting mute take precedence reads as the note having been silently deselected. Dimming the accent instead of replacing it keeps both facts visible at once. Revisit only if event selection gets its own border-style indicator independent of fill color. `EventShape`/`EventMetadata` carry `is_muted`/`muted` end-to-end from `Event::is_muted()` (`metadata/clip_view.rs::ClipView::from_clip` → `rebuild_event_shapes`), so a full clip-view resend (any `EventsModified`, including `MuteSelectedEventsEdit`) refreshes it — there is no incremental per-event mute-shape update, unlike `update_clip_shape`'s targeted `set_muted` for clips.
- **Muted notes are excluded from the arranger clip thumbnail, not just dimmed**: `build_note_thumbnails`/`thumbnails_from_event_metadata` (`clip_metadata.rs`/`ui_events.rs`) filter out muted `NoteOn`s before handing spans to `note_thumbnails_from_spans` — the thumbnail shows what will actually sound, same principle as excluding a sibling split-half's events. The clip-level `note_alpha` dimming (muted *clip*) still applies on top, unrelated to this per-note filter.
- **No minimum clip width for thumbnails**: `draw_clip_body` draws the note thumbnails for any clip with a body, however narrow. Don't add a width gate: at 32 bars per viewport a one-beat clip is ~10-14px, and a gate makes one-beat pieces (from a marqueed-piece band drag or a carve) render note-less — it reads as the thumbnails "disappearing". `draw_note_thumbnails`' `draw_thumb` clamps each bar to the drawn rect with a 1px minimum, so narrow clips need no cut-off.
- **One constant scales the whole piano roll — when there's room**: `piano_keys::PIANO_ROLL_SCALE` multiplies the default `KEY_ROW_H` and `Display::EVENT_V_PADDING`, so bumping it makes keys and events uniformly taller/thicker together whenever the clip's home range fits at that height. Below that, `fit_row_height` overrides `KEY_ROW_H` to show the whole home range, so `PIANO_ROLL_SCALE` has no visible effect until the pane is tall enough again. Tests in `piano_keys.rs` take `row_h` as an explicit parameter (rather than reading a hardcoded `KEY_ROW_H`) and use relative tolerances, so they hold at any scale and at any shrunk-to-fit height.
- **`NOTE_AREA_TOP_GAP`**: a small breathing gap below the timeline so the piano roll doesn't start flush against it.
- **New theme colors**: `theme::piano_key_white()` / `theme::piano_key_black()`, one pair per palette in `THEMES` — keep both defined for any new preset.
- **Note-lane backgrounds mirror white/black keys**: `Display::draw_note_lane_backgrounds` (`clip_view.rs`) fills white-key rows with `theme::bg()` bumped a few RGB steps brighter (per the Grid Hierarchy brightness convention, not alpha); black-key rows are left at the base `bg()` already painted by the canvas clear, so they read a shade darker by contrast — mirrors how black keys look darker than white keys on the piano-key column. It is called from `mod.rs` **before** `draw_timeline`, not from inside `draw_clip_view`, specifically so the bar/beat/16th grid lines (drawn afterward) composite on top of the lane fill instead of being painted over by it — don't move this call after `draw_timeline` or fold it into `draw_clip_view`, that would hide the vertical grid lines inside the note area.
- **E/F gets a lane separator too, not just B/C, and both live in `draw_note_lane_backgrounds`**: C/B (octave boundary) and E/F are the only two adjacent-white-key pairs with no black key between them, so both need an explicit horizontal line in the note grid or the pair reads as one solid double-height lane. Both lines use `grid_seam_color()` (the shared groove tone, `theme::bg()` − 8 per channel, full alpha) — a shadow seam *darker than the background*, not a dimmed gray line (a translucent/dimmed `grid_major` reads as a competing grid tier no matter how far it is dimmed; darker-than-bg reads as a groove). Hierarchy is by width: B/C (octave boundary) 2px, E/F 1px. Both lines are drawn inside `draw_note_lane_backgrounds`, i.e. *before* `draw_timeline`'s vertical bar/beat/16th lines, specifically so those vertical lines composite on top at every intersection rather than the horizontal separators overlapping them — drawn from `draw_clip_view` (after `draw_timeline`) they visibly cross over the vertical grid lines; don't move them there.

## Borders & Separators

- Avoid full rectangular borders on clips. A single right-edge divider line is sufficient separation.
- If a border-like effect is needed, use `BG` or `BG_PANEL` coloured lines rather than grey or track-colour ones — they read as cuts rather than frames.
- Never draw structural panel frames (between grid/timeline/header/footer) with `.with_alpha()`/`gamma_multiply()` as they turn to invisible mud on IPS panels; use pure, solid colors — either `separator()` or the solid darker-than-canvas `grid_seam_color()` (which the header-bottom, timeline-strip and lane dividers share so they read as one recessed system — see the grooves bullet below). Both are full-alpha `from_rgb` values, so neither muds out.
- **Use explicit `painter.hline`/`vline`/`line_segment` for borders**: when a border-like effect is strictly necessary, draw the sides explicitly rather than relying on `painter.rect_stroke()` for thin/precise lines — stroke weight and inset can vary at sub-pixel positions depending on `StrokeKind`.

## Selection & Indicators

- **Selection indicators**: never use `ACCENT` (yellow) outlines on clips. Make the clip itself look more prominent instead (brighter fill, wider accent strip).
- **Track selection**: anchored to the far left edge of the screen as a solid 4px accent-colored block. Avoid floating horizontal or vertical border lines that span across the grid view. The row-scoped playback-position accent (see § Playhead) is a position indicator, not a border — normally confined to the selected track's own row, or to the marqueed track span during an active multi-track selection — it doesn't fall under the "avoid floating lines" guidance above, which is about lines spanning the *whole* grid regardless of selection.
- **Arranger lane backgrounds are drawn before `draw_timeline`, not inside `draw_arranger_view`**: `draw_arranger_backgrounds` (lane fills + gutter + per-track header chrome + groove seams) is called from `rendering/mod.rs` right before `draw_timeline`, in the `else` arm opposite clip view's `draw_note_lane_backgrounds`, and for the same reason — the lane fills are **opaque**, so the vertical bar lines have to composite on top of them or they vanish. `draw_arranger_view` keeps only the clip-shape loop and still runs after `draw_timeline` so clip bodies sit above the grid.
- **Arranger lane fill is one common shade for every unselected track** (`lane_grid_fill()` in `arranger.rs`, used for the track lanes and the performance lane) — `theme::bg()` nudged `saturating_add(5)` per channel, i.e. a small luminance bump above the canvas rather than an alpha tint, so it holds across every palette. No even/odd alternation (it reads as zebra banding and makes the bar lines look coarser where they cross the shade boundaries), and not a `bg_panel()` alpha tint (it barely clears the canvas and leaves the grooves flat). The selected track alone swaps to `accent.gamma_multiply(0.12)` plus its 4px left marker, which is distinction enough.
- **The arranger grid is one system of recessed grooves, not lines laid on top** — `grid_seam_color()` (`rendering/mod.rs`) is the shared tone: `theme::bg()` with `saturating_sub(8)` per channel at full alpha, darker than the lane fill. Used for the horizontal row seams — track-to-track + performance-lane + timeline-strip↔lanes, all the same **`ARRANGER_LANE_SEAM_W` = 1.5pt** at a pixel-snapped y (`seam_y` — lane edges sit at fractional y, and a thin line there anti-aliases into soft edges; an odd physical-pixel width is centred on a pixel centre, an even one on a pixel edge, so 1.5pt = 3px on Retina lands crisp) (`draw_arranger_backgrounds` / `draw_timeline`; the strip seam is the performance lane's top edge in the arranger, so it matches that row's bottom edge and every track's) — the in-lane vertical bar lines (1px, `draw_timeline`; the dimmed in-lane beat lines run alongside them, same as clip view), and the track-column right edge (1px vline, `draw_arranger_backgrounds`) — no `separator()` rule anywhere in the grid. The lane fill sits ~5 steps *above* the canvas and the seams ~8 *below*, so the grooves have real contrast to sit in. Strength carries most of the hierarchy — seams full, in-lane bar lines `ARRANGER_BAR_LINE_STRENGTH` (see § Grid Hierarchy) — with a little width on top (1.5pt seams vs 1px bars). Since the lane fills are uniform, these seams carry the track division, so they stay present — just quiet. The header-bottom edge (`draw_header`) and footer-top edge (`draw_status_bar`) use the same `grid_seam_color()` at 1px (they frame the header/footer panels, they're not row seams): a plain `separator()` line there reads noticeably brighter/harsher than everything else, worst on the darkest palettes. `separator()` is out of every grid, in both views (the clip view's octave / E/F seams and column-edge dividers are `grid_seam_color()` too); it survives only as the pan-bar centre tick and for modal panel outlines.

## Playhead

- Drawn exclusively in the overlay pass so it layers correctly.
- Visible only when the transport is actively running.
- Rendered strictly as a pure, solid 1-pixel line (e.g., blazing white) with NO translucent/alpha focus column beneath it, to prevent additive color distortion/flicker when crossing bright clips on IPS screens.
- **Playhead start-edge stabilization**: both panes read the transport playhead, which the transport repositions before it sets `running`, so they draw it as is — no cursor stand-in on the first running frame (with two cursors it would flash the wrong one). The clip pane's playhead is snapshotted once per frame (`sync_clip_frame`), so `running` is snapshotted with it, read first (`clip_frame_running`, `render_running`): reading `running` live later in the frame draws the stopped position for a frame whenever playback starts between the two reads.
- **Selected-track row accent** (`draw_selected_track_cursor`, `overlays.rs`): marks the **playback start position**, not the live moving playback position — it tracks `render_cursor_tick()`, the same committed-cursor tick the timeline's "play" triangle marks (`draw_time_selection`, `timeline.rs`), so it sits still during playback and only moves when the cursor itself does (arrow keys, paging, clicks). This is deliberately distinct from `draw_playhead` above, which follows the live, running position. Confined to the **selected track's own row** (`arranger_layout()` + `selected_track_idx`) — or, while an active marquee (`Display.gesture.time_selection`) spans more than one track, every row `track_start..=track_end` covers, so the accent visibly expands as the drag crosses track rows (see `020-views-and-state.md`'s Arranger Time Selection section) — rather than the whole grid, and coloured with `theme::fg_dim()` — a neutral tone rather than that track's colour, so the cursor reads as one unified marker regardless of which track(s) it spans. 2px wide (`SELECTED_TRACK_CURSOR_W`), bolder than the full-grid line's 1px since it only spans one row when there's no active marquee. Arranger-only (`!view_state().is_clip_view()`). While the clip pane has the keyboard it stays drawn — `Space` still plays from it — but in an **unfocused tone**, `fg_dim` blended 60% toward `bg` (`unfocused_tone`, `UNFOCUSED_CURSOR_BLEND`; brightness, not alpha), so it can't be mistaken for the clip pane's own cursor. Always drawn regardless of transport state, matching the timeline triangle it mirrors; drawn immediately after `draw_playhead` in the draw order so it composites on top.

## Timeline, Region & Time Selection

- **Timeline strip**: the ruler lives in a dedicated `TIMELINE_H`-tall strip (`BG_TIMELINE` background, separated from clip lanes by a `grid_seam_color()` groove line — see the grooves bullet under Theme & Contrast). In **both views** the strip fill starts at `content_x`, not the window edge — the corner to its left is part of the left-gutter panel (arranger track column / piano-roll legend + key columns), which is filled up from the strip top so the column reads as one panel top to bottom. The groove right edge continues up through the strip; the arranger additionally keeps its `TRACK_COLUMN_GRID_GAP_X` canvas gap there (the piano roll has none — see § Piano Roll). Tick marks hang **downward from the bottom edge** of the strip, graduated by height at a fixed colour (`grid_major()`, `bar_color` for the bar) — bar ticks span the full `REGION_BAND_H` (so the tick top meets the bar-number baseline, one graduation-and-label unit), sub-beat ticks `0.35`, thinned to `ruler_ticks` (see the ruler-ticks bullet under § Grid Hierarchy). Bar numbers sit in the upper portion of the strip. Grid lines extend only into the clip area below, never into the strip itself. Keep this separation; do not collapse the ruler back flush with the clips.
- **Region indicator** (`draw_region`): rendered entirely within the timeline strip as a shallow (`REGION_BAND_H` = 10px, a `pub(super)` const in `timeline.rs` shared with the bar-number baseline so the two can't drift into each other) translucent `theme::region()` band, flush down to the strip-bottom groove. **Drawn in the arranger only** — it early-returns for `Clip`, where the region just spans the clip under edit and the band would stretch the whole ruler saying nothing. Modal states layer over the arranger and keep it. Its only edges are a 1px vertical line at each region bound, at a single alpha (`0.6 * loop_dim`) — no top, bottom, or handle bars (the fill marks the span, the strip-bottom groove closes it underneath). Each vertical edge draws only where that bound is on-screen. Both bounds are mapped to screen-x through `region_bound_x` (`timeline.rs`) — the *same* `round(tick * ppt + content_x - scroll_x)` used by the ruler's bar ticks, the playhead and `tick_to_screen_x` — so a bound sitting on a bar lands exactly on that bar tick instead of ~1px beside it. The right edge must **not** be computed as `start_x + round(width)`: that splits the rounding and drifts a pixel off the bar tick on bars where both fractional parts sit near `.5`, doubling the tick bleeding through the translucent band into a blurred gutter. `loop_dim` (0.4 when looping is disabled) fades the whole thing. Keep it visually subordinate to clip bodies and avoid full-height filled rectangles, which compete with the clip header strips on track 0.
- **Strip band budget**: the `TIMELINE_H` strip (30px) is partitioned by vertical band, and new indicators must claim a free band rather than overlay an occupied one. Bottom `REGION_BAND_H` (10px) = region band (`draw_region`; occupied only in the arranger — in `Clip` the bar ticks still hang through it but nothing else claims it), middle = bar numbers (12px glyphs, baseline on the region band's top edge — same `REGION_BAND_H` const), top ~8px = the range markers (`draw_time_selection`). `TIMELINE_H` tracks `REGION_BAND_H` — grow the band, grow the strip by the same amount, or the numbers eat into the marker clearance. Marker geometry lives in local `const`s inside `draw_time_selection`. The **collapsed play triangle** is the exception to the band budget: it is *bottom-anchored* flush on the strip seam with `CURSOR_MARKER_H` == `REGION_BAND_H`, so its vertical edge spans exactly the bar tick's `(strip_bottom - REGION_BAND_H)..=strip_bottom` band and the two read at the same scale. It caps the top of the in-lane playhead line that descends from the same point, and rides over the region band / bar-number bands at the cursor `x` rather than claiming the top band.
- **Time-position markers**: `draw_time_selection` draws in the timeline strip only — nothing goes into the clip lanes. With no range selected, a single right-pointing `accent()` "play" triangle marks the cursor — its straight vertical edge sits on the cursor tick and it opens rightward, the direction playback runs. It's derived from `render_cursor_tick()` rather than stored so it follows the cursor however it moves. It's the same width as the range arrows (`CURSOR_MARKER_W` == `MARKER_W`); its height is `REGION_BAND_H` — the bar tick's height exactly — and unlike the range arrows it's bottom-anchored flush on the strip seam rather than sitting in the top marker band. Since the cursor is the playback start position, this collapsed marker is drawn in `Clip` too, not just the arranger. It's the marker that carries the *emphasis* — the in-lane cursor line (`draw_cursor_line`) stays a quiet dim tone and only marks the pointer, so the triangle is what reads as "playback is here". The arranger range (never present in the clip views — `time_selection` stays `None` there) is two `accent()` arrows pointing *inward* from its bounds, each with its flat vertical edge sitting exactly on its snapped boundary tick — no connecting rail between them (it reads as clutter growing/shrinking with the drag). `accent()` is correct here — the ban on `accent()` above is specifically about clip outlines, and `accent()` already carries "position in time" in the header readout. Arrow reach shrinks on narrow ranges so the two heads meet rather than cross, and markers outside the visible content span are skipped.

## Arranger Navigation (horizontal scroll & cursor follow)

- **`Display.render.arranger_scroll_x` is the arranger's only horizontal-offset state and `Display.render.arranger_px_per_beat` its only scale state; there is no vertical zoom in the arranger** (the clip view has its own `clip_scroll_x` / `clip_px_per_beat` — see Panes below). The arranger's `pixels_per_tick()` is `arranger_px_per_beat() / PPQN`, and every time-anchored x already routes through it.
- **Horizontal zoom** (`state/zoom.rs`; design history in `archive/190-arranger-zoom.md`): `arranger_px_per_beat` is `None` until the first arranger frame, when `sync_arranger_scroll` latches the default — `BARS_IN_VIEWPORT` (32) bars across `content_w()`. From then on it is a fixed pixels-per-beat: a window resize shows more or fewer bars instead of stretching them (every DAW does this). Zoom-in stops at `MAX_PX_PER_BEAT` (3840 — four pixels per tick, so `Z` fills the width with a one-beat selection on content widths up to ≈ 4200pt. Lower caps stop `Z` short on short selections on wide displays, so the margins grow as the selection shrinks. Not deeper because `scroll_x` is `f32`). Zoom-out stops at a **content-relative floor** (`min_arranger_px_per_beat`): the scale that fits `arranger_last_content_tick()` — the same end-of-song measure the scroll clamp uses — times `ARRANGER_ZOOM_OUT_HEADROOM` (1.25) across the width, never tighter than the default 32-bar view (so an empty project can still reach the default) and never below the hard `ARRANGER_MIN_PX_PER_BEAT` (2.0, ≈ 160 bars at 1300px). The floor only blocks zooming *out*: a scale already below it (clips deleted while zoomed out, window narrowed) holds until the next zoom-in rather than jumping. `zoom_arranger_by(factor, pointer_x)` keeps an anchor tick on its screen pixel via the pure `zoomed_scroll_x` — the pointer's tick for ⌘/Ctrl+wheel / pinch (`InputEvent::TimelineZoom`, from egui's `zoom_delta()`, which egui fills *instead of* `smooth_scroll_delta` for a ⌘/Ctrl-modified wheel, so a gesture never both scrolls and zooms), the cursor for `+`/`-`, the viewport centre when neither is on screen (`zoom_anchor_tick`) — then re-clamps `scroll_x` with the new scale (a zoom-out at bar 1 pins left and grows right). Like a scroll it **suspends cursor-follow**, or the next frame's paging would undo the framing. Zoom is view state: never persisted, kept across `ProjectLoaded` / `ClipExited` (which only reset `scroll_x`), guarded to `view_state() == Arranger` like `scroll_arranger_by`. The grid, labels and snap adapt to it — see § Grid Hierarchy.
- **Zoom to fit / step back (`Z` / `X`)**: `zoom_arranger_to_fit` frames the time selection when it spans real time and is otherwise a **no-op** (pure `zoom_to_fit_range`). There is no fallback (framing every clip with no selection reads as `Z` misfiring). There is no "selected clip" step either — the view doesn't hold one (`020`'s marquee-only model), and a clip band press already marquees exactly the clip, so band press + `Z` zooms to one clip. The scale is the pure `fit_px_per_beat` (the span fills the width less `ZOOM_FIT_MARGIN` — 4% of the *content width* — a side, so every selection length frames identically — a *time* margin would swing on screen, ~17% of the width around a 1-bar selection, <1% around 32 bars; clamped between the content-relative floor and the max), the scroll the pure `centred_scroll_x`, then clamped (a selection at bar 1 can't be centred, so it keeps its width but sits flush left) — all in the pure `fit_framing`. `Z` applies only the *hard* zoom limits, not the content-relative zoom-out floor (that floor stops `-`/wheel zooming out into nothing; applied to `Z` it would squeeze a long selection in a short project). The framing it replaces (`Framing`: scale + scroll) is pushed onto `RenderState::arranger_zoom_history` (`ZoomHistory`, a bounded stack of 16) unless nothing changes; `zoom_arranger_back` pops it and re-clamps the scroll. Only `Z` pushes, and **any manual zoom (`zoom_arranger_by`: `+`/`-`, wheel, pinch) clears the history** — `X` means "undo my last `Z`", and after a hand zoom there is none to undo. Otherwise `X` after a manual zoom-out pops a stale pre-`Z` framing and jumps *in*, with no way back to the zoomed-out view (nothing records a manual framing). Scrolling does not clear it. The history is also cleared on `ProjectLoaded` (the zoom itself is kept). Both suspend cursor-follow like every zoom.
- **Snap follows the grid**: `Display::cursor_grid_ticks()` in the arranger is `grid_tiers().snap_ticks`, the finest visible tier. Every gesture that snaps through it follows the zoom — click placement, hover line, marquee drag, clip edge resize, band move, `⇧←/→` marquee edge, `⌘/Ctrl+←/→` nudge — and so does plain `←/→`: `forward_input_event` resolves it to `InputEvent::MoveCursorByGrid { step_ticks: ±snap }` → `TransportCommand::MoveCursor`, which lands on the next multiple of the step when the cursor is off-grid. Because the snap always divides the bar and `grid_tiers` is monotonic, a tick snapped at one zoom is on-grid at every coarser zoom. The *model's* minimum clip length (`time::min_clip_length_ticks()`, a beat) is separate and does not follow the zoom — a clip edge dragged on a 16th snap still can't make a clip shorter than a beat.
- **Cursor-follow paging**: `sync_arranger_scroll` (`state/scroll.rs`) runs every frame and, via the pure `followed_scroll_x` (shared with the zoomed clip views), pages `scroll_x` in steps of **two structural grid units** (`2 × GridTiers::bar_ticks` — 2 bars at the default zoom, more zoomed out, so a page always lands on a visible bar line) until the transport cursor is back inside `[scroll_x, scroll_x + content_w]`. The cursor is never written during playback, so the view only follows cursor *edits* (arrows, clicks, region jumps) — the playhead itself can run off the right edge, by design (see the Playhead notes on why it isn't smoothed/followed).
- **Two-finger trackpad / wheel scroll**: `InputPoller::poll` reads `egui`'s per-frame `smooth_scroll_delta` (nothing consumes it — there is no `ScrollArea` anywhere) and emits `InputEvent::TimelineScroll { delta_x, delta_y, pointer_y }`. `Display::forward_input_event` resolves it view-locally through `scroll_timeline_by`, in the pane under the pointer: X → `scroll_arranger_by` → pure `scrolled_arranger_x` (in the clip view, `scroll_clip_by`) (`scroll_x -= delta_x`, so positive delta = content moves right = toward bar 1, already OS natural-scroll aware); Y scrolls the piano roll's pitch (`scroll_note_area_by`, see § Piano Roll) or the arranger's track lanes (`scroll_arranger_lanes_by`, below).
- **Lane height and vertical scroll**: `arranger_layout()` splits the lane viewport (below the performance lane, to the arranger's bottom) evenly between the tracks — the live count, `Display::track_count()` = the length of the `tracks` mirror, less the `+` row under them — but never below `ARRANGER_MIN_LANE_H` (72px: the 67px header stack with room around it; pure `arranger_lane_h`). Four tracks in a full-height arranger get tall lanes; once the lanes stop fitting they keep the minimum height and the lanes scroll vertically by `RenderState::arranger_scroll_y`, which `ArrangerLayout::tracks_top` already includes (so every lane y, drawn or hit-tested, follows it). The lanes and the `+` row always fill the viewport, so there's never empty space under them. What moves the scroll: the wheel / two-finger Y over the arranger (`scroll_arranger_lanes_by`); a track selection that lands out of view (`UiEvent::TrackSelected` → `reveal_selected_track`, pure `arranger_scroll_y_to_show` — just far enough to show the lane whole, nothing when it is already in view — for the last track, the lane *and* the `+` row under it, so adding tracks one after another from the row keeps the row under the pointer; skipped while the arranger is hidden); a `⇧↑`/`⇧↓` marquee extension, which reveals the track edge it moved (`reveal_track`); and a mouse marquee or clip band drag held past the lane viewport's top or bottom, which edge-scrolls the lanes toward the pointer and re-extends the drag at the edge lane (`auto_scroll_arranger_lanes`, `ArrangerLayout::edge_overshoot`, the piano roll's `edge_scroll_speed` curve) — so a drag across tracks follows into lanes scrolled out of view. `arranger_layout` re-clamps the scroll on every read (pure `arranger_max_scroll_y`, as far as the `+` row's bottom) and carries `viewport_h`, the clamped `scroll_y` and `max_scroll_y` for the scroll code; the wheel goes through `scrolled_offset`, the same clamp as the horizontal scroll, and closes an open output menu, so a window resize or a project with fewer tracks can't strand it. Everything drawn in the lanes — lane fills, seams, header controls, clips, ghosts, the marquee gaps, the selected-track cursor — is drawn through one painter clipped to the viewport (`ArrangerLayout::lanes_painter`), so a lane scrolled up passes under the performance lane and the timeline strip; `track_idx_at` is `None` there, and the header hit-tests (`track_header_at`) resolve the lane under the pointer through it before testing that one lane's controls, so a hidden lane's can't be clicked. The column panel and the grid lines run the viewport's full height, unscrolled.
- **The `+` row**: a slim row (`ADD_TRACK_ROW_H`, 22px) under the last lane, scrolling with the lanes, gone at `MAX_TRACKS` (`ArrangerLayout::add_row_h` = 0, pure `arranger_add_row_h`). A seam closes the last lane above it; a dim `+` sits centred in the header column, accent-washed and brightened under the pointer (pointing hand). A click on its header-column part (`Display::add_track_row_rect` / `add_track_row_at`, shared by drawing and the hit-test) sends `InputEvent::AddTrack { track_idx: Some(track_count) }` — a track at the end, as ⌘T adds one after the selected track (`020` § Tracks and Regions). The row's content side is plain canvas; a press there is the last lane's, as below the lanes always was.
- **A scroll or zoom gesture suspends follow** (`arranger_follow_suspended`) so the view holds wherever the user parked it, cursor off-screen or not. `sync_arranger_scroll` clears the flag the frame it sees `cursor_tick` change (re-latching follow and paging back), and on leaving the arranger. Both flag + `arranger_follow_last_cursor_tick` are also reset where `scroll_x` is hard-reset to 0 (`ClipExited`, `ProjectLoaded` in `state/ui_events.rs`).
- **Scroll clamp**: `scroll_x` is bounded to `0.0 ..= arranger_last_content_tick() * pixels_per_tick` — the view never scrolls before bar 1. Don't add a lead-in before bar 1: it lets every scroll and zoom park the view in an empty gutter; a bar-1 selection just sits flush left, at the same width. `arranger_last_content_tick()` is the max of the latest clip end, the cursor, the region end and the time selection's end (so a marquee dragged past the last clip can be framed centred) — so the last bar of real material can reach the left content edge (one empty viewport past the arrangement) and no further. The clamp is applied in the suspended branch too, so deleting clips / shrinking the region can't strand the view.
- **Each pane's scroll offset is only ever written by that pane's scroll code** (`arranger_scroll_x` / `clip_scroll_x`). `scroll_clip_to_start` / `sync_clip_scroll` write `clip_scroll_x` against a *clip-pane* `pixels_per_tick`; the arranger's scroll/zoom code writes `arranger_scroll_x`, and the dispatchers (`scroll_timeline_by`, `zoom_timeline_*`) and the per-frame syncs run each inside `in_pane` for its pane. `UiEvent::EventsUpdated` re-fits nothing: it fires on every note edit (and for arranger-side edits), so a re-fit there would throw a zoom away or jump a long clip to its start on each nudge.
- **Panes** (`view/display/pane.rs`; design history in `archive/210-docked-clip-panel.md`): the lane area (below the header, above the status bar) is split into pane rects by the **clip panel** (`RenderState::clip_panel`: `visible`, `size` `Maximized`/`Docked`). The app starts with it shown and docked (`ClipPanel::new`). Hidden: the arranger alone (`PaneLayout::ArrangerOnly`). Maximized: the clip view alone (`ClipOnly`). Docked: the arranger above, the clip view below it (`Docked`), taking `DOCKED_CLIP_FRACTION` (40%) of the lane area, with a `PANE_GAP_Y` gap. The coordinate helpers (`pixels_per_tick`, `content_origin_x`, `scroll_x`, `render_*_tick`, `grid_tiers`, `track_area_top`/`_bottom`) answer for the **active pane**: the one an `in_pane(pane, f)` scope set, else the focused one (`focused_pane`, from `ViewState`). `ui()` draws each visible pane through `draw_pane` inside `in_pane`, with a painter clipped to the pane's rect, so a pane's draw pass, hit-tests and snap all use that pane's geometry. Docked, `draw_pane_split` draws a `separator()` line in the gap and a 2px `accent()` edge (`FOCUS_EDGE_W`, 70%) along the top of the pane with the keyboard. While the **track headers** have the keyboard (`020` § Views, Track header focus) the same edge runs across the top of the header column only (`draw_arranger_backgrounds`), in every layout — docked it replaces the arranger pane's full-width edge, so the edge always shows what the keys act on. A docked clip pane with no clip under the cursor draws a quiet "No clip at the cursor" (`draw_empty_clip_pane`) instead of an empty piano roll. Pointer input goes to the pane under the pointer (`pane_at`); a drag stays with the pane it was pressed in (`GestureState::press_pane`); the cursor line is tagged with its pane (`GestureState::hover_cursor`) and drawn only there. Keys go to the focused pane.
- **Clip-view zoom** (`state/zoom.rs` / `state/scroll.rs`; design history in `archive/200-clip-view-zoom.md`, home rules from `220`): `RenderState::clip_px_per_beat` is `None` at **home** — the clip's *home framing* across `content_w()` (`clip_home_px_per_beat`). The home framing is `RenderState::clip_home_span`: the clip's whole reach (window, notes kept outside it, headroom bar) taken when the clip is opened (`frame_clip_home` on `ClipEntered` / `LeadClipChanged`) and held until another clip is opened, so edge edits never move the view: only the shading changes. `Some` once zoomed by `+`/`=`/`-` (around the cursor) or ⌘/Ctrl+wheel/pinch (around the pointer), through the same `zoom_anchor_tick` / `zoomed_scroll_x` as the arranger (`zoom_timeline_by` / `scroll_timeline_by` dispatch by view). The zoom-out floor is the home framing; a zoom that lands on or steps across the home scale returns to `None` (`zoomed_clip_state`, with a relative tolerance so `×1.25 ÷1.25` float drift lands home). The cap is the arranger's `MAX_PX_PER_BEAT`. **The app never zooms or scrolls the clip view on the user's behalf**: `sync_clip_scroll` only keeps it valid — back to `None` at the home scale, the same tick at the left edge when the scale changes without the user (a window resize at home, via `clip_last_ppt` — so every user-driven scale change (zoom, `Z`/`X`, `frame_clip_home`) must write scroll and scale together through `set_clip_scroll`, or the sync rescales the scroll a second time and the content drifts left on each zoom-in), and the scroll clamped to `clip_scroll_span` (the home framing and the current reach together, so an edit that shortens the reach can't shrink the range under the view). The edits that move event ticks — Enter's tempo fit (and its undo/redo) and `⌥=`/`⌥-` — are followed rather than ignored: `follow_clip_retime` (`UiEvent::ClipRetimed`, in `zoom.rs`) maps the home span and the `Z` history through the `EventSpaceRetime` (`t × scale + offset`) and re-applies the on-screen framing via `apply_clip_framing`, each through pure `retimed_framing` (scale ÷ `scale`, scroll + `offset` at the new scale), so the notes keep their pixels. No cursor-follow and no cap on the home framing. A wheel scroll pans within `clip_scroll_span`. **`Z` / `X`**: `zoom_clip_to_fit` frames the hull of the selected notes (read from `event_shapes`' selected flag — the view's mirror of `Clip::event_selection`), widened to at least one beat around its centre (pure `clip_zoom_to_fit_range`; a lone 1/32 would otherwise zoom to the cap), through the arranger's own fit maths with the home framing as the floor and the scroll clamped to `clip_scroll_span` (pure `clip_fit_framing`; the floor is capped at `MAX_PX_PER_BEAT`, since a one-beat clip on a very wide screen fits above it and an inverted clamp panics). No selection ⇒ no-op, like the arranger. The replaced framing (`Framing`, the home scale standing in for `None`) goes on `clip_zoom_history`, a second `ZoomHistory` popped by `zoom_clip_back`; any manual zoom and `reset_clip_zoom` clear it. `zoom_timeline_to_fit` / `zoom_timeline_back` dispatch the bare keys by view.
- **Overlays are gutter-clipped**: any timeline element whose tick has scrolled left of `content_origin_x()` (or right of `content_right_x()`) must not paint into the track-header / piano gutter. The full-height vertical lines — the cursor line(s) (`draw_cursor_line` via `draw_lane_vline`: `cursor_line_color()` / `CURSOR_LINE_W`, a dim `fg` tone at 0.75px — drawn only at the pointer, in the pane it is over, and only while the pointer is over its time area — `update_hover_cursor_tick` gates on `content_x_on_screen` too, so over the track headers, piano keys or right padding there is no line rather than one pinned at the clamped left edge; see `020`), playhead (accent, 1px) (`overlays.rs`) — skip entirely via `Display::content_x_on_screen(x)`. The cursor line runs 0.75px because egui centres and feathers a stroke, so a nominal 1px line on the darker lanes reads heavier than the same-width bar tick does on the calm timeline strip; 0.75 matches its visual weight at the junction. It stays this quiet because the timeline strip's own play triangle (`draw_time_selection`) carries the committed / playback position; the cursor line only ever marks the pointer. The region band (`draw_region`) clamps its span to the content area through the pure `region_band_span`, and its two vertical edge lines draw only when their own edge tick is on-screen. Solid clip bodies (`arranger.rs`) and the timeline grid / time-selection markers (`timeline.rs`) have their own edge guards.

## Header & Footer

- **Header Uniformity**: All views use the same header readout. It's a **centred group of chips** (`draw_header`), each a small `theme::fg_dim()` uppercase `LABEL` (13px) next to its value — `BPM` (`theme::fg()`), `POS` (`theme::accent()`, keeping the "accent = position in time" convention), then `DSP` when an audio device was found, each a borderless `theme::bg().gamma_multiply(0.40)` square-cornered chip. The group is centred on the header's mid-x and reflows from its own measured width, so **new readouts are pushed onto the `readouts` vec** (time signature, loop state, …) — conditionally where they only sometimes apply — and the row stays balanced automatically; don't hard-code chip x positions. The `DSP` chip shows the audio callback's **deadline utilisation** (see `000-architecture.md` § audio engine) as `average/peak`, the usual audio-meter pair: the average is the steady figure to read and to compare a change against, the decaying peak is what catches a single late block that is already audible. It is coloured `theme::fg()` normally and `theme::accent()` once the **peak** crosses `DSP_LOAD_WARN` (70%). An `OVR` chip sits beside it counting blocks that actually missed the deadline — audible glitches rather than near misses — in `theme::fg()` at `0` and `theme::accent()` above it. It is latched, not decayed: an overrun is one block out of ~187 a second and nobody is watching the meter at that instant, so a peak reading can never be relied on to catch one. An `XRUN` chip follows with the same rules, counting the *backend's* overload notifications (cpal `ErrorKind::Xrun`, i.e. CoreAudio's `kAudioDeviceProcessorOverload`) — the device's verdict on the whole IO cycle rather than this render's own timing; the pair is read together (`OVR` alone: absorbed by the safety offset, inaudible; `XRUN` alone: a glitch from outside the render — see `AudioLoad::xruns`). `Display::ui` clears both on the stopped→running edge, so they read "this take" — a count that only ever grows stops meaning anything by mid-session. **Show it at zero, don't hide it until it fires**: a diagnostic nobody has ever seen work is indistinguishable from a broken one. **Show both whenever the colour keys off one of them** — showing only the average while colouring on the peak reads as the chip changing colour at an arbitrary value rather than at its documented threshold. No contextual view labels (e.g. "[CLIP]") in the corner.
- **The BPM chip is a control** (`view/display/tempo_field.rs`), Ableton's tempo box: a vertical drag on it scrubs the tempo live — on raw pointer motion (`InputEvent::PointerMotion`) with the pointer held and hidden (`sync_pointer_grab`), as the octave-legend zoom drag does, so the window edge never stops it; up faster, a whole BPM per 3 px, a tenth with ⇧ (toggling ⇧ mid-drag re-anchors at the pointer, so the tempo doesn't jump), clamped 20–300 BPM (`time::TEMPO_BPM_MIN`/`_MAX`, tap tempo's range too; reaching an end re-anchors there, so turning round acts at once) — and a double-click opens an inline field over its value (the `BPM` label stays), the tempo in it selected. The field is the rename field's twin (`show_name_field`, `field_event`, first look at every event while open): `Enter` or a press off it commits, `Esc` cancels; the text goes through `time::parse_bpm_tenths` (one decimal, `,` works as the point, clamped, not-a-number keeps the tempo). Each typed value is one undo step and each drag one more, however many steps it sent (`SetTempoEdit`, merged by drag id — `050`); `Esc` mid-drag puts the tempo back and leaves no step. A drag back to its starting tenth sends the exact starting tempo, so it too leaves none. `draw_header` notes where the chip went each frame (`TempoChip::rects`, BPM is always the first chip) for the pointer and the field; the hover shows `ResizeVertical`. Every site that treats a drag as owning the pointer (the grab, the hidden icon, frozen hovers, the release refresh) asks `Display::pointer_held_drag`, shared with the octave-legend zoom drag.
- **The `?` chip** sits at the header's **right edge** (`help_chip_rect`, `HELP_CHIP_INSET` in from it), apart from the centred readout group — it is a control, not a readout, and must not shift the group's centring. A square `HEADER_CHIP_H` chip in the readouts' fill with a `?` in the value font, `fg_dim`, `accent` under the pointer (with the pointing hand); a press opens the help overlay (`010` § Help Overlay). It is the overlay's only discoverability aid: no launch hint in the footer (the footer rule below holds without exception).
- **UI Cards**: avoid drawing explicit box borders (`draw_line`) around header readouts (BPM/Position). Use a simple, borderless flat fill (e.g., `theme::bg().with_alpha(0.40)`) to natively group text data without wireframe clutter.
- **Footer band**: the `STATUS_H` band at the bottom (`draw_status_bar`) — panel fill, bottom inset, and `grid_seam_color()` top edge — holds one thing: the **passing message**, what an action just did or why it did nothing ("Exported song_T1_B1.mid", "Select a single clip to export"). `UiEvent::Status { message }` → `RenderState::status` (`StatusMessage`): left-aligned, `theme::FONT_SIZE_LABEL`, `theme::fg_dim()`, no chip; one at a time (a new one replaces it); held 3 s, then faded out over 0.5 s (`StatusMessage::opacity`). It costs one wake at the end of the hold and the fade's frames (`StatusMessage::next_repaint`), not a steady repaint for its whole life, and is dropped once gone. Use it for an action whose result isn't visible on screen (a file written, a refusal), never as a log. Per-view key-hint chips don't belong here: they clutter the layout and go unread — a message is feedback on a press, not keybinding tuition — and modals still must **never** render their own inline key-hint rows.

## Rendering Performance

- **Frame clear and pacing are handled by `eframe`/`egui`, not manually**: `egui::CentralPanel` with a `Frame::NONE.fill(theme::bg())` background handles the clear; eframe's default `glow_options.vsync = true` (left untouched in `native_options()`, `src/main.rs`) paces the render loop. Do not add manual `clear_background()`/`thread::sleep` frame-pacing calls.
- **Repaint requests are explicit while running**: `ctx.request_repaint_after(Duration::from_millis(33))` is called at the end of `Display::ui()` only while the transport is running, so the UI redraws at ~30 fps during playback without spinning the render loop when idle. Input events (keypad/mouse) trigger their own repaints via egui automatically.
- **Don't raise that to `request_repaint()` at the display refresh rate — it looks worse**: the UI samples `playback_tick`, which the transport thread advances on its own schedule, with no synchronisation between the two. At 33 ms the sampling error is small next to the ~12px the playhead travels per frame (120 bpm, 2-bar region) and goes unnoticed; at vsync rate the per-frame step shrinks to a few px, the same error becomes a visible fraction of it, and the playhead visibly vibrates. It doesn't measurably reduce the playhead smear either. Smoothing fast playhead motion properly would mean interpolating its position from a monotonic clock instead of sampling the atomic — a bigger change than the problem justifies.
- **The playhead reads as *behind* static grid lines while moving — this is motion blur, not z-order**: it is a 1px line and the only moving element, so the eye tracks it and each held frame smears across the distance travelled, dropping its apparent contrast below the perfectly sharp grey octave separators and grid lines it crosses. It looks exactly like a z-index bug; it is not. Confirmed by stopping the transport, where the same line reads as correctly on top. The layering and opacity of the playhead are already correct (see the Playhead section) — don't go chasing this in the draw order again.
- **Per-frame snapshots prevent mixed-state stutter/ghosting**: clip-pane rendering freezes frame-local values (`clip_frame_region_bounds`, `clip_frame_playback_tick`, `clip_frame_cursor_tick`, `clip_frame_scroll_x`) at frame start/sync so each draw pass uses coherent state. Use helper accessors (`render_scroll_x`, `render_cursor_tick`, `render_playback_tick`, `render_playhead_tick`, `region_bounds_for_render`) instead of ad-hoc atomics/fields in draw code.

## Arranger Track Header

- **The arranger's left column is a real track header**: `Display::TRACK_HEADER_W` (124px) is the sole width knob — every content x (cursor, playhead, ruler, region band, clip x) routes through `content_origin_x()`, so widening this constant moves everything correctly and nothing else needs touching (same principle as the Piano Roll's `2 * PIANO_MARGIN_W`). The 4px accent selection block still sits flush at the far left, inside the column. **The column fill is one continuous panel from the top of the timeline strip, through the reserved performance-lane row, down to the arranger's bottom** (`draw_arranger_backgrounds` fills from `performance_lane_top - TIMELINE_H`) — so the strip corner and the performance lane's gutter don't read as stray patches wedged between the ruler and the track column. `draw_timeline` confines the `bg_timeline` fill to `content_x`+ so this panel owns the corner; the groove right-edge line and the `TRACK_COLUMN_GRID_GAP_X` canvas gap run its full height. The performance-lane and per-track gutter overlays are drawn on top and land at their usual brightness. **`TRACK_COLUMN_GRID_GAP_X` (8px) carves a margin out of the right edge of that reservation**: the column fill, its right-edge groove line (`grid_seam_color()`, not `separator()`) and the header controls (`track_header_rects`) all stop `TRACK_COLUMN_GRID_GAP_X` short of `content_origin_x()`, leaving a strip of bare canvas between the column and the first bar so the grid isn't flush against it. `content_origin_x()` is unchanged by the gap, so nothing in the grid moves — it only trims the column. **`TRACK_HEADER_INNER_PAD_X` (12px) then insets the controls equally on both sides** (`track_header_rects` applies it to `left` and, mirrored, to `right`) so the S/M row and the volume/pan bars sit centred in the column instead of running flush to its groove edge; `TRACK_HEADER_W` is sized to keep the bars a comfortable width with both sides padded. Volume fills left→right to `mix::fader_pos_from_db(db)`; pan fills from the centre outward (left or right). The pan bar always shows a 1px `theme::separator()` centre tick. Readout is right-aligned `FontId::proportional(11.0)` `theme::fg()` — right-aligned specifically so no `ctx.fonts()` text measurement is needed and `draw_arranger_view`'s signature stays unchanged. Volume shows `-6.0` / `-inf` (at `mix::MIN_DB`); pan shows `C` / `12L` / `50R` from `(pan * 50.0).round()`.
- **The fader taper lives in `core::audio::mix`** (`db_from_fader_pos` / `fader_pos_from_db`, piecewise-linear through DAW-conventional breakpoints, unity at 0.78 of the travel), shared by the drawn fill fraction *and* the drag mapping so the bar tracks the pointer 1:1. `MIN_DB` = −60 (true mute), `MAX_DB` = +6. Pan is an equal-**balance** law, not equal-power: centre passes both channels at unity (a CLAP instrument is already stereo), hard-one-side mutes the other.
- **Animated meters are explicitly out of scope** — these bars show the *set* value only, never signal level.
- **Mute/solo are not undoable and solo is not persisted** — see `020-views-and-state.md` § Track Header Mute / Solo Buttons and `060-persistence.md`.

## Layout Sizing

The app is a resizable desktop window (`native_options()` sets a `2560×1440` default `inner_size`, no fullscreen/platform lock). Layout constants (`HEADER_H`, `STATUS_H`, `TIMELINE_H`, `M_SCALE`, etc.) are tuned for that desktop scale, not an embedded panel. Avoid introducing platform-specific `#[cfg(target_os)]` toggles for UI sizing — dimensions should stay uniform across macOS/Linux/Windows.
