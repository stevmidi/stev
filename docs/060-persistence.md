# Project Persistence

- **Persistence lives in `src/core/project/` via DTOs**: `dto.rs` holds the serializable structures and their `Sequencer` mapping, `storage.rs` the `.stev` filesystem CRUD (and where a clip export lands, and reading a `.mid` for import), `smf.rs` the `.mid` reader and writer; where things live on disk is `src/core/paths.rs`. Save/load should serialize explicit project data structures, not runtime structs or UI state directly.
- **DTO field names are the on-disk JSON keys — renaming one is a format change**: nothing in `dto.rs` uses `#[serde(rename)]`, so the Rust identifier is written verbatim into every `.stev`. Fields without `#[serde(default)]` (`ClipData.start_tick`, `EventData.tick`, `tick`/`length`/`midi_message`, `tempo_us`, the region bounds) are **required**, so a renamed field makes every existing project fail to load with a missing-field error — not silent corruption, but the file won't open. To rename one, either migrate the files on disk in the same change or keep the old key with `#[serde(rename = "old_name")]`. `ClipData.start_tick` / `EventData.tick` were renamed from `start_ticks` / `ticks` on 2026-09-05 and the user's projects migrated with them; `clip_and_event_json_keys_are_the_on_disk_format` in `dto.rs` guards the current keys. Adding an *optional* field is safe by contrast — that is what every `#[serde(default)]` below is doing.
- **`.stev` files are arrangement snapshots, not full runtime snapshots**: persist tempo, global region, clips, clip-local regions, mute state, swing_pct, and events, but do not treat cursor position, selections, capture buffers, pending clip state, or modal view state as persisted project data unless the format is explicitly extended.
- **The arranger performance lane is never persisted, by design**: it's live-input-only (see `110-performance-lane.md`) — arm state and the currently-held trigger have no representation in `ProjectData` at all, not even a transient one that resets on load.
- **Load/new-project flows must rebuild from a clean sequencer state**: stop transport first, reset sequencer state via `new_project`, rebuild clips from saved data, emit fresh `ProjectLoaded` metadata for the UI, return to `ViewState::Arranger`, and re-establish a valid default track selection.
- **Empty projects use default tempo**: `new_project()` and undoable clip removals that leave the project with zero clips reset tempo to `TEMPO_US_DEFAULT`. Undoing that last-clip removal restores the previous tempo with the clip.
- **Persisted identity is structural, not stable**: clips and events are recreated on load, so runtime UUIDs change. Persist data fields, not runtime IDs.
- **The track count is the length of `ProjectData.tracks`**: no separate field. `apply_to_sequencer` calls `Sequencer::set_track_count(tracks.len())` right after `new_project()` — clamped to `1..=MAX_TRACKS` (16), appending empty MIDI-Out tracks (track *n* on channel *n*) or dropping tracks off the end — so a project keeps the count it was saved with (projects from before the track count became variable load with their 8). A new project (`ProjectData::default()`) has `DEFAULT_TRACK_COUNT` (4). A file with more than 16 loads the first 16 and `load_project_workflow` says so in the footer (`UiEvent::Status`); one with none gets one track. Guarded by `a_loaded_project_keeps_its_own_track_count` / `a_loaded_track_count_is_clamped_to_one_through_max` (`dto.rs`). Engine slots (`Track::slot`, `050` § Track add / remove) are **not** persisted: `new_project()` puts every track back in slot = position, so a load starts with slots matching positions however tracks were added and removed before; the per-track mix values in `TrackData` are read and written by position (`Sequencer::track_volume_db(track_idx)` etc. translate).
- **A track's colour is persisted**: `TrackData.color: Option<usize>` is the track's colour slot (`Track::color_slot`, an index into the theme's 16 track colours), so a track keeps its colour across a save and reload however tracks were added and removed before — unlike the engine slot, which a load resets. `#[serde(default)]`: a project saved before the field existed loads with `None`, which `apply_to_sequencer` maps to the track's position, so it looks as it did when colour was by position. `new_project()` puts every colour back to its position too. Guarded by `track_colours_survive_a_save_and_load` / `a_track_saved_without_a_colour_takes_its_positions` (`dto.rs`).
- **A track's name is persisted**: `TrackData.name: Option<String>` is `Track::name` — `#[serde(default, skip_serializing_if = "Option::is_none")]`, so an unnamed track writes no field and a project saved before names existed loads with every track unnamed (showing its number). `apply_to_sequencer` passes a loaded name through `track_name_from_input`, the rename's own rules, so a hand-edited blank or over-long name loads as it would have been typed; `new_project()` unnames every track. Guarded by `track_names_survive_a_save_and_load` / `an_unnamed_track_saves_no_name_and_a_blank_one_loads_unnamed` (`dto.rs`).
- **Track output is persisted and restored**: `TrackData.output` (`TrackOutputData`, a tagged enum) round-trips per-track routing — a MIDI channel, or `Instrument { bundle_path, plugin_id, display_name, state }` for the macOS plugin host (see `130-plugin-host.md`). All `Instrument` fields are `#[serde(default)]` (and `state` is `skip_serializing_if` empty) so phase-3 tag-only and phase-4 stateless projects still load. `ProjectData::from_sequencer` writes it; `apply_to_sequencer` maps it back via `Track::set_output` (an empty `bundle_path` → `MidiOut { 0 }`). A project opened from disk with plugins is first **staged**: read and kept in the `"sequencer"` thread (a `StagedProject`) while the view loads its plugins (`UiEvent::StageProject`), the open project left as it is, then applied when the view says they are in (`InputEvent::ApplyStagedProject`); its `UiEvent::ProjectLoaded` names the plugin tracks and `Display::sync_instruments_to_tracks` swaps the loaded plugins in (hidden) — see `130` § Project persistence. `state` is the plugin's CLAP `state` blob (active preset), base64 in the `.stev`: `Display::capture_instrument_states` refreshes it from each live editor on ⌘S (via `InputEvent::CaptureTrackInstrumentState` → `SequencerCommand::SetTrackInstrumentState`, queued ahead of the save on the same channel) and `engine::load` re-applies it before activation on load. Caveats: a project whose plugin is not installed, or loaded where the plugin host did not initialize / off macOS, leaves that track silent; a preset changed after the last ⌘S is not persisted on quit, and on its own it is no unsaved change (§ Unsaved changes leaves plugin state out); a corrupt state blob is ignored (plugin loads at its default).
- **The time signature is a one-entry list**: `ProjectData.meter` is a `Vec<MeterData { bar_index, numerator, denominator }>` (zero-based bar), `#[serde(default = "default_meter_list")]` → `[4/4 at bar 0]`, so a project saved before time signatures loads as 4/4. It is a list so meter changes along the timeline could come later without a format change, but `from_sequencer` always writes exactly one entry at bar 0 and `apply_to_sequencer` reads only the first (`meter_from_list`): an empty list, or a first entry `Meter::new` rejects (numerator outside 1–16, denominator not 4 or 8), loads as 4/4 rather than failing. The source of truth is `SharedAtomics.meter` (`Meter::to_bits`), read and written through `Sequencer::meter` / `set_meter`; `new_project` resets it to 4/4. A Stev that predates the field ignores it and plays the project in 4/4. Guarded by `a_meter_survives_a_save_and_load`, `a_project_without_a_meter_loads_as_four_four` and `a_meter_list_reads_its_first_supported_entry_or_four_four` (`dto.rs`). See `archive/270-time-signature.md`.
- **Per-track volume and pan are persisted**: `TrackData.volume_db` (dB, `0.0` = unity) and `TrackData.pan` (`-1.0`..=`1.0`, `0.0` = centre), both plain `#[serde(default)]` — `0.0` *is* the neutral value, so a project saved before these fields existed loads at unity/centre with no custom default fn (unlike `swing_pct`). The source of truth is `SharedAtomics.track_mix` (`TrackMixAtomics`, `f32` bit patterns), not a `Track` field: `from_sequencer` reads `sequencer.track_volume_db(i)` / `track_pan(i)`, `apply_to_sequencer` writes them via `sequencer.set_track_volume` / `set_track_pan` (which clamp), and `new_project` → `reset_track_mix()` clears them. `ProjectData::default()` must also set both to `0.0` on every per-track entry or `⌘N` won't reset them (`default_project_data_resets_every_track_mix_to_neutral` guards this). Not undoable — a continuous mixer parameter, like region length (`050-undo-redo.md`). Only instrument (CLAP) tracks show the header bars; the values are stored for every track regardless. See `030-ui-design.md` § Arranger Track Header and `130-plugin-host.md`.
- **Per-track mute is persisted; solo is not**: `TrackData.muted` is a plain `#[serde(default)]` `bool` — `false` (audible) *is* the neutral value, so a project saved before the field existed loads unmuted, no custom default fn. Same source-of-truth story as volume/pan: `SharedAtomics.track_mix.mute` (`[AtomicBool; MAX_TRACKS]`), `from_sequencer` reads `sequencer.track_muted(i)`, `apply_to_sequencer` writes `sequencer.set_track_muted(i, …)` alongside the volume/pan writes, `ProjectData::default()` sets `muted: false` per track (guarded by `default_project_data_resets_every_track_mix_to_neutral`), and `new_project` → `reset_track_mix()` clears mute *and* solo. **Solo has no `TrackData` field** — it is transient monitoring state, so it is never written and `apply_to_sequencer`'s leading `sequencer.new_project()` already clears any leftover solo from the previous session on load. Not undoable — a mixer-surface control, like volume/pan (`050-undo-redo.md`). Note `ClipData.muted` is a separate, unrelated field (per-clip mute), and `EventData.muted` (per-*event* mute, `#[serde(default)]` so older projects load unmuted) is a third, likewise unrelated field — see `050-undo-redo.md`'s `MuteSelectedEventsEdit` note.
  `apply_to_sequencer`'s per-track loop only runs over `self.tracks`, so `⌘N`'s reset depends on `ProjectData::default()` supplying one `MidiOut { channel: i }` entry per track (`DEFAULT_TRACK_COUNT`, four, matching `Sequencer::new`'s own defaults) rather than an empty `Vec` — `new_project()` itself only clears clips, it never touches `Track.output`. Without that explicit per-track default, a track routed to a CLAP instrument in the previous project would survive `⌘N` unchanged (regression fixed 2026-09-01; see `default_project_data_resets_every_track_to_midi_out` in `dto.rs`'s tests).
- **On-disk layout (`src/core/paths.rs`)**: the library `~/Documents/Stev/` (`library_dir()`) holds only user content, in root folders — today `Projects/` (`project_dir()`) and `Exports/` (`exports_dir()`, the audio export's; made by the first export); forks add siblings (`Samples/`, …), which is why projects don't sit directly in the library. App settings (`settings.json`) live in the platform config dir (`config_dir()`: `~/Library/Application Support/stev/`, `~/.config/stev/`, `%APPDATA%\stev\`), the VST3 catalog cache in the platform cache dir (`cache_dir()`: `~/Library/Caches/stev/`; macOS-only like the plugin host, so `cache_dir` and `VST3_CACHE_FILE_NAME` are `cfg`-gated to it); either falls back to the library on a platform without one.
- **No layout migration.** The startup migration from the pre-2026-10-03 flat layout was deleted with the rename to Stev (2026-10-08), after it had run on the only install. The rename's folder moves were done by hand (`archive/240-release-plan.md` § C). A layout change after publication needs a migration of its own again.
- **Projects live in per-project folders, made in the browser or in Finder**: each subfolder of `paths::project_dir()` (`~/Documents/Stev/Projects/`) is one project; `.stev` files inside it are that project's saves. `list_project_folders()` lists them (dot folders and the `Clips` folder hidden, the latter in any case); `list_projects(folder)` gives one folder's `.stev` projects newest first, dotfiles hidden, for the browser panel (`020`). The browser makes, renames and deletes folders (`create_project_folder`, `rename_project_folder`, `delete_project_folder` — the last to the Trash on macOS; `020` § Views), one level deep; neither may take the `Clips` folder's name. A renamed current folder updates `last_project_folder` (§ active project folder), and so does a deleted one with no saved project open from it; with one open, it stays current, and ⌘S makes it again. `list_projects`/`save_project`/`load_project`/`delete_project`/`rename_project`/`next_project_name` take `folder: Option<&str>`, `None` being the projects root: the bootstrapping fallback where a project is saved before any folder has been chosen, whose loose projects the browser lists after the folders.
- **MIDI clips live in one `Clips` folder** (`project_dir()/Clips`, `storage::CLIPS_FOLDER`, 2026-10-11): every clip export lands there, whichever project it came from, and the browser's Clips category lists it (`list_clips`, `.mid` stems alphabetical; `clip_path`, `rename_clip`). It is made by the first export. `.mid` files elsewhere — in project folders, from before the folder existed — are no longer listed; move them into `Clips` to see them.
- **Audio exports live in one `Exports` folder in the library** (`~/Documents/Stev/Exports/`, `paths::exports_dir()`, beside `Projects/` — moved out of the projects root 2026-10-18): every audio export gets its own folder inside it (`create_audio_export_dir`, named `<project> <tempo>bpm <n>-<d> bar <bar>`, never reused: ` 2`, ` 3`, …), whichever project it came from. Nothing in the browser lists it. An export's folder holds `NN Name.wav` per stem (`stem_file_name`: the 1-based track number, the track's name or else its plugin's) and `Mix.wav` (`MIX_FILE_NAME`), 32-bit float stereo at the device rate (`core/audio/wav.rs`). The handler makes the folder before the run plays; if the plugin host is missing it removes it again, still empty. See `130-plugin-host.md` § Audio export.
- **A project is named by the user, the first time it is saved** (2026-10-05): ⌘/Ctrl+S on a project that has never been saved opens Save As, as in every DAW; on a named one it overwrites that file in place at once. There is no generated name — the `<folder>_ddmmyy_NN` names (`next_project_name`, removed 2026-10-05) were a stand-in for a name field, and projects saved under them keep them.
- **Save As saves under a typed name** — ⌘/Ctrl+⇧+S always, ⌘/Ctrl+S on a project never saved: it opens a name field (`view/display/project_dialog.rs`, drawn by `rendering/modals/project_dialog.rs`) holding the open project's name — or `Untitled` for one never saved — selected whole. a **"Save in" dropdown** under the field chooses the destination folder (the projects root, then each project folder, read from disk when the dialog opens; a click on its box, or ↑/↓ or Space while the dropdown has the keyboard (never from the name field), opens the list, a click or Enter picks a row, Esc closes the list before it cancels the dialog; a click on the box or a row gives the dropdown the keyboard; at most 8 rows show, the window following ↑/↓; `SaveAs::list`, `list_window`; the note line under it stays empty unless the name is refused or replaces a project), with a **`+` beside it** (`SaveAsHit::NewFolder`; or the new-folder chord, ⌘/Ctrl+⇧+N, resolved through the keymap so a rebinding follows) that turns the box into a field for a new folder's name (`SaveAs::folder_field`), which opens with the keyboard. **Tab** moves the keyboard to the next stop and ⇧Tab to the previous, round from the last to the first (`SaveAsFocus`, `focus_stops`): the name field, the dropdown and the `+` — whichever has the keyboard wearing the text fields' focus edge and the others the dropdown's plain outline (`control_edge`; a text field without it gets `has_keyboard: false` from `TextField::show`), Space opening the dropdown's list or pressing the `+`, Enter pressing the `+` too (on the dropdown with its list closed, Enter saves, as from the name) — or, while the new folder's field is open, the name field and that field; Tab closes an open list; a press on either field gives it the keyboard too (the two hold the egui focus by turns, neither while the `+` has it). Closing the field gives the name the keyboard back. Enter in it, or a press off both fields, chooses the folder — one already listed under that name in any case, else a new entry at the end of the list — Esc goes back to the folder chosen before, a blank name chooses nothing, and a name `project_folder_name_from_input` refuses (the project-name rule, and not `Clips`) keeps it open with "Not a valid folder name" under it; the arrows do nothing while it is open. Enter in the name field while it is open takes the folder and saves into it in one go — or, with the folder name refused, saves nothing and hands the folder's field the keyboard. Esc closes it from either field. **The folder is made by the save** (`save_project`'s `create_dir_all`), never before, so a cancelled Save As leaves nothing on disk; the box showing the folder is all that says so. The dropdown starts at the browser's selected folder — the folder itself, or the one holding the selected project — while the browser is shown (`save_folder_default`, unit-tested), else the current folder. Enter saves under the typed name in that folder; once the file is written, the sequencer's `UiEvent::ProjectSaved` makes that folder `project_current_folder` and the name `project_current_name` (never before: a save that failed or was refused leaves a project never saved unnamed, so ⌘/Ctrl+S opens Save As again rather than silently saving where the failed one meant to — 2026-10-27), so the original file is untouched and later ⌘/Ctrl+S presses save into the copy; Esc cancels. The name goes through `project_name_from_input` (`storage.rs`, unit-tested: trimmed; refused when blank, starting with `.` — hidden, the browser would never list it — longer than `PROJECT_NAME_MAX_CHARS` (64), or holding a control character, `/`, `\` or another character Windows refuses in a file name), and Enter does nothing while it is refused. The note under the field says why, or warns `Replaces the existing <name>` when another project in the folder has that name (`project_exists`) — Enter then overwrites it, or where the project will go. There is no separate rename: Save As under the new name and delete the old file in the browser. ⌘/Ctrl+S, Save As and the prompt's Save all end in `Display::save_project_as` → `InputEvent::ConfirmFilename` → `SequencerCommand::SaveProject` → `EventHandlers::save_project_workflow`, which says `Saved <name>` in the footer (and sends `UiEvent::ProjectSaved`, then `UiEvent::ProjectFilesChanged`, so a shown browser re-reads the tree), or `Could not save <name>: <error>` — never silent.
- **Rebound keyboard shortcuts** are `SettingsData::keymap` (`#[serde(default)]`, a `BTreeMap` of action id → `Vec<ChordDto>`): only the actions whose chords differ from their defaults, an empty list meaning unbound, so a new default in a later version reaches every action the user never touched. A `ChordDto` is the key by egui's name (`Key::name` / `Key::from_name`) and the `command`/`alt`/`shift`/`ctrl` flags (`command` is ⌘ on macOS and Ctrl elsewhere, so a file is portable). Load skips unknown ids, unknown key names and refused chords (an action whose stored chords are all skipped keeps its defaults; a list stored empty stays unbound), and a conflict left in an edited file costs the later action in `ACTIONS` order its chord (`Keymap::from_overrides`). Written by the Keyboard tab on every change (`320`).
- **The active project folder is ambient session state, persisted across restarts**: `Display.project.project_current_folder` (initialized from `SettingsData.last_project_folder`) is where ⌘/Ctrl+S saves a named project and Save As's fallback. It's set (and written to `settings.json`, `Display::set_current_project_folder`) by opening a project, once it has loaded (`UiEvent::ProjectLoaded`'s `folder` — not before, so the unsaved-changes prompt's Save still saves where the open project lives), and by every save that succeeds (the folder Save As chose; `UiEvent::ProjectSaved`). The browser's selection and Enter never change it (2026-10-26: Enter on a folder used to, invisibly, and a new project then saved into the previous folder); a selected folder only pre-fills Save As.

## Unsaved changes

- **Three things replace or end the open project, and each is checked first** (2026-10-05): ⌘/Ctrl+N, opening a project (from the browser, or from Finder on macOS), quitting — `ProjectAction::{New, Open, OpenFile, Quit}` (`core/project/action.rs`). The view never runs one itself: `Display::request_project_action` sends `InputEvent::ProjectAction { action, discard_changes: false }` → `SequencerCommand::ProjectAction` → `EventHandlers::project_action_workflow`. Nothing unsaved: the action runs there and then (a quit answers `UiEvent::QuitApproved`). Unsaved: it sends `UiEvent::UnsavedChanges { action }` instead and nothing else happens. Autosave was rejected — it would clobber throwaway sessions; the prompt is app-wide, not plugin-specific.
- **"Unsaved" means "would save differently" — plugin presets aside**: the `"sequencer"` thread keeps a `SavedProject` beside the undo record — the `ProjectData::fingerprint` (a hash of the `.stev` JSON) of the project as last saved or loaded, taken at startup, on every successful save, and after a new project or a load. The check rebuilds the live project's `ProjectData` and compares fingerprints. So every persisted change counts, undoable or not — volume, pan, mute, the loop region, tempo, a track's output, which plugin a track holds — undoing back to the saved state counts as no change, and transient state (cursor, selection, solo, zoom) never does. **Plugin state blobs are left out of the fingerprint, and not captured before the check**: plenty of plugins write a different blob for the same preset on every save (seen 2026-10-05: Nexus encrypts it afresh, DUNE 3 recompresses it), so comparing them made a freshly opened, untouched project prompt on quit. A preset changed in an editor since the last save therefore doesn't prompt on its own. Telling a real preset change apart would take the plugin's own change notifications (VST3 `IComponentHandler::performEdit` / `restartComponent`, CLAP `mark_dirty`) — not built. Guarded by `an_untouched_project_quits_without_a_prompt`, `a_changed_project_prompts_and_dont_save_goes_on`, `opening_from_finder_is_checked_first`, `unsaved_means_it_would_save_differently` (`sequencer_handler.rs`) and `a_fingerprint_ignores_plugin_state_but_not_the_plugin` (`dto.rs`).
- **The prompt** (`ProjectDialog::Unsaved`, `view/display/project_dialog.rs`): `Save the changes to <name> before <starting a new project / opening <file> / quitting>?` with Cancel, Don't Save and Save buttons; `←`/`→` move the selection between them (Save to start with, accent-coloured, stopping at either end) and `Enter` presses the selected one, `D` (or ⌘/Ctrl+D, the macOS sheet's chord) doesn't save and `Esc` cancels whatever is selected (`unsaved_key`, unit-tested). Like the rename field it takes every key and press while open, ahead of everything else. While either project dialog is open, plugin editors stop floating and the main window comes to the front, so ⌘Q pressed in an editor doesn't leave the prompt hidden behind it (`130`, `EditorLevel::Behind`). **Save** saves under the project's name, then asks for the action again — `ConfirmFilename` and the action queue in order on the same channel, so the sequencer runs it now that nothing is unsaved, or prompts again if the save failed. For a project never saved it opens Save As instead, the action waiting on it (`SaveAs::then`): Enter there saves and asks for the action, Esc drops both. **Don't Save** sends the action with `discard_changes: true`.
- **Quitting**: the window's close request is held (`ViewportCommand::CancelClose`, `Display::sync_window_close`, once a frame after the sequencer's replies) and turned into `ProjectAction::Quit`; `QuitApproved` sets `Display.quit_approved`, which closes the window for real. On macOS winit's app menu wires ⌘Q to `-[NSApplication terminate:]`, which exits without any close request, so `view/appkit.rs` points that menu item at the main window's `performClose:` instead (`wire_app_menu`, from eframe's creation closure, which also points About at the About tab and adds Check for Updates… and Settings…, `330` phase 3) — ⌘Q then arrives as the same close request as the close button. Closing the main window ends `eframe::run_native`, and `main` calls `exit(0)` straight after, as `terminate:` would have, so none of `main`'s locals drop (the audio engine would drop the plugin voices the shutdown leaves to leak — `130`). Quit from the Dock, logging out, restarting and shutting down call `terminate:` themselves, which asks the app delegate's `applicationShouldTerminate:` first; winit's delegate has none, so `appkit.rs` adds one to its class at runtime (`class_addMethod`, then sets the delegate again in case AppKit cached what it answers). It answers `TerminateCancel` and sends the main window `performClose:`, so those quits become the same close request too. **Caveat**: a cancelled terminate also cancels the logout, restart or shutdown, even when nothing is unsaved and the app quits straight after. macOS then says Stev cancelled it, and the user has to log out again. `TerminateLater` would avoid that, but AppKit then runs only `NSModalPanelRunLoopMode` until the reply, and whether egui still gets its key events there is unverified.
- **Failures are said, not logged**: a load that fails says `Could not open <name>: <error>` in the footer and keeps the open project (and its saved state); a save that fails leaves the saved state as it was.

## Opening from Finder

macOS only, inside the app bundle (2026-10-25, `330` phase 4). Double-clicking a `.stev` in Finder, or dropping one on the Dock icon, opens it.

- **The type**: the bundle's `Info.plist` exports `com.stevmidi.stev.project` (conforming to `public.data`, extension `stev`, "Stev Project") and claims it as its owner (`CFBundleDocumentTypes`, role Editor). No document icon of its own: Finder draws the app's icon on a page. A bare `cargo run` registers nothing, so Finder doesn't offer it.
- **Catching the open**: macOS sends the open-documents Apple Event (`kAEOpenDocuments`), which winit doesn't pass on. `view/appkit.rs` handles it with a small class of its own (`OpenDocuments`). AppKit installs its own default handler while it launches, replacing any installed earlier, so `install_open_documents_handler` (called from `main()`, before eframe runs) only observes `NSApplicationWillFinishLaunchingNotification`, and the handler is installed from there. That is after AppKit's defaults and before a launch-time open is dispatched, as Apple advises. The handler keeps the event's first `.stev` (others ignored) in a main-thread slot and wakes the frame once egui's context exists.
- **Into the app**: `Display::sync_open_document` takes the path once a frame and asks for `ProjectAction::OpenFile { path }`, through the unsaved-changes check like the browser's Enter. It waits while a project dialog, a field or the plugin restore has the keyboard (`keyboard_taken`), so the path stays in the slot until then; Settings stays up over the opened project, as for the app menu's items. At launch it waits for the first frame and replaces the empty startup project. During a take session the sequencer refuses it, as it refuses the browser's open.
- **Where the project ends up — copied in, never opened in place**: `EventHandlers::open_file_workflow`. A file inside the library (directly in the projects root, or in one of its project folders) opens as the browser opens it (`storage::library_project`, both paths resolved, the extension in any case). Both this and the browser read a `.stev` through one reader (`storage::read_project`). Anything else — Downloads, a USB stick, a deeper folder, `Clips` — is read and parsed, then copied into the projects root (`storage::copy_project_in`) under its file name (or `Untitled` when that is no project name), with `_2`, `_3`, … while the name is taken, never overwriting. The copy is then opened as any other project, its folder the root. The footer says `Copied <name> into Projects` and a shown browser re-reads the tree. The original is never touched. A file that won't read or parse is never copied: the footer says `Could not open <name>: <error>`, and the open project stays. Decided 2026-10-25: the library stays the one place projects live; opening in place would need a project's identity to be a full path rather than `(folder, name)`. Unit-tested in `storage.rs` (`project_in`, `copy_project_into`).
- **Not done**: a recent-documents list, opening a `.mid` from Finder (import stays a drag or the browser), a second window.

## MIDI clip export

- **`⌘/Ctrl+⇧+E` writes the lead clip to a `.mid`, one clip at a time** (whole-arrangement export is not planned, `280` § Not planned). `InputEvent::ExportClip` → `SequencerCommand::ExportClip` → `EventHandlers::export_clip_workflow`: `Sequencer::export_lead_clip` picks the clip and builds the bytes, `storage::save_clip_export` writes them, and the footer message (`UiEvent::Status`, `030` § Header & Footer) says `Exported <name>`, why nothing was exported, or the write error — never silent.
- **Which clip**: the lead clip, whole, in both views — a marquee or note selection inside it never narrows the export. An arranger marquee (with a tick range) touching more than one clip on its tracks refuses ("Select a single clip to export"); to export a section or several clips, merge them first (`⌘/Ctrl+J`). No lead clip: "No clip to export".
- **What goes in**: what the clip plays — `Clip::exported_events` applies Merge Clips' bake rules (`merge.rs`): only events inside the window, notes stopped at the window end, hidden material from splits/resizes left out, the wheel moves playback makes at the window's edges written in (a bend held from before the window at tick 0, neutral at the end for a wheel left off it — `Clip::wheel_edges`) — and drops muted events. Recorded pitch bend and mod wheel (`090`) need no DTO change: `EventData.midi_message` already holds any message's raw bytes. The clip's own mute is ignored (exporting it is asking for its content). Ticks count from the window start.
- **The file** (`smf::write_smf`, no dependency): Type 0, one track, the division is `PPQN` (960), then a tempo meta event (the project tempo), the project's time signature (`FF 58`: numerator, log2 of the denominator, 24 MIDI clocks per click for x/4 and 12 for x/8), the channel messages with their own channel bytes (system messages are skipped), and the end-of-track at the clip length, so another DAW imports a two-bar loop as two bars even when its last note ends early.
- **Where and named how**: in the `Clips` folder (§ above), as `<project>_T<track>_B<bar>.mid` — the open project's name (else the folder's, else `project`), the 1-based track and the bar the clip starts in. An existing file is never overwritten: `_2`, `_3`, … go before the extension (`clip_export_name`).

## MIDI clip import

- **A `.mid` becomes one clip on one track** (multi-track import is not planned, `280` § Not planned). Three ways in, one edit: **drag** a `.mid` from the file manager onto an arranger lane, **drag** a clip row out of the browser panel onto one, or **Enter** on a clip row in the browser, which puts it on the selected track at the cursor. No dialog, no modal.
- **The drag shows where it lands** (`view/display/input/midi_drag.rs`, `GestureState::midi_drag: Option<MidiDrag>`): the file is read the moment the drag starts (`FileDragEntered`, or a browser clip press leaving the panel), and from then on the cursor line follows the pointer as on any move and a ghost of the clip-to-be (`MidiDrag::ghost_at`, drawn like the band-drag ghost at `CLIP_GHOST_ALPHA`, note thumbnails included) rides on the lane under the pointer, at the cursor line's snapped tick — the same grid test a click uses, so the ghost starts exactly where a click would put the cursor. Off the arranger lanes (the docked clip pane, track headers, performance lane, browser) there is no ghost and a drop imports nothing. The drop (`FileDropped`, or the release of a browser drag) imports at the ghost; Esc cancels a browser drag; a file-manager drag leaving the window (`FileDragLeft`) drops the ghost. A file not named `.mid`/`.midi` (`project::is_midi_file`) is refused unread, and an unreadable one says why in the footer on the drop.
- **The pointer during a file-manager drag comes from the OS.** winit 0.30 reports no pointer positions while the OS runs a drag (on macOS it implements `draggingEntered`/`performDragOperation` but not `draggingUpdated`), so egui's pointer would freeze for the whole drag. `Display` keeps eframe's content view (`DragPointer`, taken from the `CreationContext` in `main`), and while files hover — and on the drop frame — `App::raw_input_hook` (`inject_drag_pointer`) reads the pointer from AppKit (`mouseLocationOutsideOfEventStream`) and pushes it into egui's raw input as an ordinary `PointerMoved`. egui's own pointer is then right during and after the drag, so `InputPoller` and every hover need nothing special. Off macOS `DragPointer` is never built and the ghost follows whatever the windowing layer reports — to check in a port's smoke test (`260` § Smoke test); winit 0.31's drag events carry a position and would replace the AppKit read.
- **The edit**: `InputEvent::ImportMidiClip { clip, name, target }` → `SequencerCommand::ImportMidiClip` → `EventHandlers::import_clip_workflow` → `PasteClipsEdit::importing` (`clip_edits/import_clip.rs`) — a paste of the one clip with a fresh id, so it carves what it lands on like `⌘/Ctrl+V` and is one undo step. `target` `None` (Enter in the browser) resolves to the selected track at the cursor in the handler; no selected track: "Select a track to import onto". It lands like a dropped clip band drag (`PasteLead::ClipSpan`, `050`): the cursor on its start, its track selected, it the lead, its span marqueed — so a second Enter on another `.mid` replaces it in place, which makes auditioning a folder of files one key each. The footer says `Imported <name>`.
- **The file** (`smf::read_smf`, hand-rolled like the writer — no dependency): Type 0, 1 and 2 are all read the same way — every `MTrk` chunk's channel messages merged into one stream (unknown chunks, meta events and sysex skipped; running status honoured; a zero-velocity note-on becomes a note-off), ticks rescaled from the file's division to `PPQN`, rounded to the nearest. **The file's tempo and meter are ignored** — the project's stay. SMPTE-timed files are refused. Lenient where it can be: a chunk running past the end is read as far as it goes, a track without an end-of-track ends at its last event. Channels are kept as they are; playback rewrites them to the track's anyway.
- **The clip** (`Clip::imported`, `models/clip/import.rs`): window from 0, its length the file's end-of-track (or its last event, if later) **rounded up to whole bars** of the project's meter (read when the file is loaded or dragged in), so it loops on the bar like a capture; a note still open at the end is closed there, an orphan note-off dropped; CCs and the other channel messages kept. A file with no note imports nothing ("Could not import …: it has no notes").
