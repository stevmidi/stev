Everything else is open. Each actionable item is a checkbox — `[x]` done (with the date and commit), `[ ]` open, `[-]` moved out of this release. The repo is headed for open source under `MIT OR Apache-2.0` as the author's own opinionated sequencer, built around capture. It began as a minimal _base_ for others to fork; that framing was dropped on 2026-10-07 (§ Principle). This doc lists what still has to happen before it goes public, and what isn't planned. Tick items off here as they land; when the plan is done, move this file to `archive/`.

## Principle

**Build the app the author wants to use** (reframed 2026-10-07). Stev is an opinionated sequencer built around capture: play freely, and keep what you just played. That workflow is why the app exists. It grows in that direction, not toward a general-purpose DAW, and a feature earns its place by serving that workflow, not by whether every user would want it. Others are welcome to fork it and take it elsewhere. The licence, the agent-oriented docs and the clean platform boundary (§ B) make that practical, but the repo doesn't shape itself around forks. Every addition still follows the ground rules in `AGENTS.md` (tests in the same change, docs in sync, the build gate, permissive licences only).

Until 2026-10-07 the principle was the opposite: add a feature only if nearly every fork would build it the same way, and leave everything else as a seam. The § A items were scoped under that rule, so their "seam for forks" wording is historical.

## A. Core features before release

Gaps a newcomer hits in the first ten minutes.

1. [x] **Basic mouse note editing in the piano roll** — done 2026-10-01 (`ad498ec`, `b0afbce`, `7fb8f9f`). Before it, notes only arrived by recording; no gesture created, moved or resized one. As built: Deliberately minimal and modeless — no draw/pencil mode — so forks with their own editing taste build on it rather than around it:
   - **Double-click empty grid** creates a note at that pitch, start snapped to the visible piano-roll grid, with the last-used length and velocity (a beat and 100 until set). The new note becomes the selection and is auditioned. Double-click only creates; length is set by dragging the edge afterwards.
   - **Drag a note's body** moves it: horizontal = time (in whole visible-grid steps from where it was — relative snapping, so a recorded note keeps its feel; `Q` puts notes on the grid), vertical = pitch (auditioned on each pitch change). A selected note moves the whole selection; an unselected one is selected and moves alone (the velocity drag's target rule).
   - **Drag a note's left/right edge** resizes it (in whole grid steps, as the move; the left edge keeps the end fixed), resize cursor on hover. Hit priority: edge, then body, then empty grid; an edge zone is at most a third of the note's width, so tiny notes stay movable.
   - Unchanged: click selects/deselects, drag on empty grid is the event marquee, ⌘-drag is velocity, Delete/arrows/`M`/`Q` act on the selection.
   - **Rules**: one gesture = one undo step — a move/resize drag is applied live, a `DragNotesEdit` step per pointer move merged into one undo step (the velocity drag's shape, so playback hears the notes where they are dragged; Esc puts them back and leaves no step), the double-click one `InsertNotesEdit`; undo/redo of a created note keeps its event id. Selecting the new note is a deliberate exception to "a commit never changes the selection", which stays a capture rule. "Last-used" = the last note created or resized, view-local, not persisted. An edit that would overlap a same-pitch note trims the earlier note to end at the later one's start, so NoteOffs never collide. Pitch clamps to 0–127 and note starts to the clip window (a note already outside it may move back in, never further out); a growing end stops at the window end; drawing never extends the clip. Moving or stretching a sounding note during playback must not hang it — done: a regression test exposed a real hang (event edits only re-seeked), fixed for every event edit by `Track::edit_clip_events` (`050`).

   - [x] **The piano roll's vertical range follows the notes.** Done 2026-10-01 (`b93c46a`); as built in `030` § Piano Roll. `Display::note_area_geom` sizes the visible key range from the clip's notes every frame (`piano_roll_note_range`, half-octave padding, `expand_note_range_to_fill`, rows shrunk by `fit_row_height` when the range doesn't fit), so inserting a note near or past the edge of that range widens it and the whole grid jumps vertically under the pointer — the note just drawn moves away from where it was clicked, and a pitch drag ratchets the range outward as it nears the edge. It breaks the clip view's "never auto-zooms/scrolls" principle (`220`) for the vertical axis. Design (agreed 2026-10-01) — the vertical twin of the horizontal home framing (`clip_home_span`, `030` § Clip-view zoom):
     - **Home note range, latched on open.** `frame_clip_home` (`ClipEntered` / `LeadClipChanged`) also saves the padded note range (today's `piano_roll_note_range`; C2..B5 for an empty clip) in `RenderState`. From then on `note_area_geom` derives everything from that saved range and the pane height — never from the clip's current notes. Opening a clip therefore looks exactly as today: same fit, same fill (`expand_note_range_to_fill`), same row shrink when the range doesn't fit.
     - **Row height never changes on an edit.** Insert, move, resize, transpose, quantize, delete and undo/redo leave the row height and the vertical scroll untouched. Only three things set the row height: opening a clip (or another becoming the lead), a pane-size change (dock ↔ maximize, window resize — recomputed from the _saved_ range; not an edit, so allowed), and the capture re-frame below. User vertical zoom stays out (§ D territory).
     - **User-owned vertical scroll.** A `clip_scroll_y` in `RenderState`, written only by the user's scroll and the re-frame rules here. The wheel / two-finger Y delta over the clip pane scrolls it (`InputPoller` forwards `smooth_scroll_delta.y`, today dropped; still ignored over the arranger, which has no vertical scroll; the pane under the pointer decides, as for the X scroll). Clamped to the full keyboard (0–127) at the current row height, so any pitch is reachable even when the rows were shrunk to fit the home range. On a pane-size change the pitch at the centre of the view stays put. No follow: an Up/Down transpose can move notes out of view, as the clip view never follows the cursor horizontally.
     - **Drag past the edge auto-scrolls.** A note pitch drag (`gestures.rs`, today clamped through `note_at_screen_y`) keeps going past the top/bottom of the note area: while the button is held with the pointer beyond the edge, the view scrolls every frame (repaint requested), speed growing with the distance past the edge, and the dragged pitch follows the row now at the edge (the event marquee was in this design too; dropped 2026-10-02, see the marquee preview item below). The scroll belongs to the user's own gesture, so it doesn't break "never scrolls on the user's behalf"; it stays where it ended on release (and on Esc, which puts the notes back but not the view).
     - **Capture re-frames only when the take would be out of view.** A capture commit that lands notes in the open clip (the stopped `/` insert, a running commit into it): if every note of the take is inside the visible rows, nothing moves; if any would land out of view, the view re-frames exactly as on opening the clip (new saved range, row height, centred, scroll reset). Decided from what is on screen, never from a stored "has the user scrolled" flag (`220`: no stored mode-like state). Needs its own signal — `EventsUpdated` fires for every edit and must keep re-fitting nothing.
     - **Same change**: rewrite `030`'s "Vertical viewport auto-follows" bullet (and its "no manual vertical scroll input" line) and the `InputPoller` scroll comment; note the vertical axis under `220`'s "clip view never auto-zooms/scrolls" principle; pure helpers (scroll clamp, centre-anchored rescale on resize, "take fully visible" test, auto-scroll speed) carry `mod tests`.

   - [x] **Preview on marquee selection.** Done 2026-10-02 (`e6f3f9a`); as built in `020` § Event Marquee Selection. The event marquee used to be silent (auditioning on every drag-move would spam audio). Chosen design: each rect update auditions only the notes that _newly_ joined the selection (the `select_events_in_rect_workflow` diff), earliest first, one per pitch, capped at `MARQUEE_AUDITION_MAX_NOTES` (4) — no rate limit, nothing on release. And a preview's note-on on a plugin track is now `At(now)`, not `Immediate` (which queued it behind the previous preview's note-off — late, and some squeezed silent on a quick sweep; `130`).

   - [x] **Same-tick sort order for every event edit.** Done 2026-10-02 (`0ddf83e`). `Clip::sort_events_by_tick` used to sort by tick only (stable), so a `NoteOn` could land ahead of a same-pitch `NoteOff` on a shared tick and `pair_note_events`' per-pitch stack paired the wrong off — e.g. a keyboard nudge of a note onto the end of a same-pitch note gave `(480, 960), (720, 720)` instead of `(480, 720), (720, 960)`. Tests in `events.rs` and `edits.rs`; the capture-fixture tests pass unchanged.
   - [x] **Two retimes still bypass the sounding-note release.** Done 2026-10-02. `Sequencer::rescale_selected_clip_tempo` (`region/tempo.rs`, ⇧-/+) and `FitFirstClipEdit` (`clip_edits/fit_first_clip.rs`, edit and restore) retimed a clip's events through a bare clip borrow, so a note sounding during playback hung the way a dragged one did (each regression test reproduced it). One merged clip per marqueed track (never across tracks), spanning exactly the marquee's tick range — gaps become silence, a straddling clip keeps its outside part. Baked so it sounds exactly as before: only notes that play come over, ends stopped at their clip's window end (a note cut by a split stays cut), hidden material dropped (undo restores it), a muted clip's notes come over muted. 4. [x] **Add / remove / rename tracks.** Done 2026-10-05 (five commits, below). The track count is fixed (`TRACK_COUNT = 8` in `src/core/config.rs`). Touches persistence (`060`), the instrument mixer (`130`), `SharedAtomics` per-track mixer state and undo (`050`). Scope agreed 2026-10-04 (`feature/add-remove-tracks`): **a 16-track cap with add, remove and rename, no reordering; a new project starts with four tracks.**
   - **Capacity, not a growable list.** `TRACK_COUNT` becomes `MAX_TRACKS = 16` and keeps sizing every per-track array it sizes today (`SharedAtomics` volume/pan/mute/solo, the instrument mixer's voices and gain caches, `InstrumentNotes`, the DSP load meter and overrun journal, the view's per-track mirrors), so the audio thread never allocates or changes shape. What varies is the **live track count**: `Sequencer::tracks` holds that many `Track`s, slots past it are idle (no voice, unit gain, never drawn). 16 = one per MIDI channel, so every track can still default to a channel of its own. A fork wanting more raises the constant. Why still add/remove under a cap: without it all 16 lanes would always show — a fresh project of 16 empty half-height lanes. The cap decides what the engine carries; add/remove decides what you see.
   - **New project: four tracks** (`ProjectData::default`, `Sequencer::new`; was 8), channels 1–4. A saved project loads with however many tracks it holds — today's projects keep their 8. A file with more than 16 loads the first 16 and the footer's passing message says so; a file with none gets one (never zero tracks).
   - **Add** inserts a new empty MIDI track **after the selected track** and selects it (Ableton's ⌘T; an append when the selected track is the last). Its channel is the lowest one no other MIDI-Out track uses (always exists: ≤16 tracks). Refused at 16 with a passing message.
   - **Remove** deletes the **selected track** — its clips, its plugin, its mix settings — and selects the track that took its place (the one above when it was the last). Refused on the last remaining track. During playback its sounding notes are released first (`Track::release_sounding_notes`), and a plugin track's voice goes through the existing reclaim path (`130`).
   - **Both are undoable, one step each** (`AddTrackEdit` / `RemoveTrackEdit`, `050`). Not a nicety: every undo edit names its track by index (`track_idx: usize`), and the stack stays sound only because each step is undone in reverse order — undoing an edit made before a remove first undoes the remove, which puts the track back at its index. A non-undoable remove would have to clear the history. The remove step keeps the whole `Track` (clips, output, mix values); undo re-inserts it at its index, and a plugin track **reloads its plugin from the state blob** captured at remove time — the project-load path, so no live voice is parked in the undo stack. The editor stays closed on that reload.
   - **Stable engine slots, not an index shift** (changed 2026-10-04 while building commit 2; was "shift every per-slot array"). Every track has a **slot** (`Track::slot`, `0..MAX_TRACKS`) it keeps for its whole life, unique among the live tracks; everything the engine keeps per track is keyed by slot, not position: the `SharedAtomics` mix values, the instrument mixer's voices and gain caches, `InstrumentNotes`, the tag on every plugin-bound event, the view's `track_instruments`. Add takes the lowest free slot, remove frees it (back at neutral mix), and undo puts a track back in its own slot — free again because undo runs in reverse order (else the lowest free one). So **nothing moves on the audio thread**: a removed plugin track's voice goes the ordinary `Remove` / reclaim way, a restore reloads into a free slot. Why not the shift: Display (the mixer's command producer) learns of a remove a frame late while the sequencer's notes already carry new indices on a separate ring, so a shifted voice could take another track's note-on and hang it; ordering two rings against each other on the audio thread was the alternative. What still moves is only *positional* view state — clip shapes, the marquee span, the selected index — through the pure `TrackShift` helper (`models/track.rs`, `mod tests`), riding on the mirror event. Sequencer APIs stay positional (`set_track_volume(track_idx, …)` etc. translate to the slot); slots are session-only (a load resets slot = position).
   - **A track keeps its colour.** Colour is by index today (`theme::track_color(track_idx)`), so a remove would recolour every track below it. A track gets a palette slot when it is created (the next one in rotation past the last track's) and keeps it, persisted in `TrackData` (`#[serde(default)]` = its index, so old projects look as before). Palettes grow from 8 to 16 track colours. Keep the colour slot **separate from the engine slot** (`Track::slot`, commit 2): colours may repeat once tracks come and go, engine slots must never collide, and engine slots aren't persisted (a load resets them to positions) while colour slots are. Commit 2's stable engine slots already show the wanted behaviour on a delete — the tracks below keep their slot — but would reshuffle colours after a save and reload, which is why colour gets its own field. ## B. Platforms: macOS first

**Decided 2026-10-07: macOS is the supported platform; Linux and Windows build in CI but are untested.** The plugin host, the app's strongest feature, is macOS-only, so off macOS Stev is a MIDI Out sequencer. Supporting Linux and Windows properly means timing work per OS, smoke tests on machines the author doesn't use, and support requests the author can't reproduce: the kind of support that would quietly be neglected, which is worse than none promised. What stays is the cheap part that keeps a port possible: CI compiling and testing all three, and a clean `cfg` boundary. A fork that wants another platform (with an agent's help) then starts from code that already compiles there. The parked Linux/Windows plans moved to § D (official support) and § Post-launch candidates (MIDI Out timing, which helps macOS too).

  - **GitHub Actions, one workflow** (`.github/workflows/ci.yml`), one job per OS: `ubuntu-24.04`, `windows-2025`, `macos-26` (as built: pinned 2026-10-07 instead of the `-latest` labels, for the toolchain pin's reason — see `000` § CI). Branches are merged locally and fast-forwarded (no PRs), so CI reports after the merge and a red `main` is fixed forward. Why not every push: while the repo is private, Actions minutes are billed (macOS counts 10×, Windows 2×; one three-OS run ≈ 100 of the free plan's 2,000 a month). CI and local `cargo` (rustup reads the file) use the same version, and a new stable's lints can't turn `main` red on a day nothing changed.   - **A licence check**: `cargo deny check licenses` with a `deny.toml` allowing the § Licensing families (MIT, Apache-2.0, BSD-2/3-Clause, ISC, Zlib, Unicode-3.0 and the like; MPL-2.0 tolerated). The runner installs `libasound2-dev` and `pkg-config` (ALSA, for cpal and midir), plus whatever the first run shows is missing.

## D. Not planned

List these in the README so nobody expects them. Some may come later if the capture-first workflow needs them, but none is on the roadmap. (Until 2026-10-07 this section was "deliberately out of scope": features left for forks to build.)

- tempo maps and meter changes
- audio tracks and audio recording
- automation lanes and CC lane editing
- effect plugins, sends, a mixer panel
- MIDI clock / Ableton Link / external sync
- notation
- whole-arrangement MIDI file export and multi-track import (the base moves one clip at a time, § A2)
- a richer browser: search, tags, favourites, preview playback, sample/preset categories (§ A3 is a Projects category of folders, `.stev` and `.mid` files, and a flat Plugins category)
- richer piano-roll editing: a draw/pencil mode, paint-drag, erase gestures, ⌥-drag duplicate, unsnapped drawing, drawing velocity in the velocity panel, Shift-click to add to the selection, drawing clips in the arranger
- more than 16 tracks, track reordering, track groups/folders (§ A4)
- DAW integration: Mackie Control or other control-surface sync (removed 2026-10-07, § Trim)
- **official Linux and Windows support** (§ B, decided 2026-10-07). They build and pass the tests in CI; nothing more is promised. What a port would need (what's macOS-only, MIDI Out timing first, plugin hosting, a smoke test) is in `260-porting.md`.

**Never in scope:** VST2 or any VST format older than VST3. The VST2 SDK is no longer licensed by Steinberg and cannot be redistributed under `MIT OR Apache-2.0`; VST3 (MIT since SDK 3.8) and newer formats only. See `180-vst3-host.md`.

## Post-launch candidates

Not part of the first public release: what comes next, each weighed against § Principle when it comes up. Listed here so they stop reopening this plan.

- **Time signature, done properly — the first post-launch priority** (decided 2026-10-07, replacing § A10's 4/4-only project field). 4/4 is assumed everywhere today, and proper support means the meter reaches every place a bar is computed, which needs its own design. Survey of where 4/4 lives:
  - **The maths:** `bars_to_ticks`, `bars_to_beats` and `ticks_to_bars` in `core/time.rs` multiply by a literal 4; about 250 call sites go through them (capture and stopped capture, phrase detection's bar windows and tokens — `phrase_tokens.rs` even has its own `BAR = 3840` — region windows and tempo fit, clip edits, quantize, the grid, zoom, scroll, the timeline ruler).
  - **The metronome's downbeat** (`metronome.rs`, the strong click on the bar).
  - **What other software is told:** the CLAP transport (`clap/voice.rs`, numerator/denominator 4/4), the VST3 `ProcessContext` (`vst3/voice.rs`, `timeSigNumerator`/`Denominator`), `BlockTransport::bar_number`/`bar_start_beats` (`plugin_host/transport.rs`), SMF export's `FF 58` bytes (`smf.rs`). SMF import ignores any `FF 58`.
  - **Persistence:** `ProjectData` has no meter field. None was added before release on purpose: a project without the field already means 4/4, so the feature adds it with `#[serde(default)]` → 4/4 and every earlier file still loads.
  - **The first design question:** one meter per project, or meter changes along the timeline. The second touches the bar ↔ tick maths at every site above, not just its constant.
- **MIDI Out timing** (parked 2026-10-07 with the macOS-first decision, § B). The analysis, the timing-probe design and the fixes moved to `260-porting.md` § Timing on 2026-10-08, since they are a port's first job. If picked up here, it starts on macOS alone: the probe measures macOS as well, the precise `"midiout"` wait helps every platform (crossbeam's `select!` timeout is a condvar wait on macOS too), and macOS threads have no real-time priority either. The author's own test plan stays here:
  - **The machines**: the Windows 11 machine, booted both natively and from an **Ubuntu 24.04 live USB stick**, so Windows and Linux are compared on the same hardware; the Intel Mac as the reference (the mach timer path); a **Surface Pro 3 on Windows 10** as the old-laptop worst case (2014 low-power Intel, throttles when hot: run it plugged in, on the *High performance* power plan, cooled between loaded runs; a first release build may need `-j 2` on 4 GB of RAM); and, optionally, the headless Raspberry Pi 4. Windows 11 stays the main Windows machine: unlike 10, it stops honouring a process's timer-resolution request while that process's window is minimised or hidden, so the `timeBeginPeriod` fix (`260`) must be checked on 11, in the app, with its window minimised. On the live stick, nothing persists across a reboot: `apt install build-essential pkg-config libasound2-dev git`, install rustup (the pinned toolchain installs itself), and fetch the private repo with a GitHub token over HTTPS, or copy it over on a stick.
  - **Loopback hardware**: a Roland UM-ONE with its Out plugged into its own In, on every machine (the Scarlett 2i2 has no MIDI).

- **Keyboard shortcuts as a settings tab, with rebinding** (user direction, 2026-10-07). The § A8 help overlay is the first-release form. ## Trim before publishing? Resolved

The question (2026-10-01) was whether to keep, feature-gate or remove features specific to the author's workflow before going public. Since 2026-10-07 the author's workflow *is* the point (§ Principle), so they stay:

- the performance lane (`110-performance-lane.md`)
- phrase detection (`040-phrase-detection.md`), the heart of capture

Two DAW-companion features went instead, since the author no longer runs a DAW alongside (plugin hosting replaced that setup):

- [x] **DAW track sync via Mackie Control emulation: removed 2026-10-07.** It created a `midi-seq Control` virtual port pair and kept track selection in sync with Logic Pro. Gone: `midi/mcu.rs`, the `"mcu"` thread and its channel, `SequencerCommand::SelectTrackFromSurface`, the selection-origin enum (track selection is one path again), and the port-list filter for the MCU port. Its doc moved to `archive/120-daw-track-sync.md`.
- [x] **The Bitwig-extension track-select CC: removed 2026-10-07.** It sent channel 16 / CC 0 on every track selection, for a Bitwig controller extension used alongside the app before plugin hosting existed. Mackie Control sync did the same job (removed the same day, above), and the author no longer uses Bitwig. `send_select_track_mcu` moved into `event_handlers/selection.rs`, its only caller, and `midi_cc_helpers.rs` was deleted. The CC was also the last user of `EventHandlers`' own MIDI-out sender (`midi_out_tx` / `send_midi_out`), which went with it; previews, thru and releases have their own senders (`160`).
