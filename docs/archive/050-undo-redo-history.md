# Undo / Redo

Undo/redo uses the [`undo` crate](https://docs.rs/undo) (`Record<SequencerEdit>`) and is wired entirely inside the sequencer thread — no new shared state or atomics.

## Data Flow

```
⌘/Ctrl+Z keystroke
  → InputEvent::KeyPressed { Z, command }
  → send SequencerCommand::Undo
  → sequencer thread select! arm
  → undo_record.undo(sequencer) → EditResult
  → handle_edit_result() dispatches clip workflows or inline event-selection sync
```

## `EditResult` and `SequencerEdit`

- **`EditResult`** is the return type of `Edit::edit()` and `Edit::undo()`. It carries enough information for the handler to fire the correct UI events. Current variants include `ClipsSplit`/`ClipsUnsplit`, `RangeDeleted`/`RangeRestored`, `SilenceInserted`/`SilenceRemoved`, `TimeDeleted`/`TimeUndeleted` (`⌘/Ctrl+Delete` "Delete Time" — the exact opposite of `SilenceInserted`/`SilenceRemoved`: `carve_updated`/`carve_added`/`carve_removed` mirror `RangeDeleted`'s buckets instead of a split's, since the space-closing step is a full non-rippling carve, not a single boundary split; `shifted` is every clip that moved to close the gap, same as `SilenceInserted`'s `shifted`; both variants carry selection context since the carve half — unlike Insert Silence's split half — can remove the selected clip outright; `TimeUndeleted` additionally carries `restored_selection: (i32, i32)`, the edit's frozen `start`/`end`, so the handler can put the Arranger time selection back — the mirror of `TimeDuplicated`'s `new_selection` below, restoring instead of advancing), `ClipsPasted`/`ClipsUnpasted` (each carrying `carve_updated`/`carve_added`/`carve_removed` — the range-carve buckets, mirroring `RangeDeleted` — plus `pasted`/`unpasted`), `ClipMoved`/`ClipUnmoved` (the band-drag move — `from`/`to` metadata of the one clip plus the same three carve buckets), `RangeMoved`/`RangeUnmoved` (the marquee band-drag move — `moved_from`/`moved_to` for every piece forward, `unmoved`/`restored` on undo, plus `split_updated`/`split_added` forward and `split_removed` on undo for the pre-move split of the source clips, never including a piece itself, the three carve buckets, and `new_selection`/`restored_selection: TimeSelectionRect` so the handler moves the marquee with the block), `ClipsDuplicated`/`ClipsUnduplicated` (plain `⌘/Ctrl+D` "Duplicate Clips" — exactly `ClipsPasted`/`ClipsUnpasted`'s buckets, since `DuplicateClipsEdit` *is* a `PasteClipsEdit`, plus `new_selection`/`restored_selection: TimeSelectionRect`; the carve buckets are real here — the copy overwrites — and the rect carries its track span, so the handler sends `TimeSelectionSet { track_span: Some(..) }`), `TimeDuplicated`/`TimeUnduplicated` (`Shift+⌘/Ctrl+D` "Duplicate Time" — the union of the `SilenceInserted` buckets and `pasted`, plus `new_selection`/`restored_selection` so the handler can advance the Arranger time selection; its carve buckets are always empty because the insert-silence step pre-clears the gap), `RangeMuted`/`RangeUnmuted` (`M` with a time selection — every clip overlapping the range is split at its edges like `RangeDeleted`, but nothing is removed; `RangeMuted { updated, added }` carries no selection context since nothing can be removed, `RangeUnmuted { updated, removed, selected_track_idx, selected_clip_id }` does, since undo deletes the split pieces), `ClipCommitted`/`ClipUncommitted` (`CommitClipEdit` — a brand-new clip on a track / lifted off it; each carries just the one `clip: ClipMetadata`, no selection context, since lifting doesn't touch the selection and `uncommit_clip_workflow` reads it live), `EventsModified`, and `NoOp`. `ClipsUnsplit`/`RangeDeleted`/`ClipsUnpasted`/`RangeUnmuted`/`TimeDeleted`/`TimeUndeleted` carry optional selection context (`selected_track_idx`, `selected_clip_id`) so remove paths can preserve valid selection when available (undoing a split/paste/mute can remove a clip that may be the current selection, and a range delete or Delete Time's carve half can remove one directly). There is no single-clip `ClipRemoved`/`ClipRestored` pair any more — it backed the removed `RemoveClipEdit`. `RangeMuted`/`RangeUnmuted` trigger a `UiEvent::ClipUpdated` for each affected clip so the display refreshes mute appearance. `ClipsPasted` no longer carries a `select` field — it was added to force-select a newly duplicated clip for the now-removed bare-`D` binding (see below); `⌘V` and both `⌘/Ctrl+D` forms already use the cursor-based reselection `paste_clips_workflow` falls back to.
- **`SequencerEdit`** is an enum of all undoable edit structs, implementing `undo::Edit<Target = Sequencer, Output = EditResult>`. The enum and its `Edit` impl are generated by the `sequencer_edit_dispatch!` macro — add new variants to its invocation list.
- **Current `SequencerEdit` variants**: the clip commit (`CommitClip`, backing the capture `/`, running or stopped, and a completed live take — see the dedicated paragraph below), the Ableton-style range carve-out (`DeleteInRange`, backing `Delete`/`Backspace` and both `⌘/Ctrl+X` forms — all marquee-only; the old single-clip `RemoveClip` edit that backed their no-selection fallbacks is gone, see `020-views-and-state.md`), Delete Time (`DeleteTime`, the exact opposite of Insert Silence, backing the `⌘/Ctrl+Delete` binding — same section), the Ableton-style split (`SplitClips`, backing both the single-selected-clip and time-selection-range `⌘/Ctrl+E` bindings — same section), Ableton/Bitwig-style Insert Silence (`InsertSilence`, backing the `⌘/Ctrl+I` binding — same section), "Duplicate Clips" (`DuplicateClips`, backing plain `⌘/Ctrl+D` — same section — a marquee-scoped, overwriting paste anchored at the selection end), Ableton-style "Duplicate Time" (`DuplicateTime`, backing `Shift+⌘/Ctrl+D` — same section — the global, space-inserting one; there is no bare-`D` binding, these two cover every duplicate need), Ableton-style clip paste (`PasteClips`, backing `⌘/Ctrl+V` and reused by both Duplicate edits — same section; the `⌘/Ctrl+C` copy that fills the clipboard is **not** an edit, and `⌘/Ctrl+X` cut adds no variant of its own — it fills the clipboard non-undoably then reuses `DeleteInRange`), the arranger band-drag clip move (`MoveClip`, backing the whole-clip mouse drag in `020-views-and-state.md` § "Clip Band Press & Move Drag" — with `MoveRange` the only mouse drags that are undoable, because they can carve other clips) and its marquee sibling (`MoveRange`, backing the same drag started inside an active marquee: everything in the marquee's rect moves as one block), the Ableton-style range-mute (`MuteInRange`, backing the Arranger's marquee-only `M` — same section; the old per-selected-clip `MuteSelectedClips` is gone), clip edge edits (`ResizeClip`, backing the arranger edge drag, merged to one step per drag, and `[`/`]` in both views; and `FitFirstClip`, Enter's tempo fit to the project's only clip, whose undo restores the bounds, the retimed events, the cursor and the tempo together, the one undo that reverts the tempo; both report `EditResult::ClipResized { clip }` in both directions, and neither moves the playhead (the loop follows only a project's only clip) — see `020-views-and-state.md` § "Clip Edge Drag-Resize" and `220-capture-without-pending-view.md`), the marquee-scoped quantize (`QuantizeInRange`, backing `Q` — same section; marquee-only, the old `QuantizeSelectedClip` fallback is gone; touches events only, never bounds, and reports `EditResult::RangeQuantized { updated }` in both directions), and event edits (`DeleteSelectedEvents`, `DuplicateSelectedEvents`, `NudgeSelectedEvents`, `NudgeSelectedEventsLength`, `TransposeSelectedEvents`, `DragEventsVelocity`, `MuteSelectedEvents` — per-*event* mute, backing `M` on selected notes in `Clip`; see below), and the capture insert into an existing clip (`InsertCapture`, backing `/` with a lead clip, running or stopped — see the paragraph after `CommitClipEdit`'s).
- **`PasteClipsEdit` composes one `DeleteInRangeEdit` per pasted clip**: same reuse pattern as below — it holds `carves: Vec<Option<DeleteInRangeEdit>>` parallel to its frozen `targets` (final positioned clips), each built with `DeleteInRangeEdit::from_track_range` so the carve is scoped to that pasted clip's target track only. `edit()` runs every carve first, then `Track::add_clip`s the frozen targets; `undo()` removes the targets then undoes the carves LIFO. Clipboard content is read once in `from_sequencer`; `targets` are built there so redo re-adds identical ids, and `undo()` overwrites each slot with the clip as lifted (see the `CommitClipEdit` paragraph) so redo also carries any edge trim made in between. `PasteClipsEdit::from_clipboard_at(sequencer, &clipboard, anchor)` factors this out from *which* clipboard and *where*: `⌘V` passes the real `clip_clipboard()` + cursor, `DuplicateTimeEdit` (`Shift+⌘/Ctrl+D`) passes a throwaway all-track `Sequencer::clipboard_snapshot` + the selection's `end` as anchor, and `DuplicateClipsEdit` (plain `⌘/Ctrl+D`) passes a throwaway track-scoped `Sequencer::copy_range_to_clipboard` + the same anchor. **`DuplicateClipsEdit`** (`src/core/sequencer/edit/clip_edits/duplicate_clips.rs`) is nothing more than that: a newtype holding the `PasteClipsEdit` plus its frozen `TimeSelectionRect`; `edit()`/`undo()` delegate and rewrap `ClipsPasted`/`ClipsUnpasted` as `ClipsDuplicated`/`ClipsUnduplicated` with the rect slid right by its own width / restored. The paste's per-target carve does real work here — the copy overwrites whatever it lands on — and the loop region is never touched. **`DuplicateTimeEdit`** (`Shift+⌘/Ctrl+D`, "Duplicate Time") composes *two* existing edits: an `Option<InsertSilenceEdit>` anchored at the selection's `end` (open the gap / push later clips right, **always every track**) followed by a `PasteClipsEdit` built pre-insert via `from_clipboard_at(.., end)` (drop the copied `[start, end)` slice into the freed span). `edit()` runs insert-then-paste; `undo()` runs paste-then-insert LIFO. Both sub-edits keep their own frozen state, so redo is stable; the paste's carve is always a no-op since the gap is pre-cleared — nothing is carved/destroyed. It also *moves* (never resizes) the loop region right by the selection width when the region start sits within/after the duplicated span (`Sequencer::shift_region`, decision frozen on first `edit()` as `region_shifted`, reversed in `undo()`) — the one place a clip-range edit deliberately touches the region.
- **`CommitClipEdit` is the one edit that puts a brand-new clip on a track, and it is idempotent by design** (`clip_edits/commit_clip.rs`, 2026-09-20): it holds `(track_idx, clip: Clip, consume_capture: bool)` where `clip` is a `detached_clone` of the clip *as last seen off the track* — the committed clip until the first `undo()`, whose id is what undo lifts and redo re-adds (so the UI shape keyed on `(track_idx, clip_id)` stays valid). Two paths create a clip from live input and both reduce to this shape, but they reach the record differently, which is what the idempotent `edit()` — "make sure the frozen clip is on its track": `add_clip` a fresh detached clone if `get_clip_by_id` finds nothing, otherwise touch nothing — exists to unify: (1) the **capture commit** builds its clip *pure* via `Sequencer::build_committed_capture_clip` (`capture.rs`; `None` on an empty buffer or a gap under one grid step, so a no-op commit never enters the record — the old one-shot `commit_clip_to_track` is now a `#[cfg(test)]` shim over the edit) in `from_running_capture`, or, while stopped, via `Sequencer::build_stopped_capture_clip` in `from_stopped_capture` (since 2026-09-25; pure — a first clip keeps its exact window and the tempo is untouched until Enter's `FitFirstClip`), and the first `edit()` places it and, once, `reset_capture()`s (`consume_capture` then flips to `false`, so a redo can never wipe a take the user started after undoing); (2) a **completed live take** has *already* placed its clip by the time its workflow runs (`end_live_recording` adds it), so it snapshots it with `from_placed_clip(sequencer, track_idx, clip_id)` and the first `edit()` finds it present. (A confirmed pending phrase took this path too until the pending view was deleted, 2026-09-26.) That workflow calls `undo_record.edit(..)` and **drop the forward `ClipCommitted`** rather than passing it to `handle_edit_result`: that arm is Arranger-shaped (`ClipAdded` + select + `reset()`) and the workflow has already done its own fan-out (`RecordingCompleted`/`ClipUpdated`). Undo and every redo go through `handle_edit_result` normally. `undo()` is `Sequencer::lift_clip` (the same remove-with-note-release `MoveClipEdit` uses) **and it keeps what it lifted** (`self.clip = detach(lifted)`), so a redo re-adds the clip *as it was when undone* — with every non-undoable change made since the commit (an `⌥-` clip stretch that shortened the first clip, an edge trim) — rather than re-materialising the construction-time snapshot, which lost those (reported 2026-09-20: 2-bar clip → `Shift+-` → 1 bar → undo → redo brought back 2 bars); the clip travels through `edit()`/`undo()`, the `MoveClipEdit` pattern, and the snapshot only ever places the first time. `PasteClipsEdit::undo` follows the same rule — each `targets` slot is overwritten with the clip as lifted, so a pasted (or `⌘D`-duplicated) clip trimmed before the undo comes back trimmed; it still fits on redo because a widening trim was bounded by the same neighbours the replayed carve leaves in place. Returns `ClipUncommitted { clip }`; `NoOp` if the clip is already gone (something else removed it, e.g. a later carve that was itself undone out of order — cannot happen with a linear record, kept defensive) or if a redo's `add_clip` is refused because the span is occupied now. **`uncommit_clip_workflow` is the one removal workflow that may change the view**: if the lifted clip is the selected one *and* the view is `Clip` — the user `Shift+Tab`bed into the clip after committing it — it leaves to the `Arranger` exactly like `exit_clip_workflow` (view state, `clear_event_selection_workflow`, `ClipExited`), then deselects, then sends `ClipRemoved` last (the invariant below). Two things it deliberately does **not** revert: the capture buffer (stays cleared — redo is the way back) and the project tempo (only Enter's `FitFirstClipEdit` changes it, and undoing that edit restores it).
- **`InsertCaptureEdit` is the capture into an *existing* clip** (`event_edits.rs`, 2026-09-26, phase 4 of `220-capture-without-pending-view.md`): `/` with a lead clip, running (`from_running_capture` over the pure `Sequencer::build_running_capture_insert`, `100-running-capture.md`) or stopped (`from_stopped_capture` over `Sequencer::build_stopped_capture_insert`, the detected phrase, `040-phrase-detection.md`). Both builders return a `CaptureInsert { track_idx, clip_id, events }` with the notes already in the clip's event ticks, or `None` when nothing would land in the clip, so a no-op insert never enters the record and the buffer is kept. It borrows `CommitClipEdit`'s capture rule: the first `edit()` clears the buffer (`consume_capture`), no redo does, and undo leaves it cleared. It wraps the file's shared `ClipEventsEditState`: `edit()` snapshots the clip's events through `edit_with`, adds the notes (same ids on every redo) and re-pairs; `undo()` is the state's restore. It isn't macro-generated because the macro's constructor requires a non-empty selection, and this edit acts on notes from outside the clip, not on the selection. **It never changes the event selection** (`020-views-and-state.md`): both directions report `EventsModified` with the selection the clip had when the edit was built, so the inserted notes are never selected. Pinned by `stopped_insert_lands_the_detected_phrase_at_the_clip_cursor`, `stopped_insert_is_undoable_and_keeps_the_selection`, `insert_running_capture_is_undoable` and the handler-level `stopped_commit_into_the_lead_clip_is_one_undoable_insert`.
- **`MoveClipEdit` composes one `DeleteInRangeEdit::from_track_range`, built lazily *after* the clip has been lifted**: it freezes `(clip_id, from_track_idx, from_start_tick, to_track_idx, to_start_tick)` at construction (`MoveClipEdit::new`, which returns `None` for a no-op / negative / out-of-range target so nothing enters the record) and holds `carve: Option<Option<DeleteInRangeEdit>>`. `edit()` first removes the clip from its source track (`Sequencer::lift_clip`, which queues `release_sounding_notes_for_clip` when running, like `DeleteInRangeEdit::take_interior`), sets its new `start_tick` (region untouched — a move never trims), and only *then*, on the first call, builds the carve for `[to_start, to_end)` on the destination track — so a same-track move over its own old span never targets itself; redo replays the frozen carve. Then `Track::add_clip` puts the clip back down, same id. `undo()` lifts it off the destination, `carve.undo()`s, and adds it back at `from_start_tick` (guaranteed to fit: the source span was vacated and the carve only touched other clips). No frozen `Clip` snapshot and no `detached_clone`: the clip object itself travels through `edit()`/`undo()`, never cloned into the edit, so the `Region` `Arc` caveat below doesn't arise. Returns `EditResult::ClipMoved`/`ClipUnmoved { from, to, carve_updated, carve_added, carve_removed }` — `from` is the shape to remove, `to` the shape to add (always remove + add, even same-track: shapes are keyed by `(track_idx, clip_id)`), the carve buckets mirror `ClipsPasted`/`ClipsUnpasted`; no selection context, since the moved clip always survives and `move_clip_workflow`/`unmove_clip_workflow` re-select it (and re-marquee its span) wherever it now sits via `select_clip_span_workflow`. `Sequencer::lift_clip` (the remove-with-note-release, in `clip_edits/mod.rs`) is shared with `MoveRangeEdit` below, `CommitClipEdit`, `PasteClipsEdit::undo` and `DeleteInRangeEdit::take_interior`.
- **`MoveRangeEdit` composes track-scoped `EdgeSplits` and one `DeleteInRangeEdit::from_track_range` per piece, in three phases**: it freezes the marquee `rect: TimeSelectionRect`, `delta_ticks`, `delta_tracks` and `source_ids` (every clip overlapping the rect on the marqueed tracks) at construction (`MoveRangeEdit::new`, `None` for a zero delta, a zero-width rect, a shift off tick 0 / off the lanes, or nothing to move) and builds its `EdgeSplits` restricted to the marqueed tracks — exactly `DeleteInRangeEdit::build`'s split step, same "cut at `end` first" order for the same id-keeping reason. `edit()`: (1) runs both splits; (2) resolves the **pieces** — every clip on the marqueed tracks now fully inside the rect, in track order — freezing `pieces: Vec<(source track, id)>` on the first call (stable across redo because the splits freeze their products), and **lifts all of them before carving anything** (`Sequencer::lift_clip` each), which is what stops a block shifted by less than its own width from carving its own pieces; (3) per piece, in order, shifts its `start_tick` by `delta_ticks`, builds (first call only, against the live post-lift, post-previous-carve state — the `PasteClipsEdit` pattern) and runs `carves[i]: Option<DeleteInRangeEdit>` for its destination span on `source track + delta_tracks`, and `Track::add_clip`s it there, id and region untouched (a failed add — should-not-happen, the carve just cleared the span — puts the piece back at its source, which the lifts left empty, so nothing is ever lost). `undo()` mirrors it LIFO: lift every piece off its destination first (so each carve's span is vacated), undo the carves in reverse, put every piece back at its source (always fits: the rect span was vacated by the lifts and the carves only touched other clips), then `EdgeSplits::undo` (`start` before `end`) — after the pieces are back, since `SplitClipsEdit::undo` bails on a missing right-hand product. Returns `EditResult::RangeMoved { moved_from, moved_to, split_updated, split_added, carve_*, new_selection }` / `RangeUnmoved { unmoved, restored, split_removed, carve_*, restored_selection }`: `moved_from`/`moved_to` are the pieces at source / destination (parallel, same ids; a piece split out mid-clip is a fresh id the UI never saw, so its `moved_from` remove is a harmless no-op), the split buckets are read back from the live state *after* the carves (`metadata_for`, de-duplicated — both splits report the same original — and **never a piece**, which is `moved_*`) so a leftover a carve then touched reports its final bounds; on undo `restored` is every `source_ids` clip at its re-merged bounds (`add_clip_shape` replaces by id, so `ClipAdded` covers a leftover shape the UI still has and one that left with its piece alike) and `split_removed` is the right-hand leftovers minus the pieces. The selection rects let the handler move the marquee with the block (`select_range_workflow`, `020-views-and-state.md`).
- **`InsertSilenceEdit` and `DeleteInRangeEdit` compose `SplitClipsEdit` rather than duplicating split logic**: `InsertSilenceEdit` holds an `Option<SplitClipsEdit>`, `DeleteInRangeEdit` an `EdgeSplits` (the pair of them), and they call `edit()`/`undo()` directly (both are `pub(in crate::core::sequencer::edit)`, which covers every submodule of `edit`, including sibling `clip_edits` files). `InsertSilenceEdit` splits any clip straddling the insertion point, then bulk-shifts every clip at/after it — **always every track**, unconditionally (see below). `DeleteInRangeEdit`'s `EdgeSplits` cuts every straddling clip at `end`, then at `start` (that order keeps the original id on the piece that still straddles `start`, so the `start` split's frozen targets stay valid) — then removes every piece left fully inside the range and re-adds them on undo (detaching each re-added clip's `Region` so a later split undo can't mutate the frozen snapshot). Both are worked examples for a compound edit that reuses an existing edit struct as an internal step instead of re-deriving its logic.
- **`DeleteTimeEdit` (`⌘/Ctrl+Delete`, "Delete Time") is `InsertSilenceEdit`'s mirror image, composing `DeleteInRangeEdit` the same way `InsertSilenceEdit` composes `SplitClipsEdit`**: it holds an `Option<DeleteInRangeEdit>` field, runs it first in `edit()` to non-rippling-carve `[start, end)` out of every track (reusing the carve verbatim rather than reimplementing "trim/split every overlapping clip, remove anything left fully interior"), then bulk-shifts every clip — pre-existing or freshly carved — with `start_tick() >= end` **left** by `end - start` (`Sequencer::shift_clips`, shared with `InsertSilenceEdit`), always every track, same alignment reasoning as `InsertSilenceEdit`. `undo()` reverses in the mirrored order: shift right first, then `delete.undo()` last — same ordering rationale as `InsertSilenceEdit::undo`'s shift-then-unsplit, so the piece the shift and the carve-undo both touch is in the right place when the carve unwinds. The one asymmetry from `InsertSilenceEdit`: since `DeleteInRangeEdit` (unlike `SplitClipsEdit`) can remove clips outright, `DeleteTimeEdit` also threads `selected_track_idx`/`selected_clip_id` through from the inner carve's `RangeDeleted`/`RangeRestored` into its own `EditResult::TimeDeleted`/`TimeUndeleted`, so `delete_time_workflow`/`restore_time_workflow` (`src/core/event_handlers/clip_range_edits.rs`) can fall back to clearing the *clip* selection exactly like `delete_in_range_workflow` does — `InsertSilenceEdit` needs no such fallback since a shifted or split-left clip always keeps its id. Separately from clip selection, `DeleteTimeEdit` stores `start` and `end` (the shift distance is derived from them) and reports `restored_selection: (start, end)` on undo — the *Arranger time selection* (the marquee) is collapsed on the forward edit (`UiEvent::TimeSelectionCleared`, sent from `edit_result_handler.rs` after a `TimeDeleted` result, since the deleted span no longer frames any real content) and restored on undo (`UiEvent::TimeSelectionSet`, same event `DuplicateTimeEdit` uses to advance the selection). `InsertSilenceEdit` never touches the marquee at all — the selection still frames real content after a shift, just moved, so there's nothing to collapse or restore.
- **Track-span scoping is a single generalized field, threaded through three edit types** (arranger marquee, `020-views-and-state.md`): `SplitClipsEdit`, `DeleteInRangeEdit`, and `MuteInRangeEdit` each hold a `track_filter: Option<(usize, usize)>` — `None` = every track, `Some((lo, hi))` = only tracks `lo..=hi` inclusive, generalizing what used to be an `Option<usize>` (single-track-or-all). `SplitClipsEdit::from_time_range_filtered` is the one choke point that gates on it; `DeleteInRangeEdit`/`MuteInRangeEdit` each delegate their two `SplitClipsEdit`s to `SplitClipsEdit::from_time_range_in_tracks` when `Some`, and gate their own interior-resolution scans (`take_interior`, the mute-target `flat_map`) the same way. Each type keeps its old single-track (`from_track_range`, `lo == hi` — still backs `PasteClipsEdit`'s per-target carve, unaffected by the marquee) and all-track (`from_time_range`) constructors, plus a new `from_track_span(track_start, track_end, ...)` for the marquee's `Some` case. `DuplicateClipsEdit` gets the equivalent `from_track_span` constructor at the clipboard layer instead: `Sequencer::copy_range_to_clipboard(tracks: (usize, usize), start, end)` (generalized from a bare `start`/`end` all-track function) is the shared primitive both `clipboard_snapshot` (all-track, `(0, tracks.len()-1)` — what `DuplicateTimeEdit::from_time_range` uses) and `DuplicateClipsEdit::from_track_span` call. `DuplicateTimeEdit` deliberately has **no** `from_track_span`, for the same reason as `InsertSilenceEdit` below: its shift half must be global, and a variant that shifted every track but pasted only the marqueed ones existed briefly and was removed as the worst of both worlds. **`InsertSilenceEdit` deliberately has no track-span constructor** — see the alignment note above and below; it is a global-timeline shift, not a "select fewer things to touch" operation like the other three, so narrowing its track set is a different, riskier operation (misaligning the marqueed tracks from the rest) rather than a mechanical generalization.
- **`DuplicateClipsEdit` history**: an earlier iteration bound it to bare `D` with a selected-clip fallback; the marquee refactor then deleted it outright and re-purposed plain `⌘/Ctrl+D` as a marquee-scoped *Duplicate Time* (global shift, scoped paste). That left both `⌘D` chords inserting time and no way to duplicate content in place, so `DuplicateClipsEdit` was brought back (2026-09-19) as the plain `⌘/Ctrl+D` operation — marquee-only this time, no selected-clip fallback, matching every other range key — and the hybrid `DuplicateTimeEdit::from_track_span`/`DuplicateTimeInRangeScoped` path was removed. The physical keypad's `DUPLC` button, which can only send a bare `D`, has no Arranger function — the hardware has no command modifier.
- **Plain `⌘/Ctrl+X`'s clip-scoped carve is `DeleteInRangeEdit::from_track_span`, not a dedicated type**: an earlier iteration had a purpose-built `DeleteInSelectedClipEdit` (composing `SplitClipsEdit::from_selected_clip` calls scoped to one known clip id) specifically so plain `⌘/Ctrl+X` could carve just the lead-selected clip without touching a sibling clip on the same track. Once the marquee gained a track dimension and plain `⌘/Ctrl+X`'s scope widened from "the lead clip" to "the marquee rectangle," that whole type became redundant — the marquee itself is now the source of truth for what's included, and `DeleteInRangeEdit::from_track_span(sequencer, rect.track_start, rect.track_end, rect.start, rect.end)` (the same constructor `Delete`/`Backspace` use) does exactly the right thing. `DeleteInSelectedClipEdit` was deleted outright (file, `mod`/`use` wiring, `sequencer_edit_dispatch!` entry, and its own tests) rather than kept around unused — if a future feature needs "carve exactly one already-known clip, ignoring siblings on its track" again, `SplitClipsEdit::from_selected_clip` (still used by `⌘E`'s bare-selected-clip fallback) is the primitive to reach for; it doesn't need reviving the old type verbatim.
- **Clip-level edit structs** (e.g. `DeleteInRangeEdit`, `SplitClipsEdit`) are hand-written with a constructor (`from_time_range()`, `from_track_span()`, …), `edit()`, and `undo()` methods. Use `ClipMetadata::from_clip(track_idx, &clip)` to build metadata from a clip reference.
- **Event edit structs** are generated by the `clip_events_edit!` macro, which wraps `ClipEventsEditState` and requires only the struct name, optional extra fields, `post_selection` mode (`keep` or `clear`), and a mutation closure. New event-level edits should use this macro. `ClipEventsEditState::edit_with`'s closure returns the post-edit selection, and its `undo` moves the snapshot back into the clip (every `edit()` takes a fresh one). **Exception**: if the post-edit selection must be IDs that only exist after the mutation runs (e.g. newly cloned events), the macro cannot express this — hand-roll the struct around `ClipEventsEditState` instead, returning the new IDs from the `edit_with` closure. `DuplicateSelectedEventsEdit` is the reference example. A second, different exception: if the edit must target an explicit event id set that may not be (and must not become) the real selection, `edit_with`'s forced `restore_event_selection` would corrupt that — hold a `ClipEventsEditState` (built by `from_selected_clip`, which allows an empty selection) but write `edit()` directly; `undo()` still delegates. `DragEventsVelocityEdit` is the reference example (⌘/Ctrl+drag velocity gesture — see `020-views-and-state.md`).
- **Continuous mouse-driven data mutations still undo as one step, via `Edit::merge`**: a drag that mutates real data on every `MouseMoved` (unlike a selection-only drag, e.g. the event marquee, which never touches undo at all) would otherwise flood the record with one entry per pixel. `sequencer_edit_dispatch!`'s generated `impl undo::Edit for SequencerEdit` hardcodes the `merge()` special cases for exactly this: `DragEventsVelocity` entries merge (`Merged::Yes`, keeping the first entry's `pre_events` and appending the later step's nudge via `DragEventsVelocityEdit::absorb` — each step is relative and clamped to the velocity range, so redo replays the steps in order rather than their sum; until 2026-09-27 the later nudges were dropped and redo restored only the first step) when they share the same `drag_id`, a counter the view hands out once per gesture (`Display.gesture.next_drag_id`) specifically so two separate drags on the same notes never coalesce. `ResizeClip` (the clip edge drag) merges the same way, except that its steps are absolute targets, so the merged edit keeps the first `before` bounds and takes the later step's `after` (`ResizeClipEdit::absorb`); keyboard `[`/`]` edits carry no id and never merge. Every other variant keeps the trait's default (`Merged::No`) — one undo step per discrete action, unchanged. Reach for this pattern, not a bypass-undo-record "commit on release" scheme, for any future continuous-drag data mutation.

## Adding a New Undoable Operation

1. **Event-level edits** (operating on selected events within a clip): add a `clip_events_edit!` invocation in `edit/event_edits.rs` specifying struct name, extra fields, `post_selection` (`keep`/`clear`), and the mutation closure.
2. **Clip-level edits**: add a hand-written struct with `from_sequencer()`, `edit()`, and `undo()` methods. Use `ClipMetadata::from_clip()` for metadata construction.
3. Register the variant in the `sequencer_edit_dispatch!` invocation.
4. Add any new `EditResult` variants needed to carry UI-event payloads.
5. In `sequencer_handler.rs`, replace the existing direct mutation with `self.record_edit(sequencer, undo_record, XxxEdit::from_...(...))` (`command_helpers.rs`): it takes the constructor's `Option` as-is — every edit type converts `Into` its `SequencerEdit` variant, generated by `sequencer_edit_dispatch!` — records it and runs `handle_edit_result`, returning whether anything was recorded.
6. Add UI side-effects either in a per-concern workflow file (`clip_lifecycle.rs`, `clip_range_edits.rs`, `selection.rs`, …) for reusable flows, or directly in `handle_edit_result` when the behavior is localized to one `EditResult` variant.
7. Extend `handle_edit_result` in `edit_result_handler.rs` to dispatch the new `EditResult` variant(s).
8. Prefer existing clip/sequencer helper methods for selection or range mapping instead of duplicating range math.

## Invariants

- **The loop region is changed only by explicit intent**: an edit must not move `region_start`/`region_end` as a side effect of clip add/remove/undo/redo. The exceptions are the deliberate ones — `set_global_region` (new/load), `DuplicateTimeEdit`'s `shift_region`, and the user's own region keys. (The old `capture_region_length` setting and its "intentional-only" rule are gone — the loop region now sizes captures directly; see `100-running-capture.md`.)
- **`ClipAdded` UI event must be sent before selecting the restored clip**: the display shape must exist before the selection highlight is applied.
- **Removal workflows send removed UI events last**: reset → selection update → send one or more removed events (`delete_in_range_workflow` and every workflow composing the same carve).
- **`EventsModified` should restore selection before UI sync**: restore `selected_event_ids` onto the mutated clip before `sync_clip_post_edit_workflow()` so rendering and follow-up UI events see consistent state.
- **The `undo` crate handles redo automatically**: there is no manual redo stack; `undo_record.redo()` replays the last undone `edit()` call.
- **Undo/redo is not persisted**: the `Record<SequencerEdit>` lives only in memory for the session. New-project and load-project flows do not need to save or restore it.
- **Track mute/solo are *not* undoable** (unlike clip mute below): they are mixer-surface controls — `SequencerCommand::ToggleTrackMute`/`ToggleTrackSolo` flip an `AtomicBool` in `SharedAtomics.track_mix` as a direct mutation, no `SequencerEdit`, no `EditResult` — sitting in the same non-undoable category as track volume/pan, `SetSelectedTrackOutput`, region length and `ToggleMetronomeMute`. Solo in particular is transient performance state. See `020-views-and-state.md` § Track Header Mute / Solo Buttons.
- **Mute edits snapshot pre-state, not toggle**: **`MuteInRangeEdit`** (the Arranger's marquee-only `M` — the only clip-mute edit; the old per-selected-clip `MuteSelectedClipsEdit` and its `EditResult::ClipsMuteStateChanged` were deleted outright) stores `mute_targets: Option<Vec<(usize, Uuid, bool)>>` and applies a uniform target derived from it (mute all if any are unmuted, unmute all if all are muted). Undo restores each clip's exact prior mute state from the snapshot; the snapshot is populated once on the first `edit()` call and preserved across redo so the `is_none()` guard skips re-snapshotting. It composes `EdgeSplits` first — exactly `DeleteInRangeEdit`'s end-then-start ordering, for the same reason (the original id lands on the left piece, so the `start`-split's construction-time targets stay valid) — and takes the snapshot *after* both splits run, so the freshly-split interior pieces are included. `edit()` re-derives the target from the frozen snapshot and applies it to the frozen target set every time (first call and redo alike); `undo()` restores each clip's exact prior flag, then un-splits `start` before `end` (LIFO), and reports every restored clip in `RangeUnmuted.updated` — including one wholly inside the range, which no split touched (until 2026-09-27 undo reported only the split originals, so such a clip stayed drawn muted). The splits are never undone by a second muting press — only a further `M` press flips the flag back — so pressing `M` twice over the same range leaves the interior split in place, unmuted.
- **`MuteSelectedEventsEdit`: per-*event* mute, the piano roll's counterpart to `MuteInRangeEdit`**: bound to `M` when `input_handler.rs`'s `handle_mute` resolves `ClipContext::ClipWithSelection` (every other context sends nothing there; the Arranger's `M` is marquee-only, `MuteClipsInRange`/`MuteInRangeEdit`, resolved in the view — see the bug note in `020-views-and-state.md`). It is `clip_events_edit!`-macro-generated (`event_edits.rs`, `post_selection = keep`) rather than hand-rolled: the toggle logic itself lives in `Clip::toggle_muted_for_selected_events` (`models/clip/edits.rs`), which reads `event_selection` directly, applies the same uniform-target rule as the clip/range variants, and sets `Event::muted` on both a selected `NoteOn` and its paired `NoteOff` together (via `pair_note_events`) so a muted note's off-edge is silenced too. Unlike the clip variants, undo doesn't snapshot a narrow `Vec<(Uuid, bool)>` — it reuses `ClipEventsEditState`'s whole-event-list clone/restore (`pre_events: Option<Vec<Event>>`), the same mechanism every other event edit in that file uses, so `edit()` recomputes the toggle target fresh from current flags every call (first and redo alike) rather than freezing it, relying on `undo()` having put the flags back exactly. Reuses `EditResult::EventsModified` rather than a new variant — the UI fan-out (redraw the clip, re-sync the event selection) is identical to every other event edit, so `050-undo-redo.md`'s own "new `EditResult` variant if the UI fan-out differs" rule says no new variant is warranted here. Playback honors the flag at the emission sites, not by filtering the event list: `Sequencer::tick` (`playback.rs`) drops any event with `is_muted()` before the track-audibility check (both the `NoteOn` and its paired `NoteOff` carry the flag, so nothing needs releasing later — unlike a muted *track*, which still emits note-offs), and `Sequencer::chase_notes` (the seek-time re-sound path) applies the same check to `chase_note_ons_at`'s results. Both `pending_note_offs`/`pending_note_ons` (staged via `Track::drain_pending`) and ordinary `Clip::tick()` events flow through the one `Sequencer::tick` check, since they're all returned through `Track::tick()`'s single `Option<Event>`.
- **`Track::pending_note_offs` prevents stuck notes on mute — and, since the non-destructive edits below existed, at any clip's own natural region end too**: `tick()` releases the *current* clip's still-open notes into this buffer before every `needs_reseek`-triggered `seek()` away from it — not just when that clip was just muted. `clip.pending_note_offs()` collects any NoteOn whose paired NoteOff has not yet been emitted (`on_idx < current_event_idx && off_idx >= current_event_idx`); `Track::tick` calls it from two sites: the top-of-function `needs_reseek` block (mute/removal, *and* the common case where another clip has started covering `current_tick` because the current one's own region just ended exactly there — e.g. the two halves of a split are directly adjacent, so `needs_reseek`'s "another clip now covers the position" term catches the crossing before the branch below ever sees it) and the inner `else` branch (`current_tick >= clip.end_tick()` with nothing else covering the position — a genuine gap, or nothing left). Both matter: a non-destructive split/carve/resize (`split.rs`) shares the *full* original event list between pieces and only narrows the region window, so a note whose `NoteOn` played but whose stored `NoteOff` lies past the region end is invisible to `clip.tick()`'s own sequential stepping — without this release it would hang forever, not just until the edit. The buffer is drained one event per `tick()` call before normal playback logic runs. Every edit that can remove, shrink, or shift a *currently-sounding* clip out from under a note additionally reuses the same buffer proactively via `Track::release_sounding_notes_for_clip(clip_id)` (a clip-scoped variant of `release_sounding_notes`) *before* mutating anything — `DeleteInRangeEdit::take_interior` (removal), `SplitClipsEdit` (the shrink of the original clip's region end, both directions and on redo), `InsertSilenceEdit`/`DeleteTimeEdit` (the forward/backward shift), and `PasteClipsEdit::undo` (dropping a pasted clip) — so the note-off travels out through `tick()` like any other event, clearing whichever safety net the track's output routes through (the MIDI-out `NoteLogger` or the CLAP `instrument_notes`; see `130-plugin-host.md` § Stuck-note safety). That proactive path is gated on `sequencer.is_running()` (only a *currently sounding* note needs releasing at edit time); the natural-boundary release in `tick()` has no such gate — it's just ordinary playback. This replaced a project-wide `NoteLogger` `ReleaseNotes` command the edit *workflows* (`EventHandlers`) used to fire on every clip edit — which released every sounding note on every track, not just the one being edited (a clip delete on one track could cut a held chord on an unrelated one). Workflows now rely entirely on the edit's own clip-scoped release; see `160-midi-out-offset.md` for the command's remaining legitimate uses (transport stop / seek).
- **`Track::pending_note_ons` is the counterpart: it chases a note back in when playback arrives at a clip whose content has one already "in flight"** — the other half of the same non-destructive-sharing bug the note above fixes. Splitting a clip mid-note leaves the *right* half's stored `NoteOn` sitting before its own region start (still there — non-destructive), so `clip.tick()`'s sequential stepping never reaches it; without chasing, the split silently drops the tail half of the note instead of continuing it. `Clip::chased_note_ons_at(tick)` (already used by `Sequencer::chase_notes` for an explicit user seek — `playback.rs`) finds every NoteOn with `on_tick < target && off_tick >= target`, so an ordinarily-recorded clip's own legitimate opening note (`on_tick == target`) is never mistaken for one. `Track::tick` calls it from **one** site — the "Play clip" branch, gated on `current_tick == clip.start_tick()` — which covers every way of arriving at a clip's start: the adjacent case (`needs_reseek`'s `seek()` lands on the new clip's start and the branch runs on that same call), the gap case (`current_tick` catches up to the next clip's start on a later tick), and an explicit seek onto the start (play-from-cursor parked on the right half, a loop wrap to a region starting there). **Exactly once per arrival**: `tick()` is called repeatedly at one position (once per event it emits — `current_tick` only advances once `clip.tick()` returns `None`), so the gate alone re-fires on every call while an event sits exactly on the cut; `Track::chased_start_tick` records the tick already chased and `seek()` clears it. **`Sequencer::chase_notes` (the explicit-seek chase, `playback.rs`) deliberately skips a clip when `playback_tick == clip.start_tick()`** — that instant is `Track::tick`'s, and chasing from both sounded the straddling note twice for one `NoteOff` (a stuck voice when starting playback from the right half; the first-half start only ever went through `Track::tick`). Ordering: whatever was staged on the arriving call — the left half's release, then the chased note-ons — drains *before* the new clip's own events at that tick (`Track::drain_pending`, also the top-of-`tick()` drain), so a split boundary plays as `NoteOff` (left, released) → `NoteOn` (right, chased) → the right half's own events on the cut, then the *original* stored `NoteOff` fires later at its own unchanged absolute tick via the normal `Clip::seek`-primed `elapsed_delta_ticks` math (phase-locked, so no extra tracking is needed for that half). No stored event is ever mutated to produce this — chasing is playback-time synthesis only, so the "drag an edge back out to reveal hidden content" invariant (`split.rs`, `020-views-and-state.md`) stays intact.
- **`Track::awaiting_start_tick` re-seeks a *waiting* clip whose start moved under a running transport**: when `Track::seek` lands in the gap before a clip (a loop wrap onto a region that starts before the clip, a play-from-cursor there), it parks that clip's delta-driven walk at its start (`clip.seek(clip.start_tick())`) and records that tick. The parked walk is right only if playback reaches exactly that tick — but a header-band edge trim or a clip move can change `start_tick` while the playhead is still in the gap, and nothing in `needs_reseek`'s other terms notices (the clip is already `current_clip_idx`). Dragging the left edge back *behind* the playhead (the running-capture "reveal the pre-roll" gesture, `100-running-capture.md`) then fell straight into the "Play clip" branch with the old start's priming: every event of that wrap sounded early by the drag distance and the revealed notes between playhead and old start were skipped, until the next wrap's `seek` put it right — reported 2026-09-19. Trimming *forward* while waiting had the same fault (arrival at the new start played the old start's events). `tick()` therefore adds a `needs_reseek` term — while waiting, the current clip's `start_tick() != awaiting_start_tick` — and the ordinary `seek(current_tick)` either lands inside the moved clip (correct position, `awaiting` cleared) or re-parks at the new start. Cleared the moment playback is *inside* the clip, because there the walk advances on its own and an edge trim must **not** re-seek: `Clip::seek`'s lower-bound lookup would re-emit an event sitting exactly at the playhead. **The inside case has one exception, and it was the actual bug**: a real drag's target is the snapped pointer position, so its first move events can trim the left edge *forward past the playhead* before the drag heads backwards. `tick()` then sits in "wait for clip to start" — `clip.tick()` is never called, so the note sounding at that moment never gets its `NoteOff` (**stuck note**), and the walk is frozen mid-clip; dragging the edge back behind the playhead resumed it from there — **out of phase for the rest of the wrap**, corrected by the next wrap's `seek`. The same term covers it: `awaiting_start_tick == None` with `current_tick < start_tick()` is "the start moved past us", so the `needs_reseek` block releases the clip's sounding notes into `pending_note_offs` (drained on the next `tick()` call, the same one-tick latency as a mute) and re-parks it at the new start. Regression tests beside `release_sounding_notes_for_clip_…` in `track.rs`: start moved behind the playhead while waiting, start moved ahead while waiting, start trimmed past the playhead while inside (release + phase), and no re-seek for a trim that stays behind the playhead; plus `left_edge_drag_during_playback_keeps_phase_and_releases_notes` in `capture.rs`, which drives a real running-capture clip through `Sequencer::tick` across two wraps and the overshoot-then-back gesture, asserting on the MIDI actually emitted.
- **Unmute triggers re-seek via playback position check**: `tick()` also re-seeks when any unmuted clip spans `current_tick` but is not the clip currently being tracked — catching the case where a clip was muted (causing a seek to the next clip) and then unmuted before `current_tick` has advanced past it.
- **Bounds derived from transient view state must be frozen at construction, not re-read on redo**: `SplitClipsEdit`/`InsertSilenceEdit`/`DeleteInRangeEdit`/`DeleteTimeEdit`/`MuteInRangeEdit` store their bounds (`split_tick` on the first, `start`/`end` — and, where relevant, `track_filter` — on the rest) as struct fields, set once at construction (`from_time_range()`/`from_track_span()`/…), rather than re-reading them inside `edit()`. Their bounds can come from the Arranger marquee (`Display.gesture.time_selection: Option<TimeSelectionRect>`), which is view-local and may no longer exist by the time of a later redo — unlike the loop region these edits used to read from, which is persistent `Sequencer` state and would have been safe to re-read. `DuplicateClipsEdit` resolves the marquee the same way, one step earlier: `from_track_span()` builds the throwaway (track-filtered) clipboard and the composed `PasteClipsEdit` (whose `targets` are frozen positioned clips) at construction, and freezes the full `TimeSelectionRect` so `new_selection`/`restored_selection` are computed from it, never from the view. `DuplicateTimeEdit` likewise freezes `start`/`end` plus both composed sub-edits at construction; the advanced selection it emits (`new_selection`) is a pure function of those frozen bounds, computed in `edit()` but never re-derived from `Display.gesture.time_selection` — and since `DuplicateTimeEdit` itself carries no track-span state, the view-side `UiEvent::TimeSelectionSet` handler is the one place that *does* reach back into the live `Display.gesture.time_selection` to recover a track range to re-attach (see `020-views-and-state.md` § "Duplicate Time").
- **`Track::fits(&clip)` is the overlap test `Track::add_clip` gates on, exposed on its own** so an edit's constructor can know its later `add_clip` will succeed and return `None` instead of entering the record as a no-op (`CommitClipEdit::from_running_capture` via `build_committed_capture_clip`). Reach for it before adding a constructor that might build an un-placeable clip.
- **`Region`'s `Clone` shares its atomics, not just its values**: `Region { start: Arc<AtomicI32>, end: Arc<AtomicI32> }` derives `Clone`, which clones the `Arc`s themselves — the clone and the original keep pointing at the *same* atomics. Fatal for anything that clones a `Clip` and then means for the two regions to diverge independently, like `SplitClipsEdit` (the two halves' regions must differ) or `detached_clone` (a pasted/duplicated clip's region must not track the source it was copied from): mutating one's region silently mutates the other's too until you replace it. Break the sharing with `*clip.region_mut() = Region::new(start, end)` (constructs fresh atomics) rather than `clip.region_mut().set_region(...)` (mutates the shared ones) whenever a cloned clip's region needs to end up different from its source's — `clip_edits::detached_clone` (in `clip_edits/mod.rs`, shared by `SplitClipsEdit`, `PasteClipsEdit`, `DeleteInRangeEdit` and `CommitClipEdit`) is exactly that for a whole-clip snapshot, and `detach` the same for a clip already owned (just lifted), without copying its events.
