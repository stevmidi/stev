# Recent Projects

**Archived 2026-10-28. Status: built 2026-10-28. Issue: #1.** The as-built behaviour lives in `020` § Views (the category, its rows, the initial selection), `030` § Browser Panel (the folder suffix) and `060` (`list_recent_projects`, decision 9's finding: the copy is written anew, so it heads the list at once); this file is the design and its rationale, not maintained. **Changed after hand-testing (2026-10-28):** decision 2 became ten projects; decision 5 was dropped, the rows show the name alone (the right-aligned folder ran into long names in a narrow panel, and the ambiguity is acceptable); decision 7's delete was dropped. Then decision 1 was reversed: the list is most recently **opened or saved**, the usual "Open Recent" order, kept in `SettingsData::recent_projects` and pruned of files that are gone, which made the more useful delete possible: Delete on a Recent row takes it off the list, the file untouched, with no confirm. Decision 9 no longer applies (a Finder file counts when it loads). A RECENT category at the top of the browser lists the five projects saved most recently, from every project folder and the projects root, so the project you are working on is one ⌘O ↓ Enter away wherever it lives. The list is worked out from the files on disk every time the tree is read. Nothing is stored. Read the browser's part of `020` § Views, `030` § Browser Panel and `060`'s on-disk layout first.

## Decisions (2026-10-28)

1. **Recent means most recently saved, not most recently opened.** The list is the `.stev` files under `paths::project_dir()` (every project folder plus the loose projects at the root) with the newest modified times, newest first. Equal times sort by name. No opened-at list is kept in `SettingsData`, so nothing can go stale: a project renamed, deleted or moved, in the browser or in Finder, is shown as it is now on the next reload, which already happens on every show, after a save, a delete and a rename (`BrowserTree::reload`, `UiEvent::ProjectFilesChanged`). The cost is that a project opened only to listen to, and never saved, doesn't come up the list. That is on purpose: the list is meant to show work in progress. If it feels wrong in use, switching to an opened-at list in `SettingsData` is the fallback, and then it needs pruning for files that are gone.
2. **Five projects, fixed.** `config::RECENT_PROJECTS_MAX = 5`, with no setting. That's enough for the projects in progress, and short enough not to push the other categories down. Fewer projects on disk list fewer.
3. **Projects only.** Templates (`Templates/`), clips (`Projects/Clips/`) and audio exports never appear. They are not projects in progress, and the listing can't reach them anyway: the clips folder is left out by `is_project_folder_name`, and templates and exports sit outside `project_dir()`.
4. **The category comes first and starts expanded.** The order becomes RECENT, PROJECTS, TEMPLATES, CLIPS, PLUGINS. At launch every folder is collapsed (`dcfe705`) and Plugins too (`7d671e2`), but Recent is open: it's the one category you want at launch. It collapses and expands like the others (Left/Right, Enter, the triangle), and that state is not persisted, also like the others. It is listed even when empty, as Templates and Clips are, so a new user sees where recent work will show up.
5. **Each row shows its folder as a dim suffix**, drawn as the Plugins category draws a plugin's format: the project name in `fg`, then the folder name in `fg_dim`. A loose project at the projects root has no suffix. Two folders can hold projects with the same name, and the suffix tells them apart. It is always shown, not only when names clash, so a row never changes shape depending on what else is listed. Like any row, it is clipped at the panel's width.
6. **A recent row is its own row, not the project row repeated.** It is a new `BrowserItem::Recent { folder, name }`, not `BrowserItem::Project`. The same project usually appears twice, under RECENT and under its folder, and the selection, `selected_index`, the armed delete and the rename field all identify a row by its item. With the same item twice, they would always find the first copy. Its `parent()` is the Recent category, so Left goes there, not to the project's folder.
7. **A recent row acts like a project row.** Enter or a double-click opens it (`InputEvent::ConfirmOpenProject` → `LoadProject`, the unsaved-changes check first, then `ProjectLoaded` gives the keyboard to the arranger). ⌘R renames it and Delete/Backspace then Enter deletes it to the Trash, through the same `project::rename_project` / `delete_project` calls with its `folder` and `name`, and the same footer messages. The open project gets the region-coloured marker in both places. A rename keeps the file's modified time (a rename on the same volume doesn't change it), so the renamed row stays where it was in the list and stays selected. A delete reloads the tree, and the selection hands over as it does after any delete. There's no drag out of the panel: projects have none today.
8. **The first show selects the top recent row when no saved project is open.** With an untitled project, which is how the app starts, `select_initial` selects the first Recent row rather than the current folder. Launch, ⌘O, Enter then reopens the latest work. With a saved project open, the selection is its Recent row if it is listed there, so no folder needs expanding. Otherwise it falls back to today's rule: its row under its folder, with the folder expanded. An empty Recent falls back to today's rule as well.
9. **A project opened from Finder counts by its file's time.** Opening an outside `.stev` from Finder copies it into the projects (`060` § Opening from Finder). Whether the copy keeps the original's modified time decides whether it shows up in Recent before its first save. Either way is acceptable under decision 1. Check what `fs::copy` does on macOS while building, and note it in `060`.
10. **Out of scope:** the macOS Dock menu and Finder recents (`NSDocumentController noteNewRecentDocumentURL:`, a possible follow-up), a File ▸ Open Recent menu (the app menu holds only About and settings, `archive/330`), clearing the list (it is derived: saving something else is the only way to push a project out), and pinning a project to the list.

## Build

One phase, one branch and one merge, with tests, docs and a changelog line in the same change. No new `Action` and no keymap row: every key involved is a browser key that already exists.

- **Storage** (`core/project/storage.rs`): `list_recent_projects(limit) -> Vec<(Option<String>, String)>` gathers `(folder, name, modified)` from each project folder (`list_project_folders`) and the root, using the modified times `list_stev_names` already reads. It sorts newest first, breaking ties by folder and then name, and takes `limit`. The sort and limit go in a pure helper over the gathered entries, so tests can cover them without the file system.
- **Tree** (`view/display/browser.rs`): `BrowserCategory::Recent` (label `RECENT`, no `plus_action`) listed first, `DiskListing::recent`, `BrowserItem::Recent`, its row drawn with the folder suffix (`rendering/browser.rs`), and the renamable and deletable item lists and `select_initial` extended (decisions 6–8). Anything that matches every `BrowserItem` variant (open, rename, delete, the open-project marker) handles `Recent` the way it handles `Project`.
- **Tests**:
  - Storage: the helper orders by time across folders and the root, breaks ties by name, caps at the limit, and leaves out the clips folder and dotfiles.
  - Tree: Recent is first and expanded on a fresh tree. A project listed both in Recent and under its folder can be selected in either row without the other being selected. Left on a recent row selects the Recent category. Delete-then-Enter on a recent row arms that row only. `select_initial` with no open project selects the first recent row, and with an open project in Recent selects that row and leaves its folder collapsed. An empty Recent falls back as before.
- **Docs**: `020` § Views (five categories, the Recent row, the initial selection), `030` § Browser Panel (the suffix), `060` (on-disk layout: `list_recent_projects`, and decision 9's finding). `CHANGELOG.md` under `[Unreleased]`. Once built, this file is archived to `docs/archive/350-recent-projects.md` with its as-built behaviour living in those three.
