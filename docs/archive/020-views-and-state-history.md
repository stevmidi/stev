# ViewState Transitions

There are two primary editing surfaces plus several modal states.

## Views

- **`Arranger`** — default view; clips are arranged on the timeline.
- **`Clip`** — entered when the user selects a clip in Arranger and presses SHIFT+TAB (moved off bare ENTER, which is now spare in `Arranger`/`Clip` — it briefly carried the transport "Start", which moved to `⌥Space`, see `010`); `Clip` shows and captures events, and edits whichever notes are selected. **Having notes selected is not a view of its own** (there used to be a `ClipEdit` view for it, collapsed 2026-09-24): the selection lives in the model (`Clip::event_selection`, on the `"sequencer"` thread), and `EventHandlers::publish_event_selection` (`selection.rs`) mirrors whether it is non-empty into `SharedAtomics::has_event_selection`, which the UI thread's key routing reads — `input_handler.rs` splits `ViewState::Clip` into `ClipContext::Clip` / `ClipContext::ClipWithSelection` by it, and `Display::forward_input_event` reads it to leave plain `←`/`→` to the handler (note nudge) when notes are selected. It is published from exactly the places where selection membership can change: `select_clip_event_workflow` (click), `select_all_events_workflow` (`⌘/Ctrl+A`), `select_events_in_rect_workflow` (marquee drag, see Event Marquee Selection), `clear_event_selection_workflow` (ESC, a click on empty grid, and leaving the clip all go through it), and the `EventsModified` arm of `handle_edit_result` (the only `EditResult` variant carrying a selection — delete/duplicate, the capture insert, and their undo/redo). Not a blanket call after every command. **Committing a capture never changes the selection** (`InsertCaptureEdit`; fixed 2026-09-24 in its predecessor `commit_events_to_clip`): whatever was selected before stays selected, and nothing new is selected — not even the committed notes. The clip-view commit used to select the note at the clip cursor whenever the cursor fell inside the inserted span, without publishing it: invisible with nothing selected, and with notes selected it silently swapped them for that one note. `capture.rs` has the regression tests. **The clip view is a view of the lead clip, not a transport context** (since 2026-09-24, phase 2 of `archive/210-docked-clip-panel.md`): entering and leaving touch neither the loop region nor the cursor. The clip cursor is separate from the transport (arranger) cursor, mirrored one way (since 2026-09-25): the lead clip's own cursor is reset from it on every arranger cursor move (`EventHandlers::change_lead_clip` / `sync_clip_selection_to_cursor_workflow` / `select_clip_span_workflow` run `sync_selected_clip_cursor_with_arranger`), but clip-view cursor moves (`set_clip_cursor_workflow`) stay in the clip. `Space` plays from the arranger cursor and `⌥Space` from the clip cursor (`010`, `210`). The *lead clip* is the clip under the cursor on the selected track (`select_clip_workflow` / `clear_clip_selection_workflow`). Whenever it changes, `change_lead_clip` first drops the old lead's event selection, republishing the mirror (it used to go stale), then sends `UiEvent::LeadClipChanged { clip_view: Option<ClipView> }`. The Display keeps the transport's cursor/region/playhead atomics and, separately, the lead clip's (`Display::lead_clip_time`, taken from every `ClipView` it receives). The clip pane reads the latter through the pane-aware `cursor_tick_atomic` & co. Its playhead is the transport playhead mapped into the clip (`lead_clip_playback_tick`, pure `pane::clip_event_tick_at`), and it is hidden while playback is outside the clip, because the clip's own playback counter stalls then. A capture into the lead clip is one undoable `InsertCaptureEdit` from either view, running or stopped (`100-running-capture.md`, `050-undo-redo.md`). `⌥=`/`⌥-` (stretch the clip) no longer moves the loop region either. ENTER is spare. **`Clip` vs `Arranger` is the keyboard focus; the clip panel is layout** (phase 3 of `archive/210-docked-clip-panel.md`): the clip view is a panel that is shown maximized (the whole lane area) or docked below the arranger (`Display.render.clip_panel`, `⌘⌥E` — see `010`). `ClipEntered` shows it, and `ClipExited` hides it. Docked, both panes are live. A click in the pane without the keyboard focuses it first (`focus_pane_workflow`: into the clip view, Grid cursor mode with the clip cursor left alone; back to the arranger, the event selection dropped), and a click's `MouseClickedTicks` carries the pane it landed in (`pane`), so it never depends on that focus having reached the sequencer. SHIFT+TAB toggles both directions from a single `input_handler.rs::handle_shift_tab` match on `ClipContext`: from `Arranger` it sends `EnterClip`; from `Clip` it returns to `Arranger` (`exit_clip_workflow`, which also clears any event selection so a later re-entry starts clean). It replaced SHIFT+ENTER, which is unbound everywhere now. `ViewState::is_clip_view()` returns true for `Clip` and `PendingClip`.
- **`PendingClip`** — **deleted 2026-09-26** (phase 5 of `220-capture-without-pending-view.md`). It was the modal view where a stopped `/` opened the detected phrase for adjusting before a confirm. The stopped `/` now commits directly: a new clip (`CommitClipEdit::from_stopped_capture`) or, with a lead clip, an insert (`InsertCaptureEdit::from_stopped_capture`), both framed by phrase detection (`040-phrase-detection.md`). Adjusting the detected phrase after the commit is a known gap, to be scoped separately. `ViewState`'s discriminants were renumbered to stay contiguous (session state, never persisted).
- **`Project`** — two-pane folder/file browser modal entered only via ⌘/Ctrl+O in Arranger (F4 is unassigned/spare). Left pane lists project folders (`project::list_project_folders()`, alphabetical); right pane lists that folder's `.mseq` files (`list_projects_in`, modified-date descending). `Display.project.project_modal_focus: ProjectModalFocus` (`Folders`/`Files`) tracks which pane arrow keys act on, defaulting to `Files` on entry (⌘/Ctrl+O most often means "open a project," not "browse folders"); `Tab`/`F3`/`Left`/`Right` swap it, mirroring the `MidiSettings` focus-swap convention below. The Files-pane row that was highlighted (`Display.project.project_selection`) is remembered across close/reopen: `UiEvent::EnterProject` restores it by filename (`restore_project_selection`) after the folder's file list is refetched, falling back to the top of the list only when that project is gone. Moving the folder selection live-refreshes the Files pane and the link status line — it does not by itself commit anything. ENTER on the Folders pane commits the highlighted folder as `Display.project.project_current_folder` (persisting `SettingsData.last_project_folder`) and swaps focus to Files; ENTER on the Files pane opens the highlighted file (or confirms a pending delete). DEL (`Key::Delete`/`Key::Backspace`) on the Files pane arms a "delete selected" confirm needing a second ENTER; ESC cancels a pending confirm, or closes the modal otherwise. Save and New no longer live in this modal at all — ⌘/Ctrl+S saves the current project (existing name, or auto-named `<folder>_ddmmyy_NN` when unnamed — see `060-persistence.md`) instantly from anywhere without opening any modal, ⌘/Ctrl+⇧+S ("Save As") always auto-names a fresh copy the same way and adopts it as the current project, and ⌘/Ctrl+N creates a new project instantly, also from anywhere, with no confirm and no modal. `Display.project` tracks `project_current_name: Option<String>` and `project_delete_confirm: Option<String>` (the filename pending delete-confirmation). `project_current_name` is set exclusively from `UiEvent::ProjectLoaded { clips, filename }`'s `filename` field — `Some(name)` after `load_project_workflow` opens an existing file, `None` after `create_project_workflow` creates a fresh one (it is `load_project_workflow` over `ProjectData::default()`) — never optimistically by the key handler that triggers the load/create. This is deliberate: a subsequent ⌘/Ctrl+S must auto-name a freshly created project rather than silently overwriting whatever was open before it, so the reset has to happen on the actual transition, not on the keypress that requested it.
- **⌘/Ctrl+I edits the external-app link for the highlighted folder**, from either pane. It opens a paste-only text field (`Display.project.project_link_edit: Option<String>`) that intercepts input ahead of the normal Project-modal arms while open: `PastedText` (from `egui::Event::Paste`, the app's only text-input path so far) replaces the buffer, `Backspace`/`Delete` clears it, ENTER saves (`InputEvent::ConfirmProjectLink` → `SequencerCommand::SaveProjectLink` → the folder's `.midiseq-link.json` sidecar) and closes the field, ESC cancels without saving. There is no character-by-character typing/caret-positioning support — see `060-persistence.md` for the storage format and why opening a linked project launches the external app.
- **`MidiSettings`** — modal view entered via F2 in Arranger. Enter applies the currently selected IN/OUT ports immediately (sends on `Display.midi`'s `midi_in_reconnect_tx` / `midi_out_reconnect_tx` to the `"midiwatcher"`, which makes it the wanted port; updates its `midi_in_current_port` / `midi_out_current_port`). The modal stays open after Apply so the user can see the active indicator update. ESC closes it and returns to `Arranger`. The port lists refresh live from `UiEvent::MidiPortsRefreshed` (pushed by `"midiwatcher"` when its 2 s poll sees the lists change). Active devices are indicated by a green left-bar + green text; a configured device that is not currently plugged in appears as a dimmed ghost row (`○ name (not connected)`).
- **`Track`** — modal view entered via F1 in Arranger, operating on the selected track. Entered via `enter_track_workflow` (sets `ViewState::Track`, emits `UiEvent::EnterTrack { channel, instrument }`). ESC cancels without applying.
  - **Non-macOS**: `LEFT/RIGHT` adjusts the MIDI channel (0–15); ENTER sends `InputEvent::ConfirmTrackOutput { channel }`. Display state: `track_modal_channel: u8`.
  - **macOS**: two rows — an **Output** selector (`MIDI Out` ↔ `Instrument`) and a detail row (channel spinner, or a scrolling instrument-plugin list). `TAB`/`F3` moves focus between the rows (this in-modal `F3` is unrelated to the Arranger-level `F3` that opens the Themes modal below — it only fires while already inside `Track`, mirroring the `Project`/`MidiSettings` focus-swap convention); `LEFT/RIGHT` switches output kind or channel; `UP/DOWN` moves the plugin selection. ENTER applies and closes: `MIDI Out` → `ConfirmTrackOutput`; `Instrument` → `Display::load_track_instrument` (loads the plugin, opens its editor, then `ConfirmTrackInstrument` routes clips + persistence). Extra Display state (`#[cfg(target_os = "macos")]`): `track_modal_kind: TrackModalKind`, `track_modal_focus: TrackModalFocus`, `track_modal_plugin_sel: usize`. Handled in `Display::handle_track_modal_key` (`view/display/instrument.rs`). See `130-plugin-host.md`.
- **`Themes`** — modal view entered via F3 in Arranger (`EventHandlers::enter_themes_workflow`, a direct `set_view_state(ViewState::Themes)` with no `UiEvent` round-trip — the theme list and current selection are already view-local state in `view::theme`, unlike MIDI ports/track config which live in core). A single scrollable list of every palette in `view::theme::palettes::THEMES`, drawn by `draw_themes_view`. There is no separate cursor/selection state distinct from the live theme: `UP`/`DOWN` call `theme::cycle_theme(-1/1)` (wraps at both ends) and the next frame repaints in the new palette — shapes hold no colour of their own, `ClipShape`/`EventShape::color()` read the active theme at paint time — so the highlighted row *is* the active theme at all times. ENTER persists `theme::active_theme_index()` into `SettingsData.theme_index` (`core::settings::save_settings`) as the app's default for next launch — applied at startup via `theme::set_active_theme(settings.theme_index)` in `main.rs`, right after `load_settings()`. The modal stays open after ENTER (same convention as `MidiSettings`); ESC closes it and returns to `Arranger`. `Display.default_theme_index: usize` mirrors the persisted value (threaded through `setup_display`/`Display::new` at startup, updated in the ENTER handler alongside the settings write) so `draw_themes_view` can flag which row is the saved default with a right-aligned "DEFAULT" tag — distinct from the active-row accent highlight/left-bar, since browsing can leave the highlighted (live) theme different from the persisted default until ENTER is pressed again.
- **ESC is the universal "never mind" key**: every modal (`Project`, `MidiSettings`, `Track`, `Themes`) closes on ESC, dispatched by a single unconditional arm in `Display::handle_modal_input_event` that runs after the Project-specific ESC arm (which additionally cancels a pending delete-confirm before closing) — the same role ESC plays clearing an event selection in `Clip`. SHIFT+ENTER no longer closes any modal — that convention was replaced entirely rather than kept as a redundant alternate binding, and SHIFT+ENTER is now unbound application-wide (the `Clip` exit moved to SHIFT+TAB, and the Track modal's ENTER no longer excludes shift). SHIFT+TAB inside a modal is just TAB (focus swap), since modals consume input before the view-level bindings.

## Mouse-Driven Cursor Placement

- **Supported in `Arranger` and `Clip`** — not in modal views. `Display::cursor_grid_ticks()` returns the snap resolution per view (`None` disables the feature for that view): `Arranger` → the zoom-adaptive snap, the finest *visible* grid tier (`GridTiers::snap_ticks`, `view/display/grid.rs` — a beat at the default zoom, down to a 16th zoomed in, whole bars zoomed out; see `030-ui-design.md` § Arranger Navigation), `Clip` → the same zoom-adaptive snap on the piano-roll surface (`GridSurface::PianoRoll` — a 16th at typical clip lengths, an 8th on a long clip fitted to the width, never finer than a 16th zoomed in; `archive/200-clip-view-zoom.md` phase 2). The plain arrow keys step the cursor at this same resolution: in the arranger `forward_input_event` resolves the step view-side (the zoom is view-local) into `InputEvent::MoveCursorByGrid { step_ticks }` → `TransportCommand::MoveCursor`, and in `Clip` likewise into `MoveCursorByGrid` → `SequencerCommand::NudgeClipCursorByGrid { step_ticks }` → `Sequencer::grid_snapped_selected_clip_cursor_tick`, which walks one boundary via `core::time::step_to_grid` (with notes selected the plain arrows nudge them instead — a fixed 64th, not the grid) — either way one `cursor_grid_ticks()` boundary per press, so a key press advances exactly as far as the mouse's nearest-grid-line snap. The mouse still differs in kind, not resolution: it lands on whichever grid line is nearest the pointer (`core::time::snap_to_grid`) rather than always stepping forward/back by one.
- **The cursor line is always present; the mouse and the arrows both move it**: `draw_cursor_line` (`overlays.rs`) draws a dim full-height line in every timeline view — `cursor_line_color()` / `CURSOR_LINE_W`, a neutral `theme::fg()` tone (~0.45 brightness) at 0.75px, kept quiet because the timeline's play triangle carries the emphasis. It reads as "the cursor, if you click here". Its position:
  - **Mouse**: `InputEvent::MouseMoved` over the lanes sets `Display.gesture.hover_cursor` — the tick and the pane it was measured in (view-local, snapped via `Display::snapped_tick_at`) and never touches the committed transport/clip cursor — the line detaches to follow the pointer.
  - **Keyboard / default**: `hover_cursor` is `None` and the line falls back to `render_cursor_tick()`, so it sits on the committed cursor. `forward_input_event` clears the field on the keys that navigate the committed cursor (`←` `→` `↑` `↓`) so keyboard navigation visibly drags the line along instead of stranding it at a stale hover tick. Other keys (transport start, mute, undo…) leave it wherever it is.
  - It re-detaches on the next `MouseMoved` over the grid, not before (a stationary hover won't re-fire).
  - **Pinned during a time-selection drag**: `Display::update_hover_cursor_tick` (`gestures.rs`) no-ops while `gesture.time_selection_anchor.is_some()`, mirroring the same-shaped guard on `update_clip_resize_hover`/`update_track_mix_hover`. Without it the line would slide along with the pointer for the whole drag, duplicating the selection's own moving edge; pinned at the press tick, it reads as the insert marker the drag is anchored to (see "Press keeps its existing meaning" below) while the range arrows alone show the live range.
  - `draw_cursor_line` draws exactly one line in every view. (The retired `PendingClip` view drew two: the placed cursor and the hover.)
- **Click commits the snapped position**: `InputEvent::MouseClicked` is snapped and forwarded as `InputEvent::MouseClickedTicks`. `ViewState::Arranger` sends `TransportCommand::SetCursorAndSelectClip`; `Clip` send `SequencerCommand::CommitClipClickByTicks` (same path used by keyboard cursor placement) *and* `SequencerCommand::SelectClipEvent` with whatever event (if any) the click hit — cursor placement and event selection are independent effects of the same click. `PendingClip` only gets the former; event hit-testing never runs there.
- **No modifier-key behavior for cursor placement itself.** The two modifier-gated mouse gestures in the codebase are both distinct gestures checked *before* the cursor/selection click logic runs, not modifiers on it: the ⌘/Ctrl+drag velocity edit in `Clip` ("Velocity Drag" below), and the Arranger Shift+click marquee extension ("`SHIFT+click`" under "Arranger Time Selection" below) — which deliberately does *not* place the cursor, since the cursor is the anchor it extends from.
- `TransportCommand::SetCursorAndSelectClip` and `TransportCommand::MoveCursor` share clip re-selection logic via `EventHandlers::sync_clip_selection_to_cursor_workflow` — extend that helper rather than duplicating the clip-resync block if a third cursor-setting path is added.

## Arranger Time Selection — the Marquee

- **Arranger only, gesture starts in the clip lanes**: press-drag-release inside the clip area defines a 2D marquee — a tick range *and* a track range. The timeline strip itself stays inert for mouse input; it is where the tick range is *rendered* (as the two inward-pointing arrow glyphs), not where it is grabbed. Unlike the clip-edit event marquee, no separate rectangle is drawn — the arranger already tints selected content (clip-body sub-rects + gap fills, see "Visual" below), so the marquee's track range simply narrows which tracks that tint covers.
- **View-local state, never shared or undoable**: `Display.gesture.time_selection: Option<TimeSelectionRect>` (`core::input_event::TimeSelectionRect { start, end, track_start, track_end }`) holds the normalized tick range × inclusive track range. `Display.gesture.time_selection_anchor: Option<(i32, usize)>` holds the drag anchor `(tick, track)` — `Some` only while the primary button is held, so it doubles as the drag-active flag rather than a separate `bool`. No `SharedAtomics` entry, no `SequencerEdit`: a selection is not a data mutation (see `050-undo-redo.md`).
- **Snapping reuses the cursor grid; the track anchor reuses `track_idx_at`**: the tick anchor and moving edge go through `core::time::snap_to_grid` with `Display::cursor_grid_ticks()` (the zoom-adaptive snap in `Arranger`); the track anchor and live track resolve via `Display::track_idx_at(y)`. A press landing on the performance-lane row (above the track lanes, where `track_idx_at` returns `None`) clamps to track 0 for the *anchor* — mirroring `track_idx_at`'s own bottom-edge clamp; the *live* track during a drag instead falls back to whatever the anchor already was, so briefly dragging back up over the timeline/performance-lane row mid-gesture doesn't snap the span down to track 0.
- **The collapsed state is the cursor, and is never stored**: `time_selection` is `Some` only while a real drag has moved off *both* anchors — a collapsed pair is not a representable state. `draw_time_selection` derives the collapsed right-pointing play-triangle glyph from `render_cursor_tick()` instead, so it tracks every cursor move (arrow keys, viewport paging, clicks) with no syncing at all, and stays in step with the cursor line drawn in the grid. Do not reintroduce a stored `(tick, tick)` collapsed pair: that is what made ⌘L keyboard-vs-mouse behavior diverge, because only the mouse path re-anchored it. The same collapsed triangle is drawn in `Clip` (`draw_time_selection`'s view guard admits them) — those views never hold a `time_selection`, so they only ever hit this branch, and the cursor there is likewise the playback start position. Collapsing requires returning to **both** the tick and track anchor: a drag that changes only the track row (`tick_x == anchor_tick`, `track_idx != anchor_track`) stays `Some`, with `start == end` — a real, zero-tick-width selection rather than a collapse. This is the one way to select "these tracks, at this instant" without also carving out a time range, and it's what `⌘/Ctrl+E` (Split) uses to split several tracks at one point (see its own bullet below). The content-editing ops (`Delete`/`M`/`⌘C`/`⌘X`/`⌘D`) already guard `end <= start` at their own construction (`DeleteInRangeEdit`/`MuteInRangeEdit`/`DuplicateClipsEdit`/`copy_range_to_clipboard` `build`), so a zero-width selection harmlessly no-ops there instead of touching content — matching the fact that a point in time has no content to act on. `draw_selected_track_cursor` (`overlays.rs`) reflects a multi-track selection by spanning its accent across `track_start..=track_end` instead of just `selected_track_idx`, so the expansion is visible as you drag — but only while the marquee stays zero-tick-width; see the next bullet.
- **The selection is anchored to the cursor and the selected track; either moving collapses it**: `Display::sync_time_selection_to_cursor()` (called from `update()` beside the other sync passes) latches the cursor tick *and* `selected_track_idx`, clearing `time_selection` when either changes, skipping the check while a drag is in progress — a drag sets the cursor at its own anchor and must not wipe the range it is building; the guard also shields against `UiEvent::TrackSelected` for the drag's own click landing a frame or two late (it round-trips through the sequencer thread), since the anchor is still set when it arrives. Watch both here rather than enumerating cursor- or track-moving keys in `forward_input_event`: that covers every present and future path (arrow-key cursor nav, `⌘/Ctrl+L`, ↑/↓ track nav, a click) with one rule. Playback is unaffected, since it advances `playback_tick`, not `cursor_tick`.
- **The selected-track cursor hides once the marquee has real tick width**: `draw_selected_track_cursor` skips drawing when `time_selection.has_tick_range()` — the marquee's own tint (see "Visual" below) already marks the selected span at that point, so the accent sitting at one edge of it would just be a stray leftover. A purely vertical drag (tracks only, no tick width — "these tracks, at this instant" above) leaves it visible, since that shape has no tint of its own to carry the meaning. It reappears the moment `time_selection` drops back to `None` — Esc, a fresh click, or the cursor/track re-anchor above all do that.
- **`SHIFT+L/R` is the keyboard drag — single-track by default**: `Display::nudge_time_selection_edge()` moves the free tick edge one grid step per press, so ⇧← is a drag to the left and ⇧→ a drag to the right. It is bound in `Display::forward_input_event` (like `⌘/Ctrl+L`, because the operand is view-local) and consumed there, so no `KeyPressed` reaches `input_handler.rs`. Deliberately no new tick-anchor field: a selection is always cursor-anchored (a drag places the cursor at its anchor, and any later cursor move collapses the range), so the edge sitting on the cursor *is* the anchor and the other one is free; with no selection the cursor anchors a fresh gesture. Collapsing back onto the anchor clears the selection **only if the track span is also back at its own anchor** (`self.selected_track_idx`) — the same both-axes rule `extend_time_selection` uses for a mouse drag, so nudging the tick edge home after a `⇧↑`/`⇧↓` track-range extension leaves that track range in place instead of wiping it out. Extending the tick range via keyboard leaves the track range untouched (see `SHIFT+U/D` below for its track-range twin); starting a fresh selection defaults `track_start`/`track_end` to `self.selected_track_idx` (the currently selected track only).
- **`SHIFT+U/D` is the same keyboard drag for the track span**: `Display::nudge_time_selection_track()` mirrors `nudge_time_selection_edge` with track and tick roles swapped — it moves the free track edge one row per press, so ⇧↑ extends upward and ⇧↓ downward. Bound alongside `SHIFT+L/R` in `Display::forward_input_event` for the same reason (the operand is view-local); only the *unshifted* `↑`/`↓` still reach `input_handler.rs`'s `handle_prev_next_keys` (track cycling — see "Tracks and Regions" below). No new track-anchor field either: a track selection is anchored to `selected_track_idx`, so the row sitting on it *is* the anchor and the other is free; with no selection the selected track anchors a fresh gesture. Collapsing back onto the anchor clears the selection only if the tick span is *also* back at the cursor (same both-axes rule as `SHIFT+L/R`'s collapse, above) — an independent `⇧←`/`⇧→` tick extension survives a `⇧↑`/`⇧↓` track edge returning home. The tick range has no keyboard-driven anchor to extend here: extending an existing selection leaves the tick range untouched; starting a fresh selection defaults it to the current cursor tick (zero tick width) — a mouse drag is needed to span a real tick range from a keyboard-only gesture. This binding used to move the loop region (`SHIFT+UP` → set region start to cursor, `SHIFT+DOWN` → set region end to cursor); those `TransportCommand`s had no other caller and were deleted outright rather than left dead — the region no longer has a direct-to-cursor shortcut at all, only `⌘/Ctrl+L`.
- **`⌥←`/`⌥→` is coarse cursor navigation — jump to the next clip edge — and `⇧⌥←`/`⇧⌥→` is the same step applied to the marquee's free edge**: the text-editor word-jump / select-word pair, and the everyday keyboard way to build the band-press end state (cursor on a clip's start, `⇧⌥→` once ⇒ exactly that clip's span, so `⌘/Ctrl+L`, `⌘/Ctrl+D`, `Delete`, `M`, `⌘C`/`⌘X` all behave as after a band press). *Edges* are every clip start **and** end on the **selected track** (not all tracks — `↑`/`↓` already moves across tracks, and the marquee the shifted form builds lives on the selected track anyway), plus tick 0 so a leftward jump from before the first clip still lands; the recording clip counts, its live end being a real edge. The target is the nearest edge *strictly* beyond the starting point in that direction — strict so repeated presses walk, and "start and end both count" so pressing from a clip's end selects the gap up to the next clip's start and a second press takes that clip. Nothing that way ⇒ no-op. The landing tick is **not** snapped to the cursor grid: the edge is the point (a recorded clip's end need not sit on a beat). Pure core `next_clip_edge(edges, from, direction)` (`input/gestures.rs`, unit-tested) over the view-owned `render.clip_shapes`, which is why both are bound in `Display::forward_input_event` rather than the handler. The plain jump (`Display::jump_cursor_to_clip_edge`, gated `alt && !shift && !command`) sends `InputEvent::SetCursorTick { tick }` → `input_handler.rs` → `TransportCommand::SetCursorAndSelectClip` — the click-to-place path, minus the track select — so the clip selection re-syncs and any marquee collapses via `sync_time_selection_to_cursor` exactly as after a lane click; the cursor is never moved view-locally. The shifted form (`Display::extend_time_selection_to_clip_edge`, gated `alt && shift && !command`) is `nudge_time_selection_edge` with a different step: same cursor anchor, same free-edge rule, same both-axes collapse rule (walking the free edge back onto the cursor clears the selection), same untouched track span, and it starts a fresh selection from the cursor when there is none — the free edge, not the cursor, is what the next edge is measured from, so repeated presses walk edge to edge. Nothing is sent. ⌥ was chosen over ⌘/Ctrl for this — and the keyboard marquee *move* rebound the other way — because this is the everyday key and ⌥-arrows is the coarser-cursor-step convention; see "Clip Band Press & Move Drag" below.
- **`SHIFT+click` is the one-click drag — the classic "click the anchor, Shift+click the far corner" marquee**: `Display::extend_time_selection_to_click(x, y)` (`input/gestures.rs`) sets `time_selection` to the rectangle between the anchor and the click on *both* axes at once, exactly the rect a mouse drag from the anchor to that point would build. Bound as an early arm in `MouseClicked` (`input/mod.rs`) — Arranger only, gated on `modifiers.shift` and `is_mouse_inside_clip_content`, placed after the track-header button/mix-bar hit-tests but *before* `clip_edge_at`/`clip_band_at`, so a Shift+click on a clip extends the selection instead of arming a resize or move drag — and consumed there: it never reaches `begin_time_selection` (no drag anchor is set, so the following `MouseMoved`/`MouseReleased` do nothing) and is never forwarded as `MouseClickedTicks`. **Nothing is sent** — the cursor and `selected_track_idx` must stay exactly where they are, since `sync_time_selection_to_cursor` would otherwise collapse the fresh range a frame later. **The anchor is the current selection itself** — `time_selection`, or the cursor tick × `selected_track_idx` when there is none — and nothing else is stored, so a selection built by a band press, a mouse drag, the keyboard nudges or an earlier Shift+click all extend identically (a band press and a left-to-right drag over the same clip leave the *same* state — cursor on the clip start, clip span selected — and must behave the same afterwards). Per axis (`extended_edges`, `gestures.rs`): a click *outside* the selection extends it to the click — the hull, so a band-pressed or dragged clip stays inside when you Shift+click *left* of it (`[click, clip.end]`, not `[click, clip.start]`, which is the gap before the clip with the clip itself dropped — the bug in the first cut, which anchored at the cursor point like the keyboard nudges do) — the Ableton / Pro Tools "extend the selection toward the click" behaviour; a click *inside* moves the edge that is **not** sitting on the cursor (tick axis) / `selected_track_idx` (track axis) — the free edge, exactly what `⇧←`/`⇧→` move, so pulling a selection back in works the same by click as by key, and a Shift+click exactly on the pinned edge collapses it just as nudging the free edge home does — or the *nearer* edge when the cursor is on neither (a selection already extended past its anchor on both sides). Repeated Shift+clicks therefore grow outward and shrink from the free side; a plain click resets everything. (An intermediate revision remembered the band press's clip span in a dedicated `shift_click_anchor_span` field latched from `TimeSelectionSet { track_span: Some }`; that gave the band press and a hand-dragged range over the same clip different anchors — the clip vs. the cursor point — and is gone.) The click side mirrors the plain-click split between band and body (see "Clip Band Press & Move Drag" below): a Shift+click on a clip's **header band means the whole clip** (its span is the target, so the clip ends up covered whole — from before it → up to its end, from after it → from its start, from inside it → its own span), a Shift+click in a clip **body or an empty lane means that point**, snapped to the cursor grid like every other tick here. The track edge is the clicked row either way (`track_idx_at`, falling back to the selected track on the performance-lane row like `extend_time_selection`'s wander rule). Collapsing to no width on both axes clears the selection (same both-axes rule as the drags). Note the keyboard nudges keep their own cursor-pinned model: after a Shift+click has extended a selection past the cursor on both sides, `⇧←`/`⇧→` restart from the cursor rather than picking the nearer edge — a pre-existing property of the nudges, left alone. Pure core: `shift_click_selection(selection, cursor_tick, selected_track, span, track_idx)` over `extended_edges(start, end, pinned, span)`, with unit tests (including the band-press/drag leftward regression and the inside-click free-edge cases) beside `nudged_tick_selection`'s.
- **`⌘/Ctrl+A` is Select All — the marquee that surrounds every clip**: `Display::select_all_clips()` (`input/gestures.rs`) sets `time_selection` to the hull of every clip on both axes — earliest start → latest end, lowest → highest track holding a clip (pure core `clip_hull_selection(clips)`, unit-tested) — exactly the rect a mouse drag from the first clip's top-left corner to the last clip's bottom-right corner would build, so every marquee op (`⌘/Ctrl+D`, `Delete`, `⌘/Ctrl+Delete`, `⌘C`/`⌘X`, `M`, `Q`, `⌘/Ctrl+L`) then acts on the whole arrangement. Bound in `Display::forward_input_event` (Arranger only, exact chord — `command && !shift && !alt`, a stray modifier refuses) for the same reason as `SHIFT+click`: both the operand (the view-owned `render.clip_shapes`) and the result are view-local, and **nothing is sent** — the cursor and `selected_track_idx` stay exactly where they are, which is what keeps `sync_time_selection_to_cursor` from collapsing the fresh rect a frame later, and keeps the armed track unchanged. The hull hugs the clips rather than the lane edges (empty outer tracks and the gap before the first clip are excluded — a `⌘/Ctrl+D` or `⌘/Ctrl+Delete` right after acts on content, not leading silence), and its edges are the clip edges unsnapped, as for `⇧⌥←`/`⇧⌥→`; the recording clip counts, its live end being a real edge. No clips ⇒ no-op, selection kept. Like a Shift+click that reaches past the cursor on both sides, the result is generally *not* cursor-anchored — the keyboard nudges (`⇧←`/`⇧→`, `⇧↑`/`⇧↓`) restart from the cursor afterwards, the same pre-existing nudge property noted above; Esc or a plain click clears it as usual. Consumed under a keyboard-armed marquee nudge like every other `⌘/Ctrl+X` chord (first arm). The same chord in `Clip` falls through to `input_handler.rs` and selects all events instead — see "Reserved Insert Spans and Event Selection" below.
- **Press keeps its existing meaning**: the press edge still commits cursor placement and clip selection via `MouseClickedTicks`; it merely also anchors the selection. Dragging therefore moves the cursor to the selection start, matching Ableton's insert marker.
- **A drag survives vertical wander**: extension is deliberately *not* gated on `is_mouse_inside_clip_content`. Only the initial press is area-gated; once anchored, leaving the lanes vertically must not cancel the gesture (the track anchor fallback above is what keeps the *track range* well-defined through that same wander).
- **Release drops the anchor only**: `InputEvent::MouseReleased` carries no coordinates — the poller emits the `MouseMoved` for the same position earlier in the same batch, so the final boundary is already committed. `time_selection_anchor` clears.
- **Cleared on leaving the arranger**: `Display::clear_gestures()` (the hover cursor, `clear_time_selection()` and every drag) runs on `ClipEntered`, `ClipExited`, and `ProjectLoaded`. A selection is scoped to a single arranger visit.
- **Esc cancels it, mid-drag or already committed**: bound in `Display::forward_input_event` (Arranger only) and calls `clear_time_selection()` — the standard cancel-this-gesture chord (Excel/Photoshop/VS Code all treat Esc this way). No cursor/track restoration is needed: the committed cursor tick and `selected_track_idx` never leave the drag's anchor in the first place ("Press keeps its existing meaning" above), so dropping `time_selection` alone leaves `draw_selected_track_cursor` reading the anchor. Also drops the drag anchor mid-gesture, so a still-held mouse button doesn't resume extending a selection until the next press.
- **`⌘/Ctrl+L` is bound in the view, dispatched in the handler**: `Display::forward_input_event` matches the key and translates it to `InputEvent::SetRegionToTimeSelectionOrToggleLoop { time_bounds: self.gesture.time_selection.map(|r| (r.start, r.end)) }` — extracting just the tick range; the loop region has no track concept. `input_handler.rs` holds the single dispatch arm and owns the *precedence* rule: `Some` bounds go straight to `TransportCommand::SetRegionOrToggleLoop` (already resolved; moves the region and re-enables looping, or toggles looping if the region already sits there), `None` sends `TransportCommand::ToggleLoop` (a bare `loop_enabled` flip, region band untouched). The selected clip is not an operand — see `010-keybindings.md` for why. Keep this shape — do **not** re-send a raw `KeyPressed` through the channel for a second handler to re-match, and do **not** promote the time selection to `SharedAtomics` just to move the binding back: independent atomic pairs tear (hence `region_bounds_snapshot()`'s retry loop), and it buys nothing functionally.

### Which operations respect the marquee's track range, and which bypass it

Every range-scoped key below reads `self.gesture.time_selection`, but they split into two groups. **Bypass** (tick range only, always every track — unchanged since before the marquee existed): `⌘/Ctrl+L`, `⌘/Ctrl+I` (Insert Silence), `⌘/Ctrl+Delete` (Delete Time), `Shift+⌘/Ctrl+C`/`Shift+⌘/Ctrl+X`/`Shift+⌘/Ctrl+D`. **Respect** (tick range × the marqueed tracks only): `Delete`/`Backspace`, `M`, `Q` (Quantize), `⌘/Ctrl+E` (Split), plain `⌘/Ctrl+C`/`⌘/Ctrl+X`, plain `⌘/Ctrl+D`. The bypasses are not a style choice: `⌘I`/`⌘Delete` compose `InsertSilenceEdit`/`DeleteInRangeEdit` respectively, and the `Shift+⌘` trio bypass the marquee's *track* range specifically — both touch *every* clip at/after a tick on *every* track by the same amount so the tracks stay aligned on the shared timeline, scoping that to a track subset would slide the marqueed tracks out of sync with the rest. Note `⌘I`/`⌘Delete` don't follow the `Shift+⌘` convention the other three bypasses use — there's no marquee-scoped variant of either to need distinguishing from, so the plain chord was free; `Shift` is not actually read by either arm, so `⌘+Shift+I`/`⌘+Shift+Delete` fire the same bypass too. `D` is the one key whose plain and `Shift` chords are *different operations*, not the same operation at two scopes: plain `⌘/Ctrl+D` is "Duplicate Clips" (a respecting, overwriting paste), `Shift+⌘/Ctrl+D` is "Duplicate Time" (a bypassing, space-inserting one) — see their bullet below. There is no bare `D` (plain Duplicate) binding at all — those two cover every duplicate need between them; `D` with no modifier does nothing in the Arranger.

- **`Delete`/`Backspace` and `M` are both marquee-only**: both are bound in `Display::forward_input_event` (Arranger only; `M` is intercepted ahead of the bare `Key::M` arm in `input_handler.rs`, which handles `M` for the other views — see below), the same no-single-clip-fallback shape as `Q`: the view only sends `InputEvent::RemoveClipsInSelection { rect }` → `SequencerCommand::RemoveClips { rect }` / `InputEvent::MuteClipsInSelection { rect }` → `SequencerCommand::MuteClipsInRange { rect }` when a time selection is `Some`; with no selection the press is consumed and nothing is sent. The old selected-clip fallback (a `RemoveClipEdit` on a bare click-then-Delete, and the same fallback on both `⌘/Ctrl+X` forms) was removed outright, edit type and all — a clip is only ever deleted through a tick range, so a stray Delete or Cut with nothing marqueed can't wipe a whole clip. Do not reintroduce it; to delete one clip, band-press it (which marquees exactly its span) or build the span with `⇧⌥→`, then Delete. Both keys no-op when there is nothing to act on. The region is not involved at all.
  - **`Delete`/`Backspace`** carves the tick range out of every clip that *overlaps* it **on the marqueed tracks**, Ableton-style and **without rippling** — `SequencerCommand::RemoveClips` → `DeleteInRangeEdit::from_track_span` (`src/core/sequencer/edit/clip_edits/delete_in_range.rs`). A clip fully inside the range is removed whole; a clip straddling one edge is trimmed to that edge keeping its id; a clip spanning the whole range becomes two (`[os, start]` keeps the id, `[end, oe]` is a new clip) with a gap between. Non-destructive, exactly like `⌘E` and the clip edge drag-resize: every piece keeps the *full* event list, only `start_tick`/`region` diverge (phase-locked), so dragging an edge back out afterward reveals the carved material again. Material after the range keeps its timeline position — the loop region and the cursor are untouched. Internally it composes two `SplitClipsEdit`s (cut every straddling clip at `end`, then at `start`, both scoped to the track span) plus a removal of every piece left fully inside the range. Selection sticks to the pre-delete clip if it survived, else clears. See `EditResult::RangeDeleted`/`RangeRestored` in `050-undo-redo.md`.
  - **`M` mutes** — Ableton-style ("Deactivate Time Selection"): `Some` bounds carve the tick range out of every clip **on the marqueed tracks** exactly like `Delete`/`Backspace` — split at `end`, then at `start` (`MuteInRangeEdit::from_track_span`, composing two `SplitClipsEdit`s the same way `DeleteInRangeEdit` does, same ordering and for the same reason) — but **mutes the interior instead of removing it**. The old selected-clip fallback (`MuteSelectedClipsEdit`, both in the Arranger and as the whole-clip toggle inside `Clip`) was deleted outright, edit type and all — like `Delete`, a clip is only ever muted through a tick range. Toggle rule: mute all if any interior clip is unmuted, otherwise unmute all. Non-destructive, like `⌘E`/`Delete`: every piece keeps the *full* event list, only `start_tick`/`region` diverge. Nothing is removed and nothing shifts, so there is no reselection. **The splits stay in place on an unmuting press**; undo reverses both the mute flags and the splits, LIFO. See `EditResult::RangeMuted`/`RangeUnmuted` in `050-undo-redo.md`.
  - **`Q` quantizes the time selection — and only that**: marquee-only, the same no-single-clip-fallback shape as `Delete`/`Backspace` and plain `⌘/Ctrl+D`. Bound in `Display::forward_input_event` (Arranger only) as `InputEvent::QuantizeInSelection { rect }` → `SequencerCommand::QuantizeInRange { rect }`; with no time selection the press is consumed and nothing is sent, and there is **no bare-`Q` arm in `input_handler.rs`** — `Q` does nothing in `Clip`. The old selected-clip quantize (`QuantizeSelectedClipEdit`: whole region, or the selected notes' span) was removed outright rather than kept as the `None` fallback: with the arranger nearly always having a clip selected, a fallback would quantize a whole clip out from under a partial selection the user hadn't finished dragging. Do not reintroduce it. The rect quantizes only the `NoteOn`s inside the tick range on every overlapping clip **on the marqueed tracks** (`QuantizeInRangeEdit::from_track_span`): the arrangement range is clamped to each clip's span and mapped into its event-tick space (`region.start + (tick - start_tick)`), then handed to `Clip::quantize` — each clip votes its own grid over its own candidates (`070-quantization.md`). **Nothing is split** — unlike `Delete`/`M`, quantize only moves event ticks, so there is no piece to carve and no bounds change; the pieces of an earlier non-destructive split each hold their own event copy, so a marquee over one piece quantizes that piece alone. A rect overlapping no clip is a no-op. Both directions return `EditResult::RangeQuantized { updated }` (`050-undo-redo.md`); the handler re-seeks playback, refreshes each clip's arranger thumbnail via `ClipUpdated`, and re-syncs the open clip view (`EventsUpdated`, which `events_updated_refits_clip_canvas` keeps from re-fitting the arranger).
  - **`M` mutes the selected *events*, not the clip, in `Clip`**: bare `Key::M` never reaches this Arranger-only forwarder outside the Arranger (there's no marquee there), so it falls through to `input_handler.rs`'s bare arm — `handle_mute` branches on `ClipContext` there: `ClipWithSelection` sends `SequencerCommand::MuteSelectedEvents` (`MuteSelectedEventsEdit`), toggling mute on the selected events (their `NoteOn` + paired `NoteOff` together) rather than the whole clip; every other context sends nothing (the whole-clip toggle `Clip` used to have is gone); `Arranger` sends nothing (it can only get here with no marquee, and that press is already consumed upstream). This closes a prior bug where `M` with notes selected silently muted the *whole* clip out from under the events being edited. See `050-undo-redo.md`.
- **`⌘/Ctrl+E` splits clips at the cursor, Ableton-style — moved from plain `E`** for consistency with the other now-modified-key range ops: bound in `Display::forward_input_event` and translated to `InputEvent::SplitClipsInTimeSelectionOrClip { time_bounds: self.gesture.time_selection }`. The whole `Option<TimeSelectionRect>` is forwarded as `SequencerCommand::SplitClips` and the sequencer handler resolves precedence: `Some` bounds split, at the cursor tick, every clip **on the marqueed tracks** that overlaps the tick range *and* whose bounds actually contain the cursor (`SplitClipsEdit::from_time_range_in_tracks`); `None` falls back to splitting just the selected clip (`SplitClipsEdit::from_selected_clip`), which no-ops when nothing is selected or the cursor sits at/outside the clip's bounds (a boundary split would produce an empty piece). **A zero-tick-width `Some` rect (a purely vertical marquee drag) is the deliberate way to split several tracks at one instant**: `find_clip_ids_in(tick, tick)` degenerates to "does this tick fall strictly inside a clip", which is exactly the containment `split_tick` needs anyway, so every clip under the point on the marqueed tracks gets split with no dedicated code path. Non-destructive, like the clip edge drag-resize in "Clip Edge Drag-Resize" below: both halves keep the *full* original event list and only `start_tick`/`region` diverge (phase-locked the same way left-edge trim is), so dragging an edge back out afterward can reveal the other half's content again — and, since no stored event is ever mutated to produce it, a note straddling the cut still plays through continuously across the boundary during transport (`Track::pending_note_offs`/`pending_note_ons`, `050-undo-redo.md`). The original clip keeps its id and becomes the left half; the right half is a new clip, so undoing a split removes it and restores the original's pre-split region end (`EditResult::ClipsSplit`/`ClipsUnsplit` in `050-undo-redo.md`). **The right-hand piece becomes the new selection** (`split_clips_workflow`, same cursor-clip reselection rule as `paste_clips_workflow`): the cursor sits exactly on the split boundary, i.e. at the start of the new right clip, so that's where the user's attention naturally lands next — mirrors Ableton. Undoing falls back to reselecting the restored original (left) clip rather than clearing the selection outright, since the usual `remove_clips_workflow` fallback (clear if the removed clip was selected) would otherwise leave nothing selected on every unsplit.
- **`⌘/Ctrl+I` inserts silence, Ableton/Bitwig-style — moved off bare `I`, bypasses the marquee's track range, and the one binding with no single-clip fallback**: bound in `Display::forward_input_event` like `Delete`/`⌘E`, but since "how much time to insert" is meaningless without a real duration, the view only sends `InputEvent::InsertSilenceInSelection { start, end }` (extracting just the tick range from `self.gesture.time_selection`) when a selection is `Some`; with no selection the key press is simply consumed as a no-op, with no `Option`-wrapped payload and no precedence arm in `input_handler.rs` (unlike every other binding in this section). The insertion point is the selection's `start` (where the cursor already sits — see above) and the amount is `end - start`. `InsertSilenceEdit::from_time_range` (`src/core/sequencer/edit/clip_edits/insert_silence.rs`) does the work in two steps, **always across every track, regardless of the marquee's track range** — this is deliberate, not a missed generalization: it first reuses `SplitClipsEdit::from_time_range` verbatim (constructing it with `split_tick` equal to the insertion point) to split any clip whose bounds straddle the insertion point, exactly as `⌘E` would; then it shifts every clip — pre-existing or freshly split — whose `start_tick` is at or past the insertion point forward by the inserted amount, via a raw `Clip::set_start_tick` mutation rather than a `remove_clip_by_id`/`add_clip` round-trip (safe because a uniform forward shift of an already-non-overlapping clip set can never create a new overlap, and `Track::add_clip`'s overlap check has no awareness of sibling clips mid-shift in the same edit, so re-validating one at a time would risk spurious failure). Scoping this to fewer than every track would slide those tracks out of sync with the rest — the same reasoning that keeps `Shift+⌘D` (Duplicate Time) global on both halves, see below. The loop region and the cursor are **not** shifted — same "intentional-only" scope as every other key in this section. No reselection happens either: a shifted or split-left clip keeps its id, so whatever was already selected stays valid and simply tracks its new position via `ClipUpdated`. See `EditResult::SilenceInserted`/`SilenceRemoved` in `050-undo-redo.md`.
- **`⌘/Ctrl+Delete` deletes time, the exact opposite of `⌘/Ctrl+I` — bypasses the marquee's track range, same no-single-clip-fallback shape**: bound in `Display::forward_input_event` ahead of the plain `Delete`/`Backspace` arm (which has no modifier guard and would otherwise catch this chord first), matched only on `Key::Delete` (not `Backspace` — there is no `⌘Backspace` binding). Like `⌘/Ctrl+I`, only `modifiers.command` is checked — `Shift` is not read, so `⌘+Shift+Delete` fires the same binding rather than falling through to plain delete. This deliberately does **not** mirror Ableton Live, which binds Delete Time to `⌘/Ctrl+Shift+Delete`: that extra `Shift` groups it with Ableton's other track-range-bypassing chords, but `⌘/Ctrl+I` itself is already a single-modifier bypass with no marquee-scoped sibling to distinguish from, so `⌘/Ctrl+Delete` pairs with it the same way instead — the plain chord was free precisely because there is no marquee-scoped Delete Time to reserve it for. The view only sends `InputEvent::DeleteTimeInSelection { start, end }` when a selection is `Some`; with no selection the key press is consumed as a no-op. `DeleteTimeEdit::from_time_range` (`src/core/sequencer/edit/clip_edits/delete_time.rs`) does the work in two steps, **always across every track**, for the same alignment reason as `⌘/Ctrl+I`: it first reuses `DeleteInRangeEdit::from_time_range` verbatim (the exact same non-rippling carve `Delete`/`Backspace` uses) to clear `[start, end)` — trimming or splitting every overlapping clip, removing anything left fully inside the range; then it shifts every clip — pre-existing or freshly carved — whose `start_tick` is at or past `end` **back** by `end - start`, via the same raw `Clip::set_start_tick` mutation `⌘/Ctrl+I` uses (safe for the same non-overlap reason, mirrored: the carve already guarantees `[start, end)` is empty, so a uniform backward shift of the already-non-overlapping remainder can't create a new overlap). The loop region and the cursor are **not** shifted — same "intentional-only" scope as `⌘/Ctrl+I`. No reselection on the shift half either, for the same reason as `⌘/Ctrl+I`; but since the carve half *can* remove the selected clip outright (unlike `⌘/Ctrl+I`, which never removes anything), the clip selection falls back to clearing when that happens — the same fallback `Delete`/`Backspace` uses. Unlike `⌘/Ctrl+I` (which leaves the marquee untouched — the selection still frames real content, just shifted), the Arranger *time selection* (the marquee itself, distinct from clip selection above) no longer refers to anything real once its span is deleted, so the handler collapses it back to the track cursor: `handle_edit_result` sends `UiEvent::TimeSelectionCleared` after a `TimeDeleted` result, which `ui_events.rs` turns into `clear_time_selection()`. Undo restores it: `EditResult::TimeUndeleted` carries `restored_selection: (i32, i32)` (the edit's frozen `start`/`end`, not re-derived from view state — same "frozen at construction" rule as everything else in `050-undo-redo.md`), and the handler re-sends it as `UiEvent::TimeSelectionSet { start, end }` — the same event `⌘/Ctrl+D` uses to advance the selection, just restoring instead of advancing. See `EditResult::TimeDeleted`/`TimeUndeleted` in `050-undo-redo.md`.
- **`⌘/Ctrl+D` — the two Duplicate bindings, one key, two different operations**: `Display::forward_input_event` matches `Key::D` with `modifiers.command`, branching on `modifiers.shift`. Plain `⌘/Ctrl+D` is **"Duplicate Clips"** (marquee-scoped, overwriting — the everyday one); `Shift+⌘/Ctrl+D` is Ableton-style **"Duplicate Time"** (global, space-inserting — the heavier one, per the ⇧-means-wider convention `⌘C`/`Shift+⌘C` set). There is no bare-`D` Arranger binding at all — these two cover every duplicate need. Both forms are selection-only — nothing is sent without a real time selection — and both *move* the time selection onto the copy afterward via `UiEvent::TimeSelectionSet` (the cursor is not moved, so `sync_time_selection_to_cursor` leaves the pushed selection alone), so repeated presses chain copies down the timeline.
  - **Plain ⌘/Ctrl+D — "Duplicate Clips" (marquee-scoped, overwriting)**: sends `InputEvent::DuplicateClipsInSelection { rect: TimeSelectionRect }` → `SequencerCommand::DuplicateClips` → `DuplicateClipsEdit::from_track_span` (`src/core/sequencer/edit/clip_edits/duplicate_clips.rs`) → `SequencerEdit::DuplicateClips`. It is plain `⌘C` then `⌘V` at the selection's `end`, composed: a thin anchor-picking newtype over `PasteClipsEdit`, built from a throwaway `Sequencer::copy_range_to_clipboard((track_start, track_end), start, end)` (the same pieces plain `⌘C` produces) pasted via `from_clipboard_at(.., end)`, so each piece lands at `original + width` on its own track. **Nothing shifts and no time is inserted**: the copy is dropped on top of whatever already sits in `[end, 2*end - start)` on the marqueed tracks, and that material is carved out by `PasteClipsEdit`'s per-target `DeleteInRangeEdit` — the copy wins. Tracks outside the marquee are untouched, and the loop region is never moved. Reports `EditResult::ClipsDuplicated`/`ClipsUnduplicated` — `ClipsPasted`/`ClipsUnpasted`'s buckets plus `new_selection`/`restored_selection: TimeSelectionRect` — and the handler runs `paste_clips_workflow`/`unpaste_clips_workflow` verbatim then emits `TimeSelectionSet { .., track_span: Some(..) }`: the edit froze its own rect, so the advanced marquee names its track span in full.
  - **Shift+⌘/Ctrl+D — "Duplicate Time" (global, space-inserting)**: unchanged from before the marquee existed. Sends `InputEvent::DuplicateTimeInSelection { start, end }` (tick range only — bypasses the marquee's track range) → `SequencerCommand::DuplicateTimeInRange` → `DuplicateTimeEdit::from_time_range` (`src/core/sequencer/edit/clip_edits/duplicate_time.rs`). It is `⌘/Ctrl+I` followed by a paste, composed: it first runs an `InsertSilenceEdit` anchored at the selection's `end` (insert `end - start` ticks — split any straddler, shift every clip at/after `end` right, on every track), then a `PasteClipsEdit` that drops a copy of the `[start, end)` slice of every overlapping clip on every track into the freed span. Nothing is carved/destroyed, because the gap is pre-cleared. It is deliberately global on *both* halves — a marquee-scoped variant that shifted every track but pasted only some existed briefly and was removed as the worst of both worlds; the alignment argument that keeps `⌘/Ctrl+I` global (a partial shift desyncs the marqueed tracks from the rest) applies to the shift half, and once the shift is global there is no point scoping the paste. Afterwards the handler emits `UiEvent::TimeSelectionSet { start, end, track_span: None }` to advance the tick range to `[end, 2*end - start)`. Since `DuplicateTimeEdit` carries no track-span state (only `start`/`end`), `UiEvent::TimeSelectionSet`'s handler (`ui_events.rs`) preserves whatever track range was already active in `Display.gesture.time_selection`, defaulting to `self.selected_track_idx` only if there was no prior selection to preserve from (the clip band press and plain `⌘D` are the senders that name their span — `track_span: Some(..)` — see "Clip Band Press & Move Drag" below). The **loop region is the exception to the "intentional-only" scope** every other key in this section keeps: if its start sits within the duplicated span or after it (`region_start >= start`) it is *moved* (not resized) right by the selection width — `DuplicateTimeEdit` calls `Sequencer::shift_region`, and `undo()` reverses it — so a loop stays on the same musical material after the insert. A region starting before the selection is left alone (moving only its end would be a resize). See `EditResult::TimeDuplicated`/`TimeUnduplicated` in `050-undo-redo.md`.
- **`Shift+⌘/Ctrl+C` copies, `Shift+⌘/Ctrl+X` cuts the time selection across every track (bypasses the marquee), `⌘/Ctrl+V` pastes**: `egui-winit` turns the copy/cut/paste chords into `egui::Event::Copy` / `egui::Event::Cut` / `egui::Event::Paste` and **swallows the raw `C`/`X`/`V` key presses**, regardless of Shift, so `InputPoller` maps those to `InputEvent::Copy { shift }` / `InputEvent::Cut { shift }` / `InputEvent::Paste` (bare `C` with no modifier is unaffected — it no longer has a job, `Commit` moved to `/`, see `010-keybindings.md`'s "Transport" section). Since the bare `egui::Event::Copy`/`Cut` carries no modifier payload of its own, `InputPoller` samples `shift` separately from `ctx.input(|i| i.modifiers)` in the same frame — safe because `egui-winit` updates that from `WindowEvent::ModifiersChanged` ahead of dispatching the `C`/`X` keydown. `Display::forward_input_event` resolves `InputEvent::Copy { shift: true }`/`InputEvent::Cut { shift: true }` (Arranger only) into `InputEvent::CopyClipsInSelection`/`CutClipsInSelection { start, end }` — extracting just the tick range, since these two always span every track regardless of the marquee — and **only when `self.gesture.time_selection` is `Some`**: every clipboard chord is marquee-only, the same no-single-clip-fallback shape as `Delete`/`Backspace`, so with no time selection the chord is consumed and nothing is sent. **Plain `⌘/Ctrl+C`/`⌘/Ctrl+X` (`shift: false`) forward the whole `TimeSelectionRect` to the marquee-scoped siblings** — see the bullet below. `InputEvent::Paste` needs no view-local operand and is dispatched straight to `SequencerCommand::PasteClips` in `input_handler.rs`, Arranger-gated. **`egui::Event::Paste` only fires when the OS text clipboard is non-empty**, so a copy/cut also writes `input_event::CLIP_CLIPBOARD_SENTINEL` to it via `EventHandlers.repaint_ctx` (`prime_os_clipboard_for_clips`: `ctx.copy_text` + `request_repaint`, the same cross-thread wake pattern as `110-performance-lane.md`); `InputPoller` suppresses `PastedText` for that sentinel so it can't leak into the Project-modal link field.
  - **Copy** (`SequencerCommand::CopyClips { start, end }`, `Sequencer::copy_clips_to_clipboard` in `src/core/sequencer/clipboard.rs`) is **not** an undoable edit — copying is not a data mutation, exactly like a selection. It copies the portion of every clip on every track that intersects `[start, end)` as a non-destructive region-windowed piece (phase-locked, full event list retained — identical to `⌘E`/`Delete`), each piece's `start_tick` normalized to the selection start and each piece tagged with its absolute source track. The old whole-lead-selected-clip fallback (and the `ClipClipboard::single` flag that made paste retarget it onto the selected track) is gone: a band press already marquees exactly the clip's span, so "copy this one clip" is the ordinary range copy. The `ClipClipboard` is session-only in-memory state, not persisted, cleared on new/load project (`Sequencer::new_project`).
  - **Cut** (`SequencerCommand::CutClips { start, end }`) is copy-then-delete: it calls `Sequencer::copy_clips_to_clipboard(start, end)` (non-undoable clipboard fill), then runs `DeleteInRangeEdit::from_time_range` (the same Ableton-style range carve-out `Delete`/`Backspace` use, but across every track, no rippling). Marquee-only like copy: the view only sends `InputEvent::CutClipsInSelection { start, end }` when a selection is `Some`. Only the delete goes on the undo record, so undoing a cut restores the removed clips while the clipboard keeps the cut payload — mirrors Ableton. No dedicated `EditResult`/`SequencerEdit` variant: it reuses `RangeDeleted`/`RangeRestored`.
  - **Paste** (`SequencerCommand::PasteClips` → `PasteClipsEdit`, `src/core/sequencer/edit/clip_edits/paste.rs`) re-anchors every clipboard piece to the cursor tick and, in the track dimension, follows the clipboard's **track anchor** (`ClipClipboard::track_anchor`, resolved per piece by `ClipClipboard::target_track`): the all-track `Shift+⌘/Ctrl+C`/`X` forms have none, so their pieces go back on their **absolute source track** whatever is selected (the same alignment argument that makes them bypass the marquee — re-anchoring an every-track copy would just slide the whole song down), and a paste of one needs no track selection at all. The marquee-scoped plain `⌘/Ctrl+C`/`X` forms anchor on the marquee's `track_start`, so `⌘/Ctrl+V` lands the set on the **selected track with the marquee's shape** — tracks 3..=5 copied and track 2 selected pastes onto 2..=4, empty marqueed tracks included in the shape (the offset is from `track_start`, not from the first piece); pieces that would land past the last track are dropped, and with no track selected the scoped clipboard falls back to the absolute source tracks too. Both Duplicate edits pass `target_track: None` to `from_clipboard_at`, so their throwaway copies always stay on their source tracks. Where a pasted clip overlaps existing material, that span is carved out Ableton-style by composing one **track-scoped** `DeleteInRangeEdit::from_track_range` per pasted clip (the same worked-example reuse pattern as `InsertSilenceEdit`/`DeleteInRangeEdit` composing `SplitClipsEdit`). The cursor and loop region are untouched — same "intentional-only" scope. The pasted clip under the cursor on the selected track becomes the selection (same rule as `split_clips_workflow`). Plain `⌘D` (Duplicate Clips) and `Shift+⌘D` (Duplicate Time) both reuse this same paste primitive with a selection-derived anchor instead of the cursor — see above. See `EditResult::ClipsPasted`/`ClipsUnpasted` in `050-undo-redo.md`.
- **Plain `⌘/Ctrl+C` copies, plain `⌘/Ctrl+X` cuts — every clip within the marquee rectangle**: the marquee-scoped siblings of `Shift+⌘/Ctrl+C`/`X` above. `Display::forward_input_event` resolves `InputEvent::Copy { shift: false }`/`Cut { shift: false }` into `InputEvent::CopyClipsInSelectionScoped`/`CutClipsInSelectionScoped { rect }` → `SequencerCommand::CopyClipsScoped`/`CutClipsScoped { rect }` — forwarding the whole `TimeSelectionRect`, and only when a selection is `Some` (marquee-only, like `Delete`/`Backspace` and the `Shift+⌘` forms — with no selection the chord is consumed and nothing is copied or deleted). A rect acts on every clip **on tracks `rect.track_start..=rect.track_end`** intersecting `[rect.start, rect.end)` — before the marquee gained a track dimension this was scoped to the lead-selected clip only; now it's exactly the marquee rectangle, the same scope `Delete`/`M`/`⌘E` use. A rect that overlaps nothing is a no-op (clipboard untouched / nothing deleted) — there is no whole-clip fallback of any kind.
  - **Copy** (`Sequencer::copy_clips_scoped_to_clipboard`, `src/core/sequencer/clipboard.rs`) delegates straight to `copy_range_to_clipboard((rect.track_start, rect.track_end), rect.start, rect.end)` — the exact same track-range-filtered function `Shift+⌘C` uses for the all-track case, just narrower — producing a multi-piece, absolute-track-indexed clipboard — then stamps `track_anchor = Some(rect.track_start)` on it, which is what lets `⌘/Ctrl+V` re-anchor the set onto the selected track (see Paste above).
  - **Cut** (`Sequencer::cut_clips_scoped_workflow`, `src/core/event_handlers/clip_range_edits.rs`) is copy-then-delete like `Shift+⌘/Ctrl+X`, and reuses the **same** edit type Delete/Backspace use — `DeleteInRangeEdit::from_track_span(sequencer, rect.track_start, rect.track_end, rect.start, rect.end)` — rather than a dedicated clip-scoped edit type. (An earlier iteration had a purpose-built `DeleteInSelectedClipEdit` for the "lead clip only" scope; it's gone, superseded once the marquee itself became the source of truth for what's included.) There is no `None` form: like every delete, it's marquee-only. See `050-undo-redo.md`.
  - **Visual**: every clip renders the same flat tint in its own track colour — **the lead/cursor-selected clip gets no visual at all** (no tint bump, no brighter header, and no `ClipSelected`/`ClipDeselected` UI event exists any more): a highlighted clip would promise that Delete/Duplicate/Cut act on it, and they never do — the marquee is the only thing they read. A clip untouched by the marquee must look exactly as if there were no selection at all. `draw_clip_body` (`src/view/display/rendering/arranger.rs`) then paints one *additional* highlight on top, only when `time_selection` is active **and has a real tick width** (`TimeSelectionRect::has_tick_range` — a zero-tick-width point-in-time track selection, see above, has no range to visualize): the sub-rect of the clip that actually overlaps `[rect.start, rect.end)` **and** whose track falls inside `rect.track_start..=rect.track_end` (`tick_overlap`, `rendering/mod.rs`) gets a neutral `theme::fg_dim()` highlight, in place of the track colour, so a marquee spanning several tracks reads as one unified selection rather than a patchwork of per-track tints. Nothing outside that sub-rect changes — on this clip or any other. (An earlier revision additionally dimmed the *whole* body of every clip in the project as a second signal the moment any marquee went active; that read as the entire arranger flashing gray on every drag and is gone — the highlight is the only signal now.) Empty gaps within the tick range on the marqueed track lanes only (not elsewhere) get the same highlight at full row height (`draw_time_selection_gaps`/`gap_spans`, iterating `rect.track_start..=rect.track_end` instead of every track) — the highlight marks what's inside the marquee (what plain `⌘/Ctrl+C/X` would grab; `Shift+⌘/Ctrl+C/X` always grabs every track regardless of what's tinted). The clip header strip is unaffected by `time_selection` and marks nothing — it's a track identifier and a grab band. See `030-ui-design.md`.

## General Layering Principle

- **Input handlers express intent only**: key/mouse routing in `event_handlers/input_handler.rs` should dispatch commands and avoid owning state-entry defaults or business side effects.
- **Transition workflows own state-entry/exit side effects**: defaults that belong to entering/leaving a mode (for example, the clip cursor mode set on entering `Clip`) should live in `workflows.rs` / sequencer command handling where the transition is actually committed.
- **Model/sequencer layers own mutation and invariants**: data edits, normalization, and consistency rules should stay in `src/models/` and `src/core/sequencer/`, not in input dispatch code.

## Tracks and Regions

- **8 fixed tracks** currently; this may increase in the future — avoid hardcoding `8`.
- **No hard length constraints** on tracks, clips, or regions.
- **Clips on a track must not overlap**: `Track::add_clip` enforces a non-overlap invariant and returns `bool` — callers must handle `false`. Every insertion path goes through `add_clip` (`add_clip_unchecked`, which let the retired `InsertIntoClip` pending phrase overlap its source clip, was deleted 2026-09-26).
- **`Region`** (see `src/models/region.rs`) defines the cycle length for both clips and the arrangement. It stores `start`/`end` as `Arc<AtomicI32>` so the UI can read them without locking.
- **Region does not auto-follow cursor in Arranger**: moving the cursor with `L/R` (or jumping it edge to edge with `⌥←`/`⌥→`) does not shift the region window. Region changes are intentional-only — via `⌘/Ctrl+L` (snap to the time selection; with no selection it toggles looping in place instead), the *only* keyboard-driven region mutation left. Note that a time selection itself never moves the region — only `⌘/Ctrl+L` commits it. `SHIFT+UP`/`SHIFT+DOWN` no longer touch the region at all — they now extend the arranger time selection's track span instead (see "Arranger Time Selection — the Marquee" above); the region has no direct-to-cursor shortcut anymore.
- **Playback start follows cursor exactly**: `PlayFromCursor` / restart-from-cursor must honor `cursor_tick` even when cursor is outside the current region window. Region loop wrap applies when playback is inside the region; do not snap start to `region.start` just because cursor is past `region.end`.
- **Plain `+/-` and `Shift+/-` zoom in `Arranger` (and in `Clip`), never touch the region** (the zoom is view-local, `010-keybindings.md`): the loop region has no keyboard shortcut at all any more — only `⌘/Ctrl+L` mutates it — and a clip's region length is changed by dragging the clip header band's edge or by `[`/`]` (see "Clip Edge Drag-Resize" below).
- **`Delete` no longer touches the region**: it keys off the time selection only (see "Arranger Time Selection" above), not the loop region or the selected clip, and carves partial clips (`DeleteInRangeEdit`) rather than acting on whole clips only. It is acceptable for clips or events to exceed region bounds when contextually sensible.

## Event Selection

- **No reserved insert spans any more**: the keypad era inserted each committed take as a selectable *step cell*; in May 2026 those became `Clip.reserved_insert_spans` (overwrite protection for later inserts), which have since been removed from the code entirely. A capture commit now just adds events, and never changes the selection (see Views above).
- **Event selection is click-based, not keyboard-navigated**: clicking a note in the piano roll selects it (`SequencerCommand::SelectClipEvent`, resolved via a hit-test in `Display::event_id_at` against `self.render.event_shapes`, using the same geometry — `Display::note_area_geom` — as `draw_clip_view` so the clickable area always matches what's drawn). A click always fully replaces the selection: `select_clip_event_workflow` clears first, then selects, so clicking away from a multi-selection correctly deselects every member, not just the previous lead. `⌘/Ctrl+A` selects all `NoteOn` events (`handle_select_all` in `input_handler.rs`, from `Clip`, publishing the selection; it replaced `Shift++`, now spare) and ESC clears the selection (its only binding since `Shift+-` was deleted to free Shift+`+`/`-` for clip-view zoom); `Shift+L/R` no longer touches the selection at all — see `010-keybindings.md` for what it does instead. `Up/Down` transposes pitch; arrow keys never navigate events.
- **Deselecting all events is "click empty grid" or ESC**: an empty-grid click resolves to `SelectClipEvent(None)`, which the workflow treats identically to a real deselect. ESC (`ClearEventSelection`) is a no-op with nothing selected.

### Event Marquee Selection

- **Clip only, same press-drag-release shape as the Arranger's time selection** (see above), but with one key difference: a time selection is purely view-local, while event selection is model state (`Clip::event_selection`) because it drives real edits (nudge/delete/duplicate/transpose) and the key routing (`has_event_selection`). So the drag rectangle has to round-trip through a command on every move rather than staying entirely in `Display`.
- **View-local drag state**: `Display.gesture.event_marquee_anchor: Option<(f32, f32)>` (screen-space press point, `Some` only while the primary button is held — doubles as the drag-active flag) and `Display.gesture.event_marquee_rect: Option<(i32, i32, f32, f32)>` (normalized `(tick_min, tick_max, y_min, y_max)` where `y_min`/`y_max` are raw screen-space pointer y, not snapped to note rows, `Some` only once the pointer has moved off the anchor). The rect is for rendering only — `Clip::event_selection` is the source of truth for which events are actually selected.
- **Every rect update round-trips through the model**: `Display::extend_event_marquee` (driven by `MouseMoved`, alongside `extend_time_selection`) recomputes the rect and sends `InputEvent::SelectEventsInRect { tick_min, tick_max, note_min, note_max }`, which `input_handler.rs` maps 1:1 to `SequencerCommand::SelectEventsInRect`. `select_events_in_rect_workflow` calls `Clip::select_events_in_rect`, which recomputes the whole matching set from scratch each time (rather than incrementally adding/removing), so a shrinking rectangle naturally deselects events that fall back outside it. The workflow emits `EventSelected`/`EventDeselected` UI events only for the diff, then calls `publish_event_selection` — one of the call sites listed under Views above.
- **Overlap selects, not full containment**: a `NoteOn` event is included if its span overlaps `[tick_min, tick_max)` at all — matches Ableton/Bitwig/Logic, not a literal "fully surrounded" reading.
- **No grid snap**: unlike cursor placement, the rectangle bounds are unsnapped screen-derived ticks/notes — it's a hit-test box, not a musical position.
- **A small drag threshold gates the first update**: a plain click almost always produces a sub-pixel `MouseMoved` even with no intentional drag, and the rectangle's overlap test uses different boundary semantics than `event_id_at`'s click hit-test, so sending a rect update on that jitter could immediately clobber the click's own `SelectClipEvent` selection. The drag latches once the pointer has moved `DRAG_THRESHOLD_PX` from the anchor (`past_drag_threshold`) — `event_marquee_rect` turning `Some` is the latch; before that, `extend_event_marquee` is a no-op. Once latched it stays latched for the rest of the drag, so coming back near the anchor afterward keeps updating normally rather than freezing.
- **Silent**: unlike `SelectClipEvent`, which calls `preview_note_on` to audition the clicked note, `select_events_in_rect_workflow` does not — auditioning every note on every drag-move would spam audio.
- **Release drops the drag state, not the selection**: `MouseReleased` clears `event_marquee_anchor`/`event_marquee_rect` (`Display::clear_event_marquee`) but leaves whatever got selected in place, exactly like releasing a mouse button ends a drag without undoing its effect. Both fields are also cleared on `ClipEntered`/`ClipExited`/`ProjectLoaded`, alongside `clear_time_selection`, so no stale box survives a view change.

### Velocity Drag

- **Clip only, ⌘/Ctrl+press-drag on a note, decided at press time**: `MouseClicked` checks the modifier and hit-tests with `Display::event_id_at` *before* the normal cursor-placement/marquee logic runs; if both hit, `Display::begin_velocity_drag` takes over and the click is *not* forwarded as `MouseClickedTicks` — this is a distinct gesture, not a modified click. There is no separate "hovered event" concept; the press location doubles as the hover check, same as a marquee's press doubles as its anchor.
- **Target resolution matches Ableton**: if the pressed note is part of the current selection (read from `Display.render.event_shapes`' cached `is_selected()`, the same source `event_id_at` hit-tests against), the whole selection's velocities move together; otherwise only the pressed note is affected and the real selection (`Clip::event_selection`) is left untouched — this is why the underlying edit can't use the `clip_events_edit!` macro (see `DragEventsVelocityEdit` in `event_edits.rs`).
- **View-local drag state**: `Display.gesture.velocity_drag: Option<VelocityDrag>` (anchor y, drag id, target event ids, running total nudge — `Some` only while held, doubling as the drag-active flag) and `Display.gesture.next_velocity_drag_id`, a counter handed out once per gesture. Only vertical movement matters; `x` is ignored.
- **Every nudge round-trips through the model, like the marquee**: `Display::extend_velocity_drag` (driven by `MouseMoved`) recomputes the total nudge from the anchor (`VELOCITY_DRAG_PX_PER_UNIT`), diffs it against the last value sent, and — only when nonzero — sends `InputEvent::DragEventsVelocity { event_ids, nudge, drag_id }`, mapped 1:1 to `SequencerCommand::DragEventsVelocity`.
- **Unlike the marquee, this *is* a data mutation, so it must still undo as one step**: continuous `MouseMoved`-driven velocity nudges are coalesced by `undo::Edit::merge` on `SequencerEdit` (see `050-undo-redo.md`), gated by `drag_id` so two separate drags on the same notes never merge into one undo entry.
- **Release just drops the drag state**: `MouseReleased` clears `velocity_drag`; whatever velocity change happened stays, exactly like the marquee's selection persists after its drag state clears.

### Clip Edge Drag-Resize

- **Arranger only, press-drag on a clip's left/right edge, decided at press time**: `MouseClicked` hit-tests with `Display::clip_edge_at` *before* the velocity-drag/cursor-placement/marquee logic runs; on a hit, `Display::begin_clip_resize_drag` takes over and the click is *not* forwarded as `MouseClickedTicks` — same "distinct gesture" shape as the velocity drag above. Hover (no button held) is tracked separately in `Display.gesture.clip_resize_hover`, using the same hit-test, and drives the resize cursor icon (`egui::CursorIcon::ResizeHorizontal`, set once per frame in `update()`) — no other visual affordance; a grip glyph at the edge was tried and dropped as unnecessary on top of the cursor change.
- **Only the top `CLIP_HEADER_H`-px header band of the lane is grabbable**: `clip_edge_at` gates the whole hit-test on `y` landing in the lane's top strip (`rendering::clip_resize_band`, the same `CLIP_HEADER_H` the header strip is drawn with — `030-ui-design.md`). Without this, an edge hit-test spanning the full lane height swallowed every press near a shared clip boundary, so a click *between* two touching clips could never place the cursor / start a time selection there. The band clamps to half the lane height on a very short lane so body space always remains below it.
- **Selecting the target clip is the press's job, mirroring a plain click**: for a real clip, `begin_clip_resize_drag` sends a synthesized `MouseClickedTicks` (`SelectTrackAt` + `SetCursorAndSelectClip`) using the clip's own `start_tick` — not the raw press position, which sidesteps the exclusive-end hit-test edge case right at the boundary being grabbed.
- **Drives the "selected clip" region-length mutators by absolute target**: `Display::extend_clip_resize_drag` (driven by `MouseMoved`) snaps the pointer through the same `snap_to_grid` + `cursor_grid_ticks()` path as cursor placement (the zoom-adaptive snap in the Arranger) and sends `InputEvent::ResizeSelectedClipRegionEnd`/`Start { target_tick, drag_id }` on every move, mapped 1:1 to `SequencerCommand::ResizeSelectedClipRegionEnd`/`Start`. Both no-op when no clip is selected. The keyboard equivalent is `[`/`]` (`SetClipEdgeToCursor`, below).
- **Continuous clamp**: the trim calculators (`Sequencer::clip_end_trimmed_to`/`clip_start_trimmed_to`, `region/mod.rs`; they return the new `ClipBounds` and `ResizeClipEdit` applies them) clamp the target continuously to the available space — the edge just stops at the neighbor clip's boundary (`Track::next_clip_start_after`/`prev_clip_end_before`) or the minimum length, rather than refusing to move further. **The minimum is `time::min_clip_length_ticks()` — a beat**, a model invariant; it used to be a separate hard-coded bar (changed 2026-09-19). Until the zoom-adaptive grid it was also the arranger snap (then named `arranger_grid_ticks`); now the snap can be finer (a 16th zoomed in), so a drag snapped on a 16th still stops at one beat of length, and the constant was renamed so it stops implying a snap grid (`archive/190-arranger-zoom.md` phase 2).
- **Left-edge trim keeps `end_tick` fixed by moving `region().start()` in lockstep with `start_tick`**: shifting a clip's arrangement position without touching its loop-window offset would just move the whole clip, not trim it. Moving both by the same delta keeps the loop's playback phase locked to what's already there. This bounds the drag two ways: the previous clip's end (`Track::prev_clip_end_before`), and however far `region().start()` can retreat toward 0 — past that point the clip has no more original material to reveal, matching how a real DAW refuses to trim past a clip's recorded content. A running-capture commit deliberately leaves material to reveal: the new clip keeps the whole last pass of the take and its region is only the slice from the cursor, so the notes played before the cursor's phase sit before `region().start()` (left edge) and anything past a clamped window sits after `region().end()` (right edge) — see `100-running-capture.md` § *What a new clip retains*. Dragging either way while the transport is running and the playhead is in the gap *before* the clip is safe: `Track::tick` re-seeks a waiting clip whose start moved (`Track::awaiting_start_tick`, `050-undo-redo.md`), so the current wrap stays in phase rather than only the next one.
- **Undoable, one step per drag** (since 2026-09-25, `220-capture-without-pending-view.md` phase 2): every move is a `ResizeClipEdit` (`clip_edits/resize_clip.rs`) carrying the drag's id, drawn from `Display.gesture.next_drag_id` at `begin_clip_resize_drag` (the counter the velocity drag uses too). `SequencerEdit::merge` folds consecutive steps with the same id into one: the merged edit keeps the first `before` bounds and takes the latest `after`, so one ⌘Z undoes the whole drag. The result is `EditResult::ClipResized` (`clip_resized_workflow`: `ClipUpdated` plus the lead clip's `EventsUpdated`). No re-seek, as before.
- **Release just drops the drag state**: `MouseReleased` clears `clip_resize_drag`; the merged edit is already on the record.
- **`[`/`]` move a clip edge to the cursor** (`SequencerCommand::SetClipEdgeToCursor(ClipEdge)`, `clip_edges.rs`), undoably, as a keyboard `ResizeClipEdit` that never merges. Any modifier but ⌘/Ctrl, so layouts that type brackets with ⌥ or ⇧ reach them. The two views mean different things, like Ableton's arrangement trim and clip-view start marker:
  - **Arranger: an arrangement trim at the arranger cursor**, exactly the edge drag's clamping (content stays put in time). It acts on the clip under the cursor on the selected track, otherwise the nearest one on the side the edge faces (`Sequencer::arranger_edge_clip_id`: `[` the next clip after the cursor, `]` the last one ending at or before it), so the keys can grow a clip back toward the cursor as well as shrink it. The lead clip then re-syncs to the cursor.
  - **Clip view: a marker on the lead clip at the clip cursor.** `[` moves only the window start to the cursor (`selected_clip_start_marker_at`): the end stays, the clip keeps its arrangement start so the new 1.1.1 lands where the old one was, and the length follows (end − start). The end changes only deliberately, with `]` (2026-09-26; it used to keep the length and slide the end along); the clip stays put in the arrangement and the music under it moves. `]` ends the window at the whole bar count nearest the cursor, at least one bar, floored to the room before the next clip (`selected_clip_end_marker_at`). Both keep a captured clip whole bars (`150-clock-position-sync.md`).
  - **Always at the cursor, playing or not, and never the playhead** (a playhead tap was tried and dropped 2026-09-26, as were a restart, a relocate, and retime/wrap moves, `220`). The clip's events don't change, so the current pass plays out as it was and the next loop wrap's seek picks up the new window; an end pulled in behind the playhead leaves it running on past the end until the user restarts.
  - **The project's only clip is exact**: while the project has one clip, `]` on it ends exactly at the cursor in the clip view too; Enter fits the tempo to it (`FitFirstClipEdit`), nothing stored in between. With more than one clip, the clip view's `]` rounds up to the bar the cursor is in. While the project has one clip the loop region is that clip, following its edges (`loop_sole_clip_workflow`; the first stopped `/` also turns looping on with `TransportCommand::LoopOver`); with more clips the loop never follows. See `220-capture-without-pending-view.md`. Both `clip_resize_drag` and `clip_resize_hover` are also cleared on `ClipEntered`/`ClipExited`/`ProjectLoaded` (`Display::clear_clip_resize`), alongside `clear_time_selection`/`clear_event_marquee`, so no stale hover/drag survives a view change.

### Clip Band Press & Move Drag

- **Arranger only, press on a clip's header band *off its edges*, decided at press time**: `MouseClicked` hit-tests `Display::clip_band_at` right *after* `clip_edge_at` (and after the `SHIFT+click` arm — a Shift+click on the band extends the marquee to cover the clip instead of pressing it, see "Arranger Time Selection" above) (an edge grab keeps first refusal over the band behind it) and before the velocity-drag/cursor-placement/marquee logic; on a hit, `Display::begin_clip_move_drag` takes over and the click is *not* forwarded as `MouseClickedTicks` — the same "distinct gesture" shape as the edge resize. `clip_band_at` uses the exact `clip_resize_band` gate (`CLIP_HEADER_H`, `030-ui-design.md`) and a half-open `[start_x, end_x)` interior test on that track's shapes; the clip currently being recorded is never grabbable. Hover with no button held is tracked in `Display.gesture.clip_move_hover` and drives `egui::CursorIcon::Grab`; the held press drives `Grabbing` from mouse-down until release (keyed on `clip_move_drag.is_some()`, not on the drag threshold — otherwise a plain click flashed back to the arrow between press and release) — set once per frame in `update()`, after the `ResizeHorizontal` branch so an edge always wins. Consequence: a drag *starting* on a clip's band no longer starts a marquee — the body below the band, and empty lane, still do.
- **The press itself is "select this clip and marquee exactly its span" — unless it lands inside an active marquee, in which case it grabs everything in the marquee (see the next bullet)**: `begin_clip_move_drag` sends `InputEvent::SelectClipSpan { track_idx, clip_id }` → `SequencerCommand::SelectClipSpan` → `select_clip_span_workflow` (`src/core/event_handlers/selection.rs`), which puts the cursor on the clip's `start_tick`, runs `select_track_workflow` + `select_clip_workflow`, then pushes `UiEvent::TimeSelectionSet { start, end, track_span: Some((t, t)) }` — the one-press equivalent of dragging a marquee edge to edge over the clip, so the marquee ops (`⌘/Ctrl+D` Duplicate Clips — the motivating case — `Delete`, `⌘C`/`⌘X`, `M`) get the whole clip with no hand-dragged range. A press that never crosses the drag threshold does exactly this and nothing else. It is a sequencer round-trip rather than a view-local `time_selection` write because the marquee is cursor-anchored: `sync_time_selection_to_cursor` collapses it the frame it sees the cursor or `selected_track_idx` change with no drag anchor set, and this press changes both, asynchronously — a view-set marquee would be wiped a frame later. So the workflow sets cursor + track + clip first and sends the selection *last* on the same FIFO `UiEvent` channel, and the `TimeSelectionSet` handler (`ui_events.rs`) **re-latches** `gesture.last_cursor_tick` / `last_selected_track_idx` to their (already final) values, which makes the whole thing race-free. `TimeSelectionSet` gained `track_span: Option<(usize, usize)>` for this; the `Shift+⌘/Ctrl+D` / Delete-Time-undo senders pass `None` and keep their "preserve the active span" fallback, while plain `⌘/Ctrl+D` passes `Some` like the band press (see above). Behaviour notes: the cursor lands on the clip **start** (a plain lane click puts it at the snapped click tick) — the marquee's anchor edge must sit on the cursor (`nudge_time_selection_edge`), and it is Ableton's "selection start is the insert marker"; `⌘/Ctrl+E` straight after a band press is therefore a no-op (a split exactly on the clip's start boundary is meaningless — the same guard `from_selected_clip` already has), move the cursor first; `Delete` on the resulting marquee removes the clip whole via `DeleteInRangeEdit` (the only way a clip is ever deleted). The in-lane hover cursor line is moved to the clip start immediately at press time (`hover_cursor`) rather than a frame later when the sequencer's cursor move lands.
- **A press inside an active marquee drags everything inside the marquee — tick range × track range — as one block, and keeps the marquee**: decided at press time by the pure `marquee_under_press(time_selection, track_idx, press_tick)` (`gestures.rs`): when `time_selection` is `Some`, has real tick width (`has_tick_range`), its track range covers the pressed clip's track, and the *raw* press tick falls in `[start, end)`, the drag is `ClipMoveKind::Marquee` and **nothing is sent**: no `SelectClipSpan`, no cursor move, the marquee stays exactly as it was (it is the origin tint for the ghost). The dragged block is then the marquee's rect — `ClipMoveDrag.start_tick`/`end_tick`/`track_start`/`track_end` — rather than the clip's bounds on its one track (`ClipMoveKind::Clip`); the pressed clip's id is still kept, in `ClipMoveDrag.pressed_clip_id`, purely for the plain-click case below (whose lane also becomes the lane anchor, `press_track_idx`). A press on a partly-marqueed clip that lands *outside* the marquee's tick range — or on a track outside its track range, or with no marquee at all — is the ordinary press above: the marquee is discarded and replaced by the whole clip's span. This is also the one way to move *part* of a clip: marquee the piece (mouse drag or `⇧←`/`⇧→`), then grab its band inside the marquee — a marquee over one track and part of one clip is just the one-piece block.
- **A plain click (no drag) inside the marquee reselects the clip it landed on, same as a click outside it**: resolved at release, not press, since a `Marquee` press defers "is this a move or a click?" (the bullet above sends nothing at press time, unlike a whole-clip press, which already fires `SelectClipSpan` there — so the marquee case needs its own place to give a plain click its ordinary meaning). `finish_clip_move_drag` checks `!drag.dragging` — exactly "never crossed `DRAG_THRESHOLD_PX`", which happens to also mean `!has_moved()` (`dragging` and the ghost's target only ever change together, in `extend_clip_move_drag`/`nudge_clip_move_drag`) — so the move-commit branch and this one are mutually exclusive, never both, never neither for a `Marquee` drag. On a plain click it sends the exact `InputEvent::SelectClipSpan { track_idx: drag.press_track_idx, clip_id }` a press outside the marquee sends immediately: cursor to the clip's start, the clip selected, its span marqueed — collapsing the block selection down to just the one clip clicked, exactly Ableton's behavior for clicking a clip inside an existing selection. A drag that crossed the threshold and returned home (net zero delta) is a completed drag, not a click, and reselects nothing — same as a whole-clip drag returning home.
- **Hold and drag = move; the drag is a purely view-local ghost — nothing in the sequencer changes until release**: `Display.gesture.clip_move_drag: Option<ClipMoveDrag>` (`pointer_state.rs`: the clip, its press-time bounds, the raw `grab_offset_ticks`, the press point, a `dragging` latch, and the live `target_start_tick`/`target_track_idx`) is `Some` only while the button is held, doubling as the drag-active flag. `extend_clip_move_drag` (driven by `MouseMoved`) latches `dragging` once the pointer is `DRAG_THRESHOLD_PX` (3px, shared with the event marquee) off the press point, then recomputes the ghost's absolute target each move — never accumulates — as `snapped_move_start(pointer_tick, grab_offset, grid)` = `snap_to_grid(pointer_tick − grab_offset_ticks, cursor_grid_ticks())` clamped `≥ 0` (same zoom-adaptive arranger snap as cursor placement and the edge resize; keeping the grab offset holds the block under the hand instead of jumping its start to the pointer), and the lane delta as `track_idx_at(y) − press_track_idx` — off the lanes the pointer counts as the press lane (the same wander rule as `extend_time_selection`) — run through `clamped_track_delta` so the *whole* block stays on the lanes (a two-lane block can't be dragged one lane past the bottom). Both kinds move by one `delta_ticks` + `delta_tracks` (`ClipMoveDrag::delta_ticks()`), never per-clip targets. It **sends nothing**. Rendering (`draw_arranger_view`, `030-ui-design.md`): the clip keeps drawing at its real position at full opacity — that is still the data — and a translucent copy (`CLIP_GHOST_ALPHA`) is drawn last, at the target, over whatever it hovers; the marquee from the press stays on the *origin* for the same reason. The ghost (`draw_clip_move_ghost`) is every clip in the block translated by the drag delta — the one clip for `Clip`, every clip on the marqueed lanes overlapping the marquee's ticks for `Marquee` — each painted through `draw_clip_at`'s `window` (its overlap with the block, shifted) so a straddling clip shows just its marqueed piece, with its note thumbnails still lined up to where they sit inside the clip, exactly as the split-out piece will look once dropped. A `Marquee` ghost is additionally framed by `draw_marquee_ghost_frame`: the shifted rect itself, full lane-row height across every lane it spans, as a light `theme::fg_dim()` fill (no outline — tried, read as clutter) under the ghost clips — so a selection with gaps, or one reaching past its clips, keeps its shape mid-drag, and with the source marquee still tinted where it is both "from" and "to" read at once (the Logic / Bitwig / Live convention for a dragged selection). No auto-scroll at the viewport edge, no modifier to disable snap, no multi-clip or ⌥-duplicate variant — all could layer on `ClipMoveDrag` later.
- **Release is the single commit point, and it is undoable — unlike the edge resize**: `MouseReleased` → `finish_clip_move_drag`, which sends one event only when the drag latched *and* the ghost sits off the block's own position (`ClipMoveDrag::has_moved` — a non-zero tick or lane delta); a plain press or a drag returned home sends nothing. A `Clip` drag sends `InputEvent::MoveClip { track_idx, clip_id, to_track_idx, to_start_tick }`; a `Marquee` drag sends `InputEvent::MoveRange { rect, delta_ticks, delta_tracks }` — the marquee itself travels in the event because it is view-local state the sequencer has never seen. Release then re-runs the band hover test at the drag's last recorded pointer position (`ClipMoveDrag::last_x`/`last_y` — `MouseReleased` carries no coordinates and the hover was cleared at press), so a plain click goes closed hand → open hand instead of dropping to the arrow until the next `MouseMoved`; after a real move the moved shape only appears under the pointer once `ClipAdded` lands, so there the next `MouseMoved` restores the hand. It carries explicit ids rather than "the selected clip" because the press's selection round-trip is asynchronous. `input_handler.rs` maps both 1:1 (Arranger-gated) to `SequencerCommand::MoveClip` → `MoveClipEdit::new(..)` / `SequencerCommand::MoveRange` → `MoveRangeEdit::new(..)` + `undo_record.edit` (`050-undo-redo.md`). **`MoveClip`**: the clip is lifted off its source track, `DeleteInRangeEdit::from_track_range` carves exactly its destination span out of the destination track (built *after* the lift, so a same-track move over its own old span never carves itself), and the clip is put down there with the same id and an untouched region — a move never trims. Whatever it landed on is trimmed / split / removed Ableton-style, non-destructively like every other carve. **`MoveRange`**: the marquee's tick range is first split out of every clip it overlaps on the marqueed tracks (two track-scoped `SplitClipsEdit`s — at `rect.end`, then `rect.start` — the same non-destructive `⌘E` cut `Delete`/`M` use, so every leftover and piece keeps the full event list and only the region windows differ; a piece keeps its clip's id when it starts at the clip's start, otherwise it is the fresh right-hand product of the split at `rect.start`), then *every* piece is lifted before any carve — so a block shifted by less than its own width never carves its own pieces — and each piece's destination span is carved out of its destination track and the piece dropped there, shifted by the one `(delta_ticks, delta_tracks)`. The resize stays non-undoable because it only touches region length; a move can destroy other clips' spans, so it must be a `SequencerEdit`. Since no data mutates during the drag, each is a single discrete edit — not the per-`MouseMoved` `Edit::merge` pattern the velocity drag needs.
- **After a move (and after its undo) the clip is left exactly as a fresh band press would leave it**: `move_clip_workflow` / `unmove_clip_workflow` (`clip_range_edits.rs`) do `sequencer.reset()`, clear the clip selection, `ClipRemoved` for the old position, the carve buckets (`paste_clips_workflow`'s order forward, `unpaste_clips_workflow`'s on undo), `ClipAdded` for the new one, then re-run `select_clip_span_workflow` on the clip where it now sits — cursor on its start, track + clip selected, span marqueed. Always remove + add even on a same-track move: clip shapes are keyed by `(track_idx, clip_id)` and `update_clip_shape` can't change lanes. The selection is cleared *first* so the reselect is a real state change rather than a no-op on an unchanged id (the lead clip is model-only state — nothing renders it — so this is about `Shift+Tab`/`/` targeting, not pixels). `MoveClipEdit` carries no frozen selection context for the same reason — the clip always survives and is always reselected.
- **After a marquee move the marquee follows the block; after its undo it goes back**: `move_range_workflow` / `unmove_range_workflow` do the same reset + clear, then `ClipRemoved` for every piece at its source (`moved_from` — a no-op for a piece that was split out mid-clip, since the UI never saw that fresh id), the split buckets (`ClipUpdated` for the id-keeping leftovers, `ClipAdded` for the new right-hand ones — forward; `ClipRemoved` for those on undo), the carve buckets, `ClipAdded` for every piece at its destination (forward) / for every re-merged source clip (`restored`, undo — `ClipAdded`'s add-or-replace in `add_clip_shape` covers a leftover shape the UI still has and one that left with its piece alike). Then `select_range_workflow`, the block equivalent of `select_clip_span_workflow`: cursor to `rect.start`, `rect.track_start` selected, the clip under the cursor there selected if it is one of the pieces (forward) / restored originals (undo) — the same cursor-clip rule as `paste_clips_workflow` — and `UiEvent::TimeSelectionSet { .., track_span: Some(..) }` last, with the rect shifted by the delta (`RangeMoved.new_selection`) or the original (`RangeUnmoved.restored_selection`), so the block stays selected where it landed and a second band press inside it moves it on. Sent last for the same re-latch reason as the band press. Always remove + add even on a same-track move: clip shapes are keyed by `(track_idx, clip_id)` and `update_clip_shape` can't change lanes. The selection is cleared *first* so the reselect is a real state change rather than a no-op on an unchanged id (the lead clip is model-only state — nothing renders it — so this is about `Shift+Tab`/`/` targeting, not pixels). `MoveClipEdit` carries no frozen selection context for the same reason — the clip always survives and is always reselected.
- **Esc cancels a live drag; view changes drop it**: the Arranger `Escape` arm calls `clear_clip_move_drag()` beside `clear_time_selection()` — the ghost vanishes, nothing is committed. `clip_move_drag`/`clip_move_hover` are also cleared on `ClipEntered`/`ClipExited`/`ProjectLoaded`, alongside the other `clear_*` drag resets.
- **`⌘/Ctrl+←`/`→` is the keyboard twin of the marquee band drag — horizontal-only, no mouse required — and shares its ghost-preview-then-single-commit shape rather than mutating on every press**: bound in `forward_input_event` beside `⇧←`/`⇧→` (same "the operand is view-local" rationale as `⌘/Ctrl+L`), gated on `modifiers.command && !modifiers.shift && !modifiers.alt` so only the exact chord arms a destructive drag — a stray ⇧ contends with the marquee-*resize* binding, a stray ⌥ with cursor navigation. **It was `⌥←`/`⌥→` originally and was rebound**: the move is the rarer, heavier gesture, while ⌥ is the conventional "coarser cursor step" modifier (word-jump in every text editor) and sits closer to the arrows — so ⌥ is reserved for cursor navigation (`⌥←`/`⌥→` clip-edge jumps, below) and the move took ⌘/Ctrl. `⇧⌘/Ctrl+←`/`→` is deliberately unbound *and consumed* by its own arm ahead of the `⇧` nudge: it must neither keep nudging as if ⌘ weren't held nor fall through to the handler's plain cursor step. `Display::nudge_clip_move_drag` (`input/gestures.rs`) is the keyboard sibling of `begin_clip_move_drag`/`extend_clip_move_drag`: the first press with a real-tick-width `time_selection` and no drag already in progress arms a `ClipMoveDrag { kind: Marquee, via_keyboard: true, .. }` straight into `dragging: true` (a keypress is already deliberate — unlike a mouse press, there's no "was that just a click?" threshold to cross) with `target_start_tick` one grid step (`cursor_grid_ticks()`) from the marquee's edge; each further press while that same drag is live nudges `target_start_tick` by one more grid step from wherever the ghost *already* sits (`nudged_ghost_start`, clamped `>= 0`) rather than re-deriving from a live pointer tick, since there is no pointer. `delta_tracks` stays `0` for the drag's whole life — no vertical twin, `⌘↑`/`⌘↓` do nothing — **enforced**: while a keyboard-armed drag is live, the first arm of `forward_input_event`'s match consumes every `KeyPressed` except unshifted `←`/`→` (the nudge) and `Escape` (cancel), because ⌘/Ctrl is held for the drag's whole life so every key is a ⌘/Ctrl chord of the gesture, not a separate command — and since the rebind that includes every real `⌘/Ctrl+X` command (`⌘S`, `⌘Z`, `⌘D`, `⌘L`, …), which is right: none of them should fire under a live ghost; before that arm existed, `⌥↑`/`⌥↓` (the chord at the time) fell through to the plain `↑`/`↓` track cycling — and after the rebind the same arm also refuses ⌥-chorded `←`/`→`, which neither the move arm (`!alt`) nor the clip-edge jump arm (`!command`) would claim and which would otherwise reach the handler's plain cursor step under a live ghost, moved `selected_track_idx` under the live ghost and wiped the marquee tint via `sync_time_selection_to_cursor`, while the frozen drag rect still committed on the original tracks — the UI contradicted the move. Ignoring is the standard answer here (a stray key during a modifier-held nudge neither commits nor cancels in any editor; the modifier release is the commit boundary and Esc the cancel), and the keyboard mirror of "the mouse never touches a keyboard-armed drag" below (shifting a selection across tracks is a heavier gesture than "nudge it a little" and stays mouse-only, unlike Ableton, which also has no track-axis arrow-key nudge). This reuses the *exact* ghost + ghost-frame rendering already built for the mouse drag (`draw_clip_move_ghost` keys only on `clip_move_drag.dragging`, blind to `via_keyboard`) — so holding ⌘/Ctrl and tapping `→` repeatedly shows the same translucent preview sliding across whatever it passes over, carving nothing until commit. **An earlier version sent one `MoveRangeEdit` per keypress directly**; that carved into and truncated whatever the ghost passed over at each intermediate grid step instead of just its final resting position — the same destructive-preview problem the ghost exists to avoid for the mouse drag, so it needed the same fix. Committing on every press versus previewing-then-committing-on-release is a real, if under-discussed, UX fork for this exact gesture (arrow-key nudge of a selection) — Photoshop/Illustrator-style modifier-held nudges preview and commit on release; this app now follows that, matching its own mouse-drag convention instead of introducing a second, more destructive commit model for the same operation.
- **`MoveModifierReleased` is the commit trigger — the keyboard drag's only exit besides Esc**: a new `InputEvent` (`input_event.rs`; named for its role, not the key, so a rebind doesn't ripple), detected in `InputPoller` (`view/input_poller.rs`) the same way `MouseReleased` is — polling `i.modifiers.command` (⌘ on macOS, Ctrl elsewhere — the same key every `⌘/Ctrl+X` binding tests) for a down→up edge each frame, mirroring `left_mouse_down`'s pattern — rather than relying on an `egui::Event`, since egui doesn't surface a modifier's own release as one. `forward_input_event`'s `MoveModifierReleased` arm calls `finish_clip_move_drag()` — the *exact* function `MouseReleased` calls — only when `clip_move_drag.is_some_and(|d| d.via_keyboard)`, so releasing ⌘/Ctrl mid an unrelated *mouse* band drag (a live one always has `via_keyboard: false`) can't stomp on it; it's a no-op the rest of the time, including every other ⌘/Ctrl release in the app (after `⌘S`, `⌘Z`, …). Same guard (`dragging && has_moved()`) as the mouse path, so tapping ⌘/Ctrl with no arrow presses, or presses that net to zero, commits nothing. Esc still cancels a keyboard-armed drag exactly like a mouse one (`clear_clip_move_drag()`, unconditional on view). **The mouse never touches a keyboard-armed drag**: `extend_clip_move_drag` returns early on `via_keyboard`, and the `MouseReleased` arm only calls `finish_clip_move_drag()` when the live drag is *not* `via_keyboard` — the mirror of the `MoveModifierReleased` guard. Without the first, a nudge's ghost (armed straight into `dragging`, so past the threshold check) was yanked to the pointer by the first stray mouse motion while ⌘/Ctrl was held; without the second, a click during a nudge committed it on release. Standard practice (Photoshop/Illustrator nudges, DAW keyboard moves): the pointer only drives a drag the *button* started, and a keyboard move is owned by the keyboard until its own commit/cancel. The pointer icon follows the same rule: the `Grabbing` closed hand in `update()` and the hover no-op in `update_clip_move_hover` are both keyed on a live drag that is *not* `via_keyboard`, so during a nudge the pointer stays an arrow and still shows the open hand over a band, exactly as if no drag were in progress. If a fresh mouse gesture is started while a keyboard nudge's ghost is still showing (⌘/Ctrl held, no arrow press since), `begin_clip_move_drag` simply overwrites `clip_move_drag` — the pending nudge is silently discarded uncommitted, not merged or force-committed first; a narrow, physically awkward edge case (holding ⌘/Ctrl while separately mouse-pressing) judged not worth the extra state to handle specially, since nothing has actually mutated yet at that point either way. `KeyModifiers` gained an `alt` field for all this — the keypad controller thread and the plugin-editor key guard have no alt key of their own and always report `false`.
- **The `MoveModifierReleased` arm also calls `ctx.request_repaint()` — load-bearing, not decorative**: sending `InputEvent::MoveRange` only *starts* the commit; the sequencer thread applies it and mails back the `ClipRemoved`/`ClipAdded`/`TimeSelectionSet` `UiEvent`s that actually move the drawn shapes and the marquee, and `Display` only drains those on its *next* frame. The mouse-driven commit has the identical round trip and the identical one-frame lag — "after a real move the moved shape only appears under the pointer once `ClipAdded` lands, so there the next `MouseMoved` restores the hand" (above) — but it's invisible there because releasing a mouse button after a drag is essentially always followed by more pointer motion, which forces the next frame anyway. Releasing ⌘/Ctrl has no such guaranteed follow-up: with the pointer stationary and no other input pending, egui's reactive loop would otherwise sit idle for however long — the ghost gone, the content still drawn at its pre-move position — reading as "the move was cancelled," until some unrelated later input (a click, an arrow press, moving the mouse) happened to wake a frame and reveal it had actually landed all along. `forward_input_event` gained a `ctx: &egui::Context` parameter for this (threaded from `handle_input_events`, its one caller) — the same `EventHandlers::request_repaint()` idiom used for every other background-round-trip wake in this codebase, just called directly since this runs on the UI thread inside a live frame already, with no need for the cross-thread `repaint_ctx` indirection that idiom exists for.

### Track Header Volume / Pan Drag

- **Arranger only, press-drag on an instrument track's header bar, decided at press time**: `MouseClicked` hit-tests with `Display::track_mix_bar_at` **before** `clip_edge_at` / velocity / cursor logic — most specific first — and on a hit the click is *not* forwarded as `MouseClickedTicks`. The press deliberately does **not** change the selected track or move the cursor: touching a fader is not a navigation gesture. Bars only exist for tracks where `Display::track_has_instrument` is true (a CLAP plugin editor is loaded); off macOS there are none.
- **⌘/Ctrl+click on a bar resets it** to neutral (`0.0` dB / centre) and starts no drag — resolved inline in `MouseClicked` from the `modifiers` it already carries. No conflict with the ⌘+drag velocity gesture, which is clip-view only.
- **View-local drag state**: `Display.gesture.track_mix_drag: Option<TrackMixDrag>` (`Some` only while the primary button is held — doubles as the drag-active flag, like every other drag here) carrying `track_idx`, `param: TrackMixParam` (`Volume`/`Pan`), the press `anchor_y`, the parameter's `anchor_value` at press time, and `last_sent`. `Display.gesture.track_mix_hover: Option<(usize, TrackMixParam)>` is the hover-only counterpart, driving `egui::CursorIcon::ResizeVertical` (set once per frame in `update()`, beside the `ResizeHorizontal` branch).
- **`extend_track_mix_drag(y, shift)` recomputes an absolute value from the anchor** — never accumulates deltas (the drift rule every extender follows) — quantises it (0.1 dB / 1 pan unit) and sends `InputEvent::SetTrackVolume`/`SetTrackPan` only when it changed since `last_sent`. `TRACK_MIX_DRAG_PX_FULL_TRAVEL` (240px) spans the whole travel; **holding Shift divides the rate by 5** for fine adjustment (this is why `MouseMoved` now carries `modifiers`). Not gated on `is_mouse_inside_clip_content` — wandering off the bar mustn't cancel a live drag.
- **`input_handler.rs` maps the two `InputEvent`s 1:1** onto `SequencerCommand::SetTrackVolume`/`SetTrackPan`, Arranger-gated. The handler applies them as **direct mutations of `SharedAtomics.track_mix`** — no `undo_record.edit`, no `EditResult` — exactly like `SetSelectedTrackOutput` and matching the region-length precedent in `050-undo-redo.md`.
- **Release just drops the drag state**: `MouseReleased` clears `track_mix_drag`; the value stays. `track_mix_drag`/`track_mix_hover` are also cleared on `ClipEntered`/`ClipExited`/`ProjectLoaded` (`Display::clear_track_mix_drag`), alongside the other `clear_*` drag resets.

### Track Header Mute / Solo Buttons

- **Arranger only, a plain click on the S (solo) or M (mute) button in a track header**: `MouseClicked` hit-tests `Display::track_button_at` **first of all** — ahead of `track_mix_bar_at` and `clip_edge_at`, most specific first — and on a hit sends `InputEvent::ToggleTrackSolo`/`ToggleTrackMute { track_idx }` and returns without forwarding `MouseClickedTicks`. Like the fader press, this deliberately does **not** select the track or move the cursor.
- **Shown on every track, unlike the volume/pan bars**: mute/solo gate note emission in `Sequencer::tick`, which covers external MIDI-out tracks too, so `track_button_at` loops all `TRACK_COUNT` tracks with no `track_has_instrument` filter. The button row is still laid out by the shared `track_header_rects` geometry, so it lands at the same y in every lane whether or not that track shows bars below it.
- **View-local hover state only**: `Display.gesture.track_button_hover: Option<(usize, TrackButton)>` (`TrackButton` = `Solo`/`Mute`) drives `egui::CursorIcon::PointingHand` (set once per frame in `update()`, beside the `ResizeVertical` branch) and is cleared in `Display::clear_track_mix_drag` alongside the mix-bar hover/drag. There is no click-drag — a click is instantaneous — so there is no `TrackButtonDrag`.
- **`input_handler.rs` maps the two `InputEvent`s 1:1** onto `SequencerCommand::ToggleTrackMute`/`ToggleTrackSolo`, Arranger-gated. The handler flips the flag in `SharedAtomics.track_mix` (`mute`/`solo`, `[AtomicBool; TRACK_COUNT]`) as a **direct mutation** — no `undo_record.edit`, no `EditResult` — exactly like the volume/pan drag and `ToggleMetronomeMute`. Audibility is the pure `mix::track_is_audible(muted, soloed, any_solo)` (`core::audio::mix`) — mute wins over solo on the same track — derived at the point of use, never stored.
- **Silencing is immediate and total, both routes**: on a change that silences a track mid-playback the sequencer calls `release_track_notes`, which queues that track's currently-sounding clip note-offs (the `Track::pending_note_offs` path clip-mute uses) so nothing hangs — notes held on the physical keyboard are untouched. For hosted-instrument tracks that only stops *new* sound; the **reverb / delay tail** is cut by `InstrumentMixer::target_gains` forcing that track's output gain to `0.0` while it is inaudible (ramped out over one buffer, click-free). External MIDI-out tracks get only the note-offs — their tail lives in outboard gear the app can't reach.
