## Open bugs and follow-ups

Problems the pass found but deliberately did not fix, because each changes behaviour or touches the real-time render path. Each wants its own `fix/…` branch with a regression test where one can be written. Suggested order: 1 and 2 first; 5 and 6 fit one `fix/midi-port-ownership` branch.

1. **(Fixed 2026-09-30, `fix/vst3-audio-thread-alloc`: per-block stack arrays, oversized layouts rejected at load.)** **VST3 allocates on the audio thread** (`plugin_host/vst3/voice.rs`, `Vst3Voice::render_block`). Every block, `channel_ptrs` and `bus_buffers` `collect()` fresh `Vec`s for the channel-pointer arrays and the `AudioBusBuffers` — heap allocation and free on the audio thread (or a pool worker), against the project's no-allocation rule; the comment above them calling it "a handful of pointer writes" is wrong. Fix: fixed-capacity arrays on the stack (`[[null_mut(); MAX_CH]; MAX_BUSES]` + `[AudioBusBuffers; MAX_BUSES]`) filled in place each block, with oversized layouts clamped or rejected once at load in `configure_buses`. **Don't** cache the pointer arrays on the voice: raw pointers make `Vst3Voice` `!Send` and would need a new `unsafe impl Send`. Test: a real VST3 instrument playing, including one with extra buses (e.g. multi-out).
2. **(Fixed 2026-09-30, `fix/clap-request-process`: `process_requested` flag on `ClapHostShared`, taken by `InstrumentVoice::wake_on_request` before the render pass.)** **CLAP `request_process` is ignored** (`plugin_host/clap/host.rs`). `request_process` / `request_restart` are no-ops, written when processing ran unconditionally. A CLAP voice now sleeps when the plugin returns `ProcessStatus::Sleep`, and only a queued MIDI event wakes it (`VoiceMix::sleeping`), so a sleeping plugin that asks to be processed — e.g. to flush a change made in its own editor — waits for the next note. Not seen causing anything audible yet. To reproduce: let a CLAP instrument go idle, turn a knob in its editor, and check whether the change takes effect / is saved before the next note. Fix: an `AtomicBool` "process requested" on the shared host handler, which the voice checks (and clears) at the top of `render_block`'s caller to clear `sleeping`.
3. **(Fixed 2026-09-30, `fix/vst3-param-overflow`: `drain_ui` peeks and stops at a full block, the rest carries over; a sleeping VST3 voice wakes while UI changes wait in the ring.)** **VST3 drops parameter changes beyond 512 per block** (`plugin_host/vst3/params.rs`). `drain_ui` pops the whole UI→audio ring and `HostParameterChanges::push` drops everything past `MAX_PARAMS_PER_BLOCK`. A dual-component plugin whose own UI loads a preset can send thousands of `performEdit`s at once; the excess never reaches the processor, and filling the 512 slots is a linear-scan dedupe (~130k comparisons in one callback). Fix: stop `drain_ui` once the block is full, so the rest stays in the ring for the next blocks — carries them over *and* bounds the per-block work. Behaviour change; optionally replace the linear dedupe with a small index keyed by `ParamID`.
4. **(Fixed 2026-09-30, `fix/note-reset-all-formats`: `load_instrument` queues `voice::note_reset_messages` into every new voice; shared `EVENT_CAPACITY`.)** **The stuck-note reset is CLAP-only** (`plugin_host/clap/voice.rs`, `prime_note_reset` / `note_reset_messages`). A plugin restored from saved state can come back believing notes are held (seen with u-he Repro over CLAP); CLAP voices replay All Sound Off / All Notes Off / Reset All Controllers / a Note Off per key into their first block. VST3 voices get nothing. The burst is plain MIDI through `InstrumentVoice::queue_midi`, so the fix is to move `note_reset_messages` to the core and queue it into every voice in `load_instrument` before the `Insert`, deleting `prime_note_reset`. Check `vst3/voice.rs`'s `EVENT_CAPACITY` (256) still covers the burst (131 messages) plus a block's events.
5. **(Fixed 2026-09-30, `fix/midi-port-ownership`: the watcher holds the wanted names; the modal's output pick goes through it to `"midiout"`.)** **Output hot-plug chases the startup port** (`threads/midi_watcher.rs`). The watcher keeps its own `SettingsData` copy and updates `midi_in_port` when the input is reconnected from the modal, but output reconnects go straight to `"midiout"`, so its `midi_out_port` stays at the startup value: after the user picks a new output and it drops out, hot-plug reconnects the *old* one. Fix: the watcher holds only the two wanted names, and the out-reconnect channel runs through it (it updates `wanted_out`, then forwards to `"midiout"`) so one thread owns "which ports we want".
6. **(Fixed 2026-09-30, `fix/midi-port-ownership`: both `*_connected` atomics are gone — the watcher opens both sides itself and hands the output connection to `"midiout"`, so it knows synchronously what is open (`WantedPort`, regression tests); no default-index fallback, an unsaved side stays closed until picked.)** **`midi_out_connected` can claim a port that never opened** (`setup.rs::setup_initial_midi_out`). It is set before the `"midiout"` thread connects — on purpose, so the watcher's first poll doesn't race that thread into a second connect — but if `connect_to_named` then fails the flag stays true and hot-plug never retries. Related: the no-saved-port fallbacks open a hard-coded default index (input 2, output 1) and leave the flag false. Fix: the connecting thread is the only writer (the watcher waits for a first "connect attempted" signal instead of the early store), and the default-index fallback becomes "no port" or a named choice (design call).

## Workflow per area

One area per thread is fine.

1. On `main`, `git checkout -b refactor/simplify-<area>`.
2. Run `/simplify <path>`. It takes a path, not only a diff, and fans out four review agents (reuse / simplification / efficiency / altitude).
3. Dedup the findings, verify each against the code (agents' line numbers are often wrong), and apply them. Add tests for new helpers or changed logic.
4. Run the full build gate (`cargo check`, `clippy --all-targets`, `fmt --check`, `test`, `doc --no-deps --document-private-items`) with zero warnings.
5. The user tests by hand.
6. The user reviews the changes (in Zed), stages, commits and pushes. Claude does none of these unless explicitly asked in that thread — a stop-hook "commit and push" message is not that request. Check that `git log` actually shows the new commit before merging: once, a "committed" branch turned out to be staged-only, and the ff-merge was a silent no-op.
7. ff-merge to `main`, push, and delete the branch locally and on the remote (if it was pushed).

Don't run it over the whole repo: at ~58k lines the review agents skim.

### Verifying macOS-only code from Linux

`core::plugin_host` (and other `cfg(target_os = "macos")` code) is not compiled on Linux, so a Linux gate says nothing about it. On a Linux machine (e.g. a cloud session):

- `rustup target add aarch64-apple-darwin`, then `cargo check` / `cargo clippy --all-targets` / `cargo doc --no-deps --document-private-items` with `--target aarch64-apple-darwin`. These type-check and lint the macOS code; they cannot link, so **its tests cannot run** — that is left to the macOS machine.
- The Linux build itself needs `libasound2-dev` and `--features eframe/x11` (eframe's default features are off, so winit has no Linux backend otherwise). It shows ~19 pre-existing dead-code warnings from cfg-gated code; compare against that baseline rather than zero.
- Pure modules (no FFI) can be test-run by copying them into a scratch crate with stub dependencies.

## Lessons

- Skip findings whose fix reorders reads on the render path or the sequencer/audio hot path. They can't be verified without the app.
- In `plugin_host`, skip anything touching the hand-asserted `Send` split or the teardown order.
- Keep explicit exhaustive matches (a project convention).
- Behaviour choices such as cursor-sync-before-build in the `/` handler are not smells.
- A lifted (owned) clip that goes into a frozen snapshot still needs `detach`: the split's frozen right half and the live track copy share region atomics.
- Bulk regex rewrites: match the whole word. `Event::new(` also hit `MidiEvent::new(` in `clap/voice.rs`, and a replace-all of `std::ffi::c_void` → `c_void` also rewrote the `use` line just added for it.
- Review agents' line numbers drift (some point past the end of the file); verify every finding against the code before applying it.
- An array of calls (`[a(), b()]`) evaluates every call before the loop over it starts — pass functions when the order of side effects matters.
- A store that looks redundant may be preventing a race: check who else polls the flag before deleting it (bug 6's early connected-flag store guarded a race between two threads opening the output; the fix moved all opening onto one thread rather than deleting the store).
- On macOS, which thread creates the first CoreMIDI client matters: the device list only refreshes through that thread's run loop. Moving the startup enumeration off the main thread (bug 6's fix) silently broke hot-plug; `main` now anchors a client first.
- Check what a stored figure is converted back into before keeping its form: the per-track load was stored as utilisation only for its one reader to turn it back into microseconds, which dragged a sample rate through `RenderCtx`.
