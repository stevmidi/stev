# Architecture

**macOS is the supported platform**; the codebase also builds and passes its tests on **Linux and Windows** in CI (§ CI), but those are untested beyond that, and the plugin host is macOS-only (`240` § B). The UI is rendered with `egui`/`eframe` (glow backend) and driven by egui's native keyboard/mouse input. Keyboard bindings are catalogued in `010-keybindings.md`. (The project originally targeted a dedicated hardware keypad; that scope was dropped and its notes are archived in `archive/010-keypad.md`, deliberately unindexed.)

## Threading Model

Named threads. The core set communicates exclusively via `crossbeam-channel`; the `"audio-engine"` thread is fed by an `rtrb` ring (scheduled metronome clicks) and is described below. No shared mutable state beyond `Arc<AtomicX>` — mostly values the UI reads on the hot render path.

| Thread | Role |
|---|---|
| `"clock"` | BPM tick pulse → `tick_tx` as `ClockTick { at, tick }`; `at` is each tick's intended `Instant`, interpolated across the timer firing's real elapsed span (`Clock::tick_offset_ns`) so the plugin host can schedule clip events to the sample; `tick` is the absolute counter value (drives `Metronome` beat/discontinuity logic; the clock knows nothing of the meter). Musical time is credited from real elapsed nanoseconds, not a nominal 1 ms per firing. Also publishes `SharedAtomics.clock_tick_instant_nanos` (the `time::monotonic_nanos` of the last tick) so the MIDI-input callback can sub-tick-correct recorded notes, and credits `SharedAtomics.elapsed_ticks` — the transport odometer, stepped alongside `clock_tick` but only while running and never realigned. |
| `"sequencer"` | Core logic: ticks transport, handles MIDI in/out + all commands via `select!` |
| `"midiout"` | Receives `MidiOutMessage`, drives `MidiOutputConnection`. Clip messages carry their tick's intended `Instant` and are held in a `MidiOutQueue` until that instant + `SharedAtomics.midi_out_offset_ms`, so external gear lands with the plugin and click paths rather than a buffer ahead of them; live thru, chased notes, previews and the `NoteLogger` release carry no instant and go straight out. The queue is dropped on `ReleaseNotes` and on a port reconnect. See `160-midi-out-offset.md`. |
| `"midiwatcher"` | Owns which MIDI IN/OUT ports are wanted and opens them: at startup, on the modal's pick, on hot-plug (outputs handed to `"midiout"`); sends `UiEvent::MidiPortsRefreshed` |
| `"audio-engine"` | Owns the single `cpal` output stream (`src/core/audio/`), summing every `AudioSource` into the device buffer over one shared `AudioClock` (`Instant` → output-frame mapping, jitter-filtered). Always carries the built-in `MetronomeSource` (synthesized click, fed scheduled `ClickEvent`s on an `rtrb` ring from `Metronome` on the sequencer thread); on macOS the plugin host's `InstrumentMixer` is added as a second source at startup. Exits quietly if no output device exists. |
| `"audio-worker-N"` | macOS only, `N` = `min(cores - 1, MAX_TRACKS - 1)`. The engine's `WorkerPool` (`src/core/audio/worker_pool.rs`). Parked until the audio callback publishes a section, then they claim per-item work off a shared cursor alongside the callback thread and ack; the callback never returns before every one has. Today the only user is `InstrumentMixer`'s render pass, one item per instrument track. Empty pool off macOS. See `170-multicore-scheduling.md`. |
| `"audio-journal"` | Drains the overrun journal ring (`src/core/audio/journal.rs`) every 250 ms and appends one post-mortem line per overrun to `~/Library/Logs/stev/audio-overruns.log` (macOS; local-data dir elsewhere — path printed at engine start). Never touches the file until the first overrun. |
| `"plugin-host"` | macOS only. **No audio** — the `InstrumentMixer` runs inside the `"audio-engine"` callback as an `AudioSource`. This thread only reclaims removed plugin voices (`dead_rx` → drop the `Box<dyn InstrumentVoice>` off the audio thread → ack `Display`) and coordinates app-exit shutdown (`HostShutdown`). The mixer sums one hosted instrument plugin per `TrackOutput::Instrument` track, of whichever format that track picked (`InstrumentVoice`; CLAP today); voices are added/removed via a `cmd_rx` ring from `Display`; MIDI arrives on two tagged `rtrb` rings — per-track clip events (`Sequencer`, `ClipInstrumentEvent` carrying the tick's intended `Instant`, scheduled to the sample + a constant one-buffer delay) and live keyboard notes (`(track index, Midi3)`, `MidiInputForwarder`, played at the head of the block). It also hands each voice a per-block `BlockTransport` snapshot of `SharedAtomics`, which the voice translates into its own format's transport type. See `130-plugin-host.md`. |
| `"plugin-catalog-scan"` | macOS only. Runs the merged plugin catalog scan once at startup and reports it **per format** (cheapest first), so CLAP plugins reach the browser's Plugins category without waiting for VST3. CLAP bundles are enumerated in-process; **VST3 bundles are scanned one child process each** — some plugins' `bundleEntry` requires a main thread of its own — with the results cached on disk against each bundle's mtime. The sender is dropped when the scan finishes, which is how `Display` knows it is complete. See `180-vst3-host.md`. |
| `"main"` (eframe) | Renders UI via `Display` (`eframe::App`): `App::logic` pumps the plugin editors (runs even while the window is hidden), `App::ui` drains `input_event_rx`, dispatches `InputEvent` to `EventHandlers` and paints |

The `"midiwatcher"` thread is the one owner of *which* ports are wanted (the saved names, then the user's picks from the MIDI settings modal) and the one place ports are opened. It runs a `select!` loop over the modal's `midi_in_reconnect_rx` / `midi_out_reconnect_rx` and a 2 s poll timeout; the first poll runs immediately and opens the saved ports. A poll hot-plugs a wanted port that isn't open (matched ignoring the ALSA suffix) and sends `UiEvent::MidiPortsRefreshed` (+ a repaint) only when the port lists changed. It owns the live `MidiInputConnection` and `MidiInputForwarder`; an output it opens is handed to the `"midiout"` thread on `midi_out_connection_tx` (a closed connection when the open failed, so the old port closes either way), and that thread owns it from then on. With no saved port, or a pick that fails, that side stays closed (no default-port fallback). Never exits. On macOS, `main` creates the process's first CoreMIDI client on the main thread (`anchor_coremidi_to_main_thread`) before any MIDI thread starts: CoreMIDI keeps the device list current through the run loop of the thread that created the first client, and a MIDI thread has none — the watcher would then never see a device plugged in after launch.

All channels are defined in `src/core/shared_channels.rs`. All atomics are in `src/core/shared_atomics.rs` — always read with `Ordering::Relaxed`.

The `"audio-engine"` thread (`src/core/audio/`) builds the `cpal` default-output stream, holds it (its lifetime is the engine's; `Stream` has been `Send` on CoreAudio since cpal 0.17, so this is ownership, not a `!Send` constraint) and parks forever; the stream's own callback thread does the rendering. The callback zeroes a per-channel mix buffer, calls `AudioClock::observe` once, lets each registered `AudioSource` add into the mix, then hard-clips the sum to ±1.0 before converting to the device format. Sources get one `RenderCtx` per sub-block (`frames`, `first_frame`, the shared `AudioClock`) rather than a widening parameter list. Every callback first calls `enter_render_thread` (`src/core/audio/thread_role.rs`), which marks the thread for CLAP `thread-check` and calls `flush_denormals_to_zero` (`src/core/audio/denormals.rs`) — `MXCSR` `FTZ`/`DAZ`, per-thread and so also set once per `WorkerPool` worker — so a decaying reverb / filter tail doesn't fall off the x86 fast path into a ~100-cycle-per-op microcode assist; no-op on aarch64. The callback also times itself: `AudioLoad` (`src/core/audio/load.rs`) records the share of that block's real-time budget (`frames / sample_rate` — 5.33 ms at 256 frames / 48 kHz) the render actually consumed. That is **deadline utilisation on one thread**, which is what predicts a dropout — not process CPU percent, which is a throughput figure spread over every core. It is kept as a rolling average plus a decaying peak in two lock-free `f32`-bit-pattern atomics (audio thread is the only writer), plus two latched counters — `overruns` (render ran past its budget) and `xruns` (the backend's own overload notification, `ErrorKind::Xrun`, latched from the stream's error callback) — and handed to `Display` via `EngineHandle::load` / `attach_audio_load`, and shown as the header's `DSP` readout. A third atomic latches the count of blocks that reached 1.0 — real dropouts, since CoreAudio's IOProc has no queue to absorb a late callback — surfaced as the `OVR` chip and cleared on each transport start. The whole-block figure says *that* a block ran over; **attribution** says who: the engine times each `AudioSource::render_into` (named via `AudioSource::name`), and the `InstrumentMixer` times each voice's `render_block` (stored in `VoiceMix::render_time`, then `AudioLoad::record_track` per track, in microseconds — every slot rewritten every block, zero for a skipped voice). When `AudioLoad::record` returns the overrun verdict, the callback builds one fixed-size `Copy` `OverrunRecord` (wall clock, frames, total, per-source and per-track microseconds) and pushes it onto an `rtrb` ring for the `"audio-journal"` thread — no allocation or formatting on the audio thread. The journal line's `other` figure is the callback time no source claims (mix-down, conversion, worker hand-off), so a spike there rather than in a source is itself a finding. `MetronomeSource` is always present: `Metronome::on_tick()` (`src/core/metronome.rs`, a sequencer-thread-local like `Transport`, fed one `ClockTick` per clock firing) pushes a `ClickEvent { class, at }` onto an `rtrb` ring on every counted beat of the project's `Meter` (`Meter::beat_ticks`: each quarter in x/4, each eighth in x/8, so six clicks a bar in 6/8), strong on the bar's downbeat while running; the source drains the ring, maps `at` to an output frame with `RenderCtx::scheduled_frame` (the shared `AudioClock` plus the same one-buffer `SCHEDULE_DELAY_FRAMES` the plugin clip events get, through the same helper, so the click and a hosted synth on the same beat land on the same sample), and retriggers a short synthesized sine burst (enveloped, no sample assets). The click is gated by `SharedAtomics.metronome_mute` (**default muted**, toggled by `TransportCommand::ToggleMetronomeMute` → `Metronome::toggle_mute()`). If no output device is available the thread logs via `dprintln!` and exits, leaving the app fully functional without a click. This is the only metronome — the former MIDI note-trigger metronome (which drove an external sampler track on MIDI channel 10) has been removed. On macOS the plugin host's `InstrumentMixer` is added to the same engine as a second `AudioSource` (`EngineHandle::add_source`) at startup — one stream, one mix; see `130-plugin-host.md`.

**One deliberate exception to "channels + atomics only"**: `EventHandlers` also holds `repaint_ctx: Arc<OnceLock<egui::Context>>`, filled in once at startup from `eframe::run_native`'s creation closure in `main.rs`. It exists so a background thread can call `egui::Context::request_repaint()` and wake the reactive UI when it changes state the window needs to reflect but that didn't arrive via a native window input event (e.g. a MIDI trigger read by `midir` on the sequencer thread) — see `110-performance-lane.md` for the motivating case. Prefer this over polling (`request_repaint_after` gated on some "might need it soon" flag) for any future case in the same shape.

## Module Layout

```
src/core/
  config.rs              — Constants (BPM_DEFAULT=90, BARS_IN_VIEWPORT=32 (default arranger zoom), ARRANGER_MIN_PX_PER_BEAT, MAX_PX_PER_BEAT + ZOOM_KEY_STEP (shared by the arranger and clip views), PHRASE_DETECTION_WINDOW_BARS=4, MAX_TRACKS=16 (capacity of every per-track array), DEFAULT_TRACK_COUNT=4, TEMPO_US_DEFAULT, etc.)
  time.rs                — Tick/bar/beat math, PPQN, MICROSECONDS_PER_MINUTE, tempo helpers, the `Meter` time signature (unit-tested)
  audio/                 — Unified audio engine: "audio-engine" thread + one cpal stream, AudioSource trait, shared AudioClock, MetronomeSource (synthesized click voice)
  metronome.rs           — Metronome: per-tick beat/click-class decision + mute gate (sequencer-thread-local), pushes ClickEvents to the engine ring
  plugin_host/           — macOS only. Per-track instrument plugin host: format-agnostic core (InstrumentMixer added to the audio engine as an AudioSource, InstrumentVoice/InstrumentEditor traits, transport snapshot, merged catalog, "plugin-host" voice-reclaim thread) + one submodule per format (clap/, vst3/). vst3/ scans bundles in child processes (see 180). See 130-plugin-host.md
  threads/               — Thread factory functions, one file per named thread (mod.rs: clock + audio engine; midi_output.rs; midi_watcher.rs; sequencer_pump.rs; controller.rs)
  paths.rs               — on-disk layout: library_dir (~/Documents/Stev) / project_dir (its Projects/), config_dir, cache_dir
  settings.rs            — SettingsData (midi_in_port, midi_out_port, midi_out_offset_ms); load_settings / update_settings → settings.json in paths::config_dir()
  midi/                  — input.rs (MidiInputForwarder + channel routing), input_tick.rs (sub-tick timestamping of live input — see 150-clock-position-sync.md), output.rs (MidiOutputConnection), out_queue.rs (MidiOutMessage + MidiOutQueue, the MIDI-out delay queue — see 160-midi-out-offset.md), message.rs (Midi3 = [u8;3] for the instrument route; note-edge and wheel parsing; `is_recorded`, what a take keeps off the input — see 090), port.rs (VIRTUAL_PORT_NAME, port_base_name)
  project/               — dto.rs (serializable ProjectData + Sequencer mapping), storage.rs (.stev filesystem CRUD), smf.rs (.mid reader + writer)
  sequencer/             — Sequencer state, capture, clip ops, region/phrase token logic, SequencerCommand enum, performance_lane (armed state, live-trigger routing)
  event_handlers/        — EventHandlers: input_handler, transport_handler, sequencer_handler, performance_lane_handler; workflows split by concern — selection, clip_view, clip_lifecycle, clip_range_edits, edit_result_handler, live_recording, project, command_helpers
  transport.rs           — TransportCommand / TransportEvent / TickOutcome enums (TickOutcome::Wrapped re-anchors a loop wrap synchronously in the tick pump)
src/main.rs              — Wiring entrypoint; owns native_options() (eframe::NativeOptions)
src/models/              — Clip, Event, Track, Region, PerformanceLane, Selection, WheelTracker (wheels.rs — see 050 § Invariants) (pure data, no I/O)
src/view/                — Display (egui/eframe rendering), InputPoller, UiEvent enum
src/shapes/ / metadata/  — Rendering primitives; render-side clip snapshots (ClipMetadata, ClipView) built by core
```

Key enums: `TransportCommand`, `TransportEvent`, `SequencerCommand`, `ViewState` (Arranger/Clip — the settings modal and the help overlay are overlays on `Display`, not views), `InputEvent`.

## Build and Test

```bash
# Run locally
cargo run --release --package stev --bin stev

# Compile-check
cargo check --package stev --bin stev
```

A unit test suite lives in `mod tests` blocks at the bottom of each relevant `.rs` file (using `#[cfg(test)]`). Run it with:

```bash
cargo test
```

The full gate, all of which must come back clean before a change is done:

```bash
cargo fmt --check
cargo check --all-targets
cargo clippy --all-targets                    # 0 warnings
cargo test
cargo doc --no-deps --document-private-items  # 0 warnings
```

`cargo doc` is in the gate because rustdoc is the only checker for intra-doc
links — a renamed method leaves `[`old_name`]` pointing at nothing and nothing
else complains. `--document-private-items` is what makes it useful here: nearly
every item is `pub(crate)`, so without it rustdoc walks almost none of the
codebase. Note it caches aggressively; `touch src/main.rs` first to force a
re-check of an unchanged tree.

### CI

GitHub Actions (`.github/workflows/ci.yml`) runs the gate above on `ubuntu-24.04`, `windows-2025` and `macos-26` (Apple Silicon), with `RUSTFLAGS`/`RUSTDOCFLAGS=-D warnings` so a warning fails it. Each platform compiles different `cfg` code (the plugin host is macOS-only, the user-facing virtual MIDI port is `unix`-only), so every one runs the full set. `fmt --check` runs on Linux only, being the same everywhere. A separate job runs `cargo deny check licenses` against `deny.toml` (`080` § Licensing); egui's bundled-font licences are allowed there for `epaint_default_fonts` alone. The same job regenerates `THIRD-PARTY-NOTICES.md` with `cargo-about` (pinned to 0.9.2, since another version can word the file differently) and fails if it differs from the committed file, so a dependency change can't leave the notices stale. Design settled in `240` § B.

- **When it runs**: on push to `main`, on every pull request into `main` (contributors' from forks included), and from the Actions tab's "Run workflow" button for any branch. A change that only touches `docs/**` or `*.md` files is skipped (`paths-ignore`, on both triggers), because no code includes a Markdown file. If one ever does (`include_str!` of the README), drop that pattern. The author's own branches are fast-forwarded locally, with no PRs, so CI reports on their changes after the merge and a red `main` is fixed forward; a contributor's PR is checked before it's merged. The repo's Actions setting for fork pull requests is set to require approval for first-time contributors (`240` § C, publication day), so a stranger's first PR, workflow changes included, runs only after the maintainer has looked at it.
- **The toolchain is pinned** in `rust-toolchain.toml` (`1.98`, with `clippy` + `rustfmt`). Local `cargo` uses it too, since rustup reads the file. A new stable's lints therefore can't fail `main` on a day nothing changed. Upgrading is a one-line commit that also fixes whatever the new lints raise. The runner images are pinned for the same reason. A `-latest` label moves to a new OS on GitHub's schedule (`ubuntu-latest` → 26.04 from 2026-10-19), so the versions are bumped on purpose when GitHub announces a retirement. `ubuntu-24.04` matches the live USB the Linux smoke test uses. `macos-26` is the only build and test on Apple Silicon, since the development Mac is Intel.
- **Linux builds with plain `cargo`**: a Linux-only `eframe` entry in `Cargo.toml` turns on its `x11` + `wayland` backends, which `default-features = false` otherwise drops. The runner installs `libasound2-dev` and `pkg-config` (ALSA, for cpal and midir).
- **What it can't cover**: a runner has no screen, audio or MIDI devices, so CI proves compile, lint, docs and unit tests. Whether the app sounds right on Linux/Windows is the manual smoke test (`260-porting.md` § Smoke test). A unit test must not need a real device.
- **Checking another platform before pushing**: `080` § Agentic Editing.

`cargo clippy` also enforces `missing_docs_in_private_items` (wired into
`Cargo.toml` `[lints.clippy]`): every item, bare struct field and enum-variant
field included, carries a `///`, and every `.rs` file a `//!` header. An
undocumented item is a build failure. See `080-conventions.md` § Documentation
for the house style.

Tests cover pure and pure-logic functions in `src/models/`, `src/core/time.rs`, `src/core/transport.rs`, and pure geometry helpers within `src/view/` that don't touch `Display` state (e.g. `src/view/display/rendering/piano_keys.rs`). The rest of `src/core/sequencer/` and `src/view/` (anything needing live channels, a running eframe context, or `Display` fields) is not unit-tested. All behavioural validation beyond unit tests is done by running the binary.

**Capture fixtures** (`fixtures/captures/*.json`, `src/core/sequencer/capture_fixture.rs`): real takes kept as test data for the phrase-start detection. A debug build run with `STEV_CAPTURE_DIR=<dir>` dumps every stopped `/` capture there. After correcting the start with `[` and saving, `STEV_CAPTURE_DIR=<dir> STEV_PROJECT=<file.stev> cargo test extract_picked_starts -- --ignored --nocapture` writes the corrected start into each fixture. Copy the fixtures into `fixtures/captures/`, where `the_detection_picks_every_fixture_start` pins the detection to them (`220`).

**Test authoring policy**: when adding or changing logic in a testable layer, write or update `mod tests` in the same file as part of the same change. Bug fixes should include a regression test that would have caught the bug. Do not add tests for trivial accessors or for code in the untestable layers listed above.

## Integration Points

- **MIDI I/O**: `midir` abstractions; raw bytes (`Vec<u8>`) on the MIDI-in / MIDI-out channels. The in-process instrument route (clip + live feeds to the `InstrumentMixer`) instead carries `Midi3` (`[u8; 3]`, `core::midi::message`) so nothing crossing an `rtrb` ring to the audio thread has a heap payload to free there.
- **Audio**: `cpal` (default output device), all platforms — the unified audio engine in `src/core/audio/` owns the one output stream and sums its `AudioSource`s. `MetronomeSource` (synthesized click, no sample assets) is always present; on macOS `src/core/plugin_host/`'s `InstrumentMixer` is added as a second source, rendering one hosted instrument plugin per `Instrument` track (CLAP, via `clack-host`) — see `130-plugin-host.md`. No other audio I/O.
- **Graphics**: `eframe` (`glow` backend) with `egui` immediate-mode painter for all custom rendering. Entry point is a plain `fn main()` calling `eframe::run_native()`; on macOS a window close returns from it into `exit(0)`, as AppKit's `terminate:` would (`060` § Unsaved changes). `macroquad` has been fully removed — do not reintroduce it or its types (`macroquad::input::KeyCode`, etc.); all key/mouse handling goes through `egui::Key` / `egui::PointerButton`.
- **Input**: Keyboard and mouse input flow through egui's native input system (`InputPoller` in `src/view/input_poller.rs` polls `egui::Context` each frame and emits `InputEvent`s). Mouse-driven cursor placement is handled entirely inside `Display` (`view/display/input/` — `mod.rs` for the dispatch loop and `forward_input_event`, `gestures.rs` for the drag state machines, `modal.rs` for the settings modal's keymap and mouse, `settings_modal.rs` for opening/closing it, its tabs and list scroll; `help.rs` and `help_overlay.rs` likewise for the help overlay); see `020-views-and-state.md` for details. `start_controller_thread` (`#[allow(dead_code)]`, currently unused) is kept deliberately as a reference implementation for a MIDI-CC-based hardware controller — do not propose deleting it; it mirrors the legacy keypad mapping in `archive/010-keypad.md` and is the only other potential `InputEvent` producer besides `Display` (it never sets `modifiers.command`/`alt`).
- **Clock**: `MachWaitUntilTimer` on macOS (mach absolute time, spin-wait tail); `SleepTimer` on Linux/Windows. Musical time is credited from real elapsed nanoseconds between firings; `archive/140-device-frame-clock.md` is a deferred proposal to credit it from the audio device frame count instead — not implemented. The free-running `clock_tick` counter and `playback_tick` are held to `clock_tick ≡ playback_tick (mod region_length)` — *not* absolute equality, since playback wraps at the region end while the clock free-runs past it. `Transport::align_clock_with_playback{,_if_running}` sends `ClockCommand::AlignToPlayback`, and `Clock::aligned_tick` moves the counter onto playback's *phase* — by the smallest signed step, never by assignment, so the loop index it free-ran to survives. A separate counter, `elapsed_ticks`, carries elapsed musical time for live recording: same crediting, but gated on `running` and never realigned, because a duration must not move when a position does. See `150-clock-position-sync.md`.
