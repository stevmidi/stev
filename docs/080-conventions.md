# Project Conventions

## Command & Channel Patterns

- **New commands go through channels**: add a variant to the relevant enum (`SequencerCommand`, `TransportCommand`), send via `EventHandlers`, and handle in the sequencer thread's `select!` loop.
- **No locks on the render path**: UI-visible state must use `Arc<AtomicX>` in `SharedAtomics`, not channels or mutexes.
- **`dprintln!` for debug logging**: compiles away in release via `#[cfg(debug_assertions)]`. Use it instead of `println!`.
- **Platform guards**: use `[target.'cfg(...)'.dependencies]` for platform-specific crates (on macOS `mach2`, the plugin host's crates and the AppKit bindings) and `#[cfg(target_os = "...")]` for per-OS code (e.g. the plugin host's `#[cfg(target_os = "macos")]` module in `main.rs`). The one Linux-only entry re-declares `eframe` with its `x11` + `wayland` window backends, which `default-features = false` otherwise drops (`000` § CI). `cpal` (the unified audio engine, `src/core/audio/`) is an all-platform dependency.
- **Edition 2024**: use current Rust idioms freely.

## EventHandlers

- **`EventHandlers` is stateless**: it holds only channel senders and `Arc` refs. Business logic lives in `sequencer/` or `transport.rs`.
- **Extract match arms to a per-concern workflow file**: when a match arm in `handle_sequencer_command` / `handle_transport_command` grows into multiple operations, or two or more arms share the same logic, extract it to an `impl EventHandlers` method (`pub(super)`) in the `event_handlers/` file that owns that concern — `selection.rs`, `clip_lifecycle.rs`, `clip_range_edits.rs`, `clip_view.rs`, `project.rs`, `live_recording.rs`, `command_helpers.rs` (transport-command senders), `edit_result_handler.rs` (`EditResult` dispatch), etc. Add a new file if none fits. This per-concern split is the primary DRY mechanism for `event_handlers/`; there is no single `workflows.rs`.
- **Prefer helper methods for duplicated logic**: when two or more branches repeat non-trivial logic, extract a helper/workflow method to keep code DRY and side effects consistent.

## Code Quality

- **Keep instructions in sync with code**: when workflows, command routing, or `EditResult`/`SequencerEdit` shapes change, update the relevant rules file in the same patch to prevent guidance drift.
- **Prefer existing functions**: before introducing new methods or commands, check whether existing ones can be reused or composed to achieve the same goal. New abstractions should only be added when no existing path fits.
- **Avoid redundant state fields**: before adding a new field to a struct, verify it cannot be derived from existing fields at the point of use. Tracking fields that duplicate or shadow existing data (e.g. a `phrase_start_tick` that is always equal to an already-mutable `start_tick`) add noise and risk divergence — update the existing field directly instead.

## Naming & Organization

- **Naming of new modules and members**: try to follow the current naming standards to keep code organized.
- **Function parameter naming should follow local conventions**: prefer names that match existing parameter vocabulary in the same module/type (for example `selected_event_ids` over introducing one-off variants).
- **Sorting of modules and members**: when introducing new modules place it where it belongs according to existing folder structure. When introducing new members, try to place them where they belong according to the current organization that is present in the module. Try to place it within the correct group if any and in the right location within the group if you see a clear pattern.
- **`tick` is a position, `ticks` is an amount**: singular names a point on a timeline (`cursor_tick`, `playback_tick`, `start_tick`, `rec_start_tick`, `elapsed_start_tick`); plural names a quantity of musical time — a length, a delta, a span, or a free-running counter of accumulated time (`bar_ticks`, `delta_ticks`, `span_ticks`, `tolerance_ticks`, `elapsed_ticks`, and the `bars_to_ticks` / `beats_to_ticks` family). A type bundling several tick values takes the plural for that reason (`InputTicks` carries a position *and* an amount; contrast `ClockTick`, which is one tick).
  This distinction is load-bearing, not cosmetic: `150-clock-position-sync.md` records two separate bugs that were a position and a duration being conflated — one corrupted running capture, one corrupted recorded takes. A name that says which kind it is, is the cheapest guard against a third.
  One exemption: a **collection** of positions keeps the plural, because that is the ordinary Rust convention and it wins (`pending_visible_token_start_ticks: Vec<i32>`, `refined_token_start_ticks`).
  **Persisted DTO fields follow the rule too, but changing one is a file-format change, not a rename** — the field names in `core/project/dto.rs` *are* the literal JSON keys in every saved `.stev`, with no `#[serde(rename)]` indirection, and both are required fields, so a rename makes existing projects fail to load with a missing-field error. `ClipData.start_tick` and `EventData.tick` were renamed from the plural on 2026-09-05 with the projects on disk migrated in the same change; `clip_and_event_json_keys_are_the_on_disk_format` in `dto.rs` pins the result. Renaming another one means migrating the files or adding `#[serde(rename)]` to hold the old key. See `060-persistence.md`.
  The codebase was swept to this rule in 2026-09 and every remaining plural was classified by hand, so what is left is either a genuine amount (`bar_ticks`, `silence_ticks`, `tolerance_ticks`, `sub_ticks`, `nudge_cursor_by_ticks`, `cursor_grid_ticks`, `delta_ticks`, the `*_to_ticks` and `*_straight_ticks` families) or a collection. A new `_ticks` name for a position is a mistake, not precedent. Do **not** bulk-rename `_ticks` → `_tick`.
- **Parameter order must be consistent across declaration and all call sites**: when a function or constructor has a declared parameter order, all call sites must pass arguments in exactly that order. When adding a new parameter, choose its position in the declaration first (matching any logical grouping convention — e.g. channels before atomics in `EventHandlers::new()`), then update every call site to match. Never let constructor/function parameter order drift from the struct field order it mirrors.

## Enum Patterns

- **`from_u8` discriminants must stay clean and contiguous**: `ViewState` and similar enums are never persisted to disk — their `u8` values are only stored in in-memory atomics during a session. When a variant is added or removed, renumber the remaining variants to stay contiguous and ordered (0, 1, 2…). Do not keep legacy compatibility arms in `from_u8` for values that can never appear at runtime.
- **Prefer descriptive enums over mode booleans**: when behavior branches by intent (for example operation target or strategy), prefer a small named enum over `bool` flags like `do_x: bool`. This keeps call sites self-describing and reduces ambiguity during refactors.

## Clip & Model Rules

- **Edit-only helpers stay with the edit**: private helpers used exclusively inside an edit struct are private `impl Sequencer` methods within the appropriate file under `src/core/sequencer/edit/`. A non-undoable mutation called straight from an `event_handlers/` workflow is an `impl Sequencer` method in the `sequencer/` file for its concern (e.g. `mix.rs`'s `set_track_volume`).
- **Clip timeline mapping must go through `Clip` helpers**: never inline conversions between arrangement ticks (`start_tick` timeline) and clip event ticks (`region.start..region.end` timeline). Use `event_tick_from_arrangement_tick`, `arrangement_tick_from_event_tick`, and `phase_from_event_tick` in `src/models/clip/cursor_region.rs`.
- **Non-zero region starts are first-class**: code must support `region.start != 0` while preserving correct seek/play-from-cursor behavior.

## Imports

- **Always use `use` imports**: never refer to types, traits, or functions via their full crate path inline (e.g. `crate::models::event::Event`, `super::super::config::X`). Always add a `use` declaration at the top of the file and reference the short name instead. Never place `use` statements inline inside function bodies — all imports belong at the top of the file. This applies to `#[cfg(...)]`-gated items too: add a `#[cfg(...)] use ...` line at the top rather than an inline path on the field/signature.
- **The only exception**: a short (≤ 3 segment) `std::` helper path used as a call — `std::mem::swap(a, b)`, `std::iter::once(x)`, `std::array::from_fn(..)`, `std::thread::park_timeout(..)`. Anything longer, and any `std::` constant/type (`std::f32::consts::TAU`, `std::sync::atomic::Ordering`), still gets a `use`.
- **Optional hard enforcement**: `clippy::absolute_paths` with `absolute-paths-max-segments = 3` flags every offender (it also flags the longer `std::` paths, which is consistent with the rule above). Not currently wired into `Cargo.toml` `[lints]` — turning it on requires clearing the ~20 existing offenders first.

## Clippy Rules

- **Merge `if`/`else if` arms with identical bodies**: Clippy rejects two branches that return the same expression (`clippy::if_same_then_else` / "identical blocks"). Always combine them with `||` into a single arm rather than repeating the body.
- **Collapse nested `if` blocks**: Clippy rejects a nested `if` inside another `if` when the outer has no `else` (`clippy::collapsible_if`). Always merge them into a single `if` with `&&` rather than nesting.

## Documentation

- **Every item is documented, and the lint enforces it**: `clippy::missing_docs_in_private_items = "warn"` is wired into `Cargo.toml` `[lints.clippy]`. Combined with the zero-warning `cargo clippy --all-targets` gate, an undocumented item — including a bare struct field or enum-variant field — is a build failure. A new item does not compile clean until it has a `///`; a new `.rs` file needs a `//!` header (a bare `mod x;` is covered by the target file's `//!`).
- **Explain *why*, not *what***: `/// Returns the clip id.` on `fn id()` is noise — say what the id is *for* (stable across edits, the key the undo system records against). Where a getter genuinely has nothing to add, one short clause is fine, but prefer stating the invariant the field upholds. A `//!` header answers: what the module owns, who calls it, and the design decision or invariant a reader would otherwise get wrong.
- **The house voice** — match these, don't invent one: `src/core/midi/out_queue.rs` (a header that explains why the thing exists; field docs that name the invariant), `src/core/audio/mix.rs` (constants documented with the reasoning behind the value), `src/core/audio/clock.rs` (a tuning constant with what raising/lowering it trades off), `src/core/sequencer/mix.rs` (a header that places the module in the architecture).
- **Cross-reference the topic docs** with the bare filename in backticks (`see \`150-clock-position-sync.md\``) rather than re-explaining. Use intra-doc links (`` [`TrackMixAtomics`](crate::core::shared_atomics::TrackMixAtomics) ``) for cross-module references — but a name already in the module's scope resolves as a bare `` [`Name`] `` (an over-qualified path is a `redundant explicit link target` warning, and `cargo doc` is in the gate). When documenting a `_tick` / `_ticks` name, say whether it is a position or an amount (see the `tick`/`ticks` rule above).

## Licensing

- **The project is dual-licensed `MIT OR Apache-2.0`** (`LICENSE-MIT`, `LICENSE-APACHE`, `license` in `Cargo.toml`), the Rust ecosystem default. Decided 2026-10-01: the repo is private for now but headed for open source as an opinionated app others are free to fork (`240` § Principle), so it must stay publishable as it grows. No per-file licence headers; the root files cover the tree, as is Rust convention. `README.md` carries the standard inbound = outbound contribution clause, so contributions arrive under the same dual licence without a CLA.
- **A new dependency must be licence-compatible.** Check the crate's `license` field before adding it, including what it pulls in transitively: `cargo deny check licenses` (CI runs it on every push) or `cargo metadata --format-version 1 | jq -r '.packages[] | select(.source != null) | "\(.name): \(.license)"'`. `deny.toml`'s `allow` list is the machine form of this bullet: a licence it doesn't list fails CI until someone decides. Add it there only if it fits the rules below. Fine: MIT, Apache-2.0, BSD-2/3-Clause, ISC, Zlib, 0BSD, Unlicense, Unicode-3.0, and any `OR` choice that offers one of them. MPL-2.0 is tolerated (file-level copyleft: only a modified copy of that crate's own files has to stay MPL). GPL, LGPL or AGPL with no permissive alternative is a no, because it would make every distributed build copyleft. Where a crate offers a choice, we take the permissive side.
- **Known non-plain entries** (surveyed 2026-10-01, so a new one stands out): `option-ext` is MPL-2.0 (via `dirs`); `self_cell` is `Apache-2.0 OR GPL-2.0-only` (we take Apache); `epaint_default_fonts` is egui's bundled fonts under OFL-1.1 + Ubuntu Font Licence (Noto Emoji, Ubuntu Light) and MIT + Bitstream Vera (Hack, the emoji icon font; its `license` field misses these), which only ask for attribution notices once binaries are shipped.
- **`THIRD-PARTY-NOTICES.md` ships with every binary** and is generated, never edited: `cargo about generate about.hbs -o THIRD-PARTY-NOTICES.md` (`cargo install cargo-about --locked --features cli`, version 0.9.2 to match CI). Regenerate it in the same change as any `Cargo.lock` change; CI fails when it's stale. `about.toml` covers the macOS targets only (the only ones shipped), skips Stev itself (`publish = false`), and pins each egui font licence file by checksum, so an egui upgrade that changes the fonts stops generation until someone checks them. `about.hbs` holds the two notices cargo can't see, because they come from headers the bindings were generated from: the VST 3 SDK's MIT text (for `vst3`) and CLAP's (for `clap-sys`). Bump the SDK version and copyright there when `vst3` moves to a newer SDK.
- **No third-party content without a redistributable licence**: samples, presets, wavetables, fonts and images included. A committed third-party asset carries its licence file beside it. Local-only material stays gitignored: `assets/instruments/` holds commercial sample content and must never be committed.
- **Plugin formats: VST3 and newer only, never VST2.** The VST2 SDK is no longer licensed by Steinberg and can't be redistributed under our licence, so no VST2 headers, bindings or hosting code. "VST" is Steinberg's trademark: using it to denote compatibility follows their usage guidelines (`240-release-plan.md` § C), and it never goes into a product or feature name. In practice: ® on the first "VST" of each user-facing document (README, CHANGELOG, CONTRIBUTING), the sentence "VST is a registered trademark of Steinberg Media Technologies GmbH." in it, and the VST Compatible logo (`docs/images/vst/`, light and dark variants) on every web page that mentions VST support: the README, release notes, and later the website. The topic docs under `docs/` are developer documentation of the host's internals and don't carry it.
- **Describe, don't imitate.** User-facing text (README, CHANGELOG, CONTRIBUTING, release notes, the repo description, the website) describes what Stev does in its own terms. It may say a workflow is "inspired by" a commercial DAW, but never "clone", "free <DAW>" or "<DAW> alternative", and shows no other company's logos or product screenshots (the VST Compatible logo, used under Steinberg's guidelines, is the exception). Naming another product to say what Stev doesn't do ("no Ableton Link") or to compare behaviour in the developer docs ("Ableton-style") is fine. A screenshot shows Stev's own window only, never a plugin's editor.

## Changelog and Versions

- **`CHANGELOG.md` gets a line in the same change** as anything a user would notice, and anything that could break a project or a fork, under `## [Unreleased]` in its Keep a Changelog section (`Added`, `Changed`, `Fixed`, `Removed`). Internal refactors, test-only and doc-only changes don't need one. Write it for a user, not a reviewer: what they can now do or what behaves differently, not which type changed.
- **Breaking** (marked as such, with what to do about it): a `.stev` from an earlier version no longer loads, or loads with something lost or changed — renaming or removing a DTO field is one, adding a `#[serde(default)]` field isn't (`060`); a large rename or module move; a new `AGENTS.md` ground rule. Before 1.0 a breaking change bumps the minor version, anything else the patch.
- **Releasing**: move `## [Unreleased]` under a `## [x.y.z] - YYYY-MM-DD` heading and start a new empty `[Unreleased]` above it; set `version` in `Cargo.toml` to match (that changes `Cargo.lock`, so regenerate `THIRD-PARTY-NOTICES.md`, § Licensing); run the build gate; commit; then tag that commit on `main` with an annotated tag, `git tag -a vx.y.z -m "Stev x.y.z"`, and push it (`git push origin vx.y.z`). Tags are never moved or deleted once pushed: forks and users treat them as fixed points. A GitHub release's notes are a web page that mentions VST, so they carry the VST Compatible logo and the trademark sentence, like the README (§ Licensing).

## Agentic Editing

- **`/simplify` before merge**: every branch gets a `/simplify` pass over its diff (`git diff main...HEAD` plus uncommitted work) before it is merged to `main`. Apply the fixes, re-run the full build gate, then hand it over for manual testing. Dedup findings across the review angles, and **skip** (noting why) any finding that:
  - reorders reads or adds work on the render path or the sequencer/audio hot path — these can't be verified without running the app;
  - collapses an explicit exhaustive `match` into a wildcard arm — listing every variant is deliberate, so a new variant fails to compile at each site (e.g. the `ClipContext` matches);
  - changes behaviour (e.g. selection lead, event order, when the transport moves) rather than structure;
  - needs a design change well outside the diff — record it for later instead.
  - touches `plugin_host`'s hand-asserted `Send` split or its teardown order.
- **Verify review findings against the code**: review agents' line numbers drift, so check each one before applying it. Bulk regex rewrites must match whole words (`Event::new(` also hits `MidiEvent::new(`). A store that looks redundant may be guarding a race — check who else polls the flag before deleting it.
- **Checking another platform's code locally**: each OS compiles different `cfg` code, so a change can be clean here and fail CI elsewhere. `check` / `clippy --all-targets` / `doc --no-deps --document-private-items` take `--target`. They type-check and lint without linking, so tests stay with CI or the native OS. First run `rustup target add <triple>` (it installs for the pinned toolchain).
  - **Windows from macOS or Linux**: `--target x86_64-pc-windows-msvc`. Nothing else is needed.
  - **Linux from macOS**: `--target x86_64-unknown-linux-gnu`. `alsa-sys`'s build script wants pkg-config to find ALSA, so point `PKG_CONFIG` at a stub that exits 0 and prints `-lasound` for `--libs` and `1.2.0` for `--modversion`, and set `PKG_CONFIG_ALLOW_CROSS=1`. `ALSA_NO_PKG_CONFIG` doesn't work, because alsa-sys aborts on it. Nothing links, so the stub is enough.
  - **macOS from Linux** (e.g. a cloud session): `--target aarch64-apple-darwin` reaches the plugin host.
  - **Dead code off one platform**: an item used only by `cfg`-gated code (the plugin host) is unused elsewhere. Mark it `#[cfg_attr(not(target_os = "macos"), allow(dead_code))]` (or the matching `cfg`, e.g. `not(unix)` for the virtual-port code), rather than gating it out.
- **The completed whole-codebase pass** (2026-09-30) is archived in `archive/230-simplify-pass.md`; read it only for the per-area findings deliberately left.
- **Agentic File Editing**: When AI agents utilize `.sh` shell scripts (e.g. `awk`, `sed`) to perform robust file parsing or string operations, **all temporary scripts must be explicitly deleted** (`rm patch_*.sh` etc.) immediately after task verification to keep the workspace pristine.
